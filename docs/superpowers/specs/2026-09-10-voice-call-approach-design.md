# 호출 접근 설계 — "비카야"로 부르면 다가간다

2026-09-10 · 대상 저장소 `vica-voice-llm` + `vica_ros2_ws`

## 1. 무엇을 만드나

**방아쇠 하나다.**

지금 로봇은 눈으로 본 사람에게만 말을 건다. 귀는 "비카야"를 듣고 소리 방향까지
알아내지만, **그쪽으로 고개를 돌릴 줄 모른다.** 카메라는 정면만 보므로 옆이나
뒤에서 부르면 영영 못 본다.

이 문서는 **소리 쪽으로 고개를 돌리는 동작 하나**를 붙인다. 고개만 돌리면 그
다음은 전부 이미 있다.

### 이미 있는 것 (dev `c9bd12b` 에서 확인)

| 단계 | 위치 | 상태 |
| --- | --- | --- |
| "비카야" 감지 | voice `wakeword_monitor.py` (`vica_bikaya_v1.onnx`) | ✅ |
| 호출 순간 DOA 잠금 (±15°·120초) | voice `wakeword_monitor.py:895` | ✅ **ROS 로 안 나감** |
| `/vica/wake` 발행·구독 | voice `ros_wakeword_node.py:72` / mission `_on_wake` | ✅ **IDLE 은 무시** |
| 사람 발견 → 자동 접근 요청 | perception `person_detector_node.py:224` | ✅ |
| 사람 앞 1.1 m 정지 | mission `approach_geometry.approach_goal()` | ✅ |
| "안내를 받으시겠어요?" | `MSG_APPROACH_QUESTION` | ✅ |
| "네/아니오" 판정 | voice 규칙 우선 + LLM 폴백 → `/vica/intent` | ✅ |
| 수락 → **로봇 180° 회전**(핸들을 사람 쪽으로) | `approach_turn_yaw_deg=180.0` → `SpinInPlace(π)` | ✅ |
| 온보딩 → "어디로 가고 싶으신가요?" | `MSG_APPROACH_ONBOARDING` | ✅ |

즉 **YOLO 경로의 후반부 전체가 그대로 재사용된다.** 이 설계는 그 앞에 진입로를
하나 더 낼 뿐이다.

### 새 노드는 만들지 않는다

발행은 기존 웨이크워드 노드가, 처리는 기존 Mission Manager 가 한다. 노드가 늘면
CPU·기동순서·문서가 전부 따라 움직이므로 늘리지 않는다.

## 2. 마이크 사실 (2026-09-10 실측)

| | |
| --- | --- |
| 모델 | reSpeaker USB 4-Mic Array **v3.0** · 칩 XVF3000 · `2886:0018` |
| 채널 | 6ch — ch0 처리음(AEC·잡음억제·빔포밍 완료) / ch1~4 원음 / ch5 재생참조 |
| DOA 읽기 | `DspState.doa_angle()` — USB vendor control transfer, 파라미터 id21 `DOAANGLE`, 0~359° |
| 권한 | `/etc/udev/rules.d/99-respeaker.rules` 적용됨(`MODE=0666`). 읽기 확인 완료 |
| 기준선 | **핸들 = 180°** (2026-09-01 `doa_probe` 실측, 표본 33, 범위 172~180) → **정면 ≈ 0°** |

### 한계 3가지 — 설계가 여기에 묶인다

1. **빔 방향은 고정할 수 없다.** 빔포밍은 칩이 가장 큰 소리로 자동 조준한다.
   우리가 쓰는 것은 "들은 뒤에 방향을 보는" 소프트웨어 관문뿐이다.
2. **거리를 모른다.** DOA 는 나침반이지 줄자가 아니다. 그래서 소리만으로
   목표점을 만들지 않는다 — **카메라가 확인한다.**
3. **각도가 정밀하지 않다.** 실측 퍼짐 ±4°(조용할 때) ~ ±16°(소리가 섞일 때).
   사람 한 명을 향해 고개를 돌리기엔 충분하고, 목표점을 찍기엔 부족하다.

한계 2·3 이 §4 의 "돌아서 카메라로 본다" 를 강제한다. 소리만 듣고 주행하지
않는다.

## 3. 새 인터페이스 — 토픽 하나

```text
/vica/wake_doa    std_msgs/Float32    호출 순간의 DOA (0~359°, 마이크 좌표계)
```

웨이크워드 감지 시 1회 발행한다. DOA 를 못 읽으면 **발행하지 않는다**(무음 실패).

### `/vica/wake` 를 확장하지 않는 이유

`/vica/wake` 에는 이미 안내 중 각성·복귀 브레이크·옛 질문 접기가 걸려 있다.
동작 중인 대화 경로의 payload 를 바꾸는 것보다 토픽을 하나 더 내는 쪽이 싸다.
두 토픽의 도착 순서는 문제가 되지 않는다 — IDLE 에서 `/vica/wake` 는 아무 일도
하지 않고, 새 흐름은 `/vica/wake_doa` 하나로만 열린다.

`std_msgs/Float32` 를 쓰는 이유는 인터페이스 재빌드를 피하기 위해서다. 시각은
Mission 이 수신 시각으로 대신한다 — 호출은 살아 있는 사건이다.

## 4. 상태기계 — `SEEKING` 하나를 더한다

```text
IDLE ── /vica/wake_doa ──▶ SEEKING
                            │  SpinInPlace(θ)  ← 소리 쪽으로 고개 돌리기
                            ▼ 회전 완료(SUCCEEDED)
                          IDLE + 탐색 창(SEEK_LOOK_SEC) + 복귀각(−θ) 보유
                            ├─ 창 안에 접근 요청 도착 ──▶ APPROACHING (기존 경로)
                            │                              복귀각은 버린다
                            └─ 창 만료 ──▶ SEEKING(복귀) ──▶ IDLE
                                            SpinInPlace(−θ)
```

### 왜 회전이 끝나면 IDLE 로 돌아가나

접근 요청 관문(`check_approach_gate`)은 `state != State.IDLE` 을 전부 거절한다.
탐색 창 동안 IDLE 을 유지하면 **그 관문을 한 줄도 건드리지 않고** 기존 경로에
합류한다. 안전 판정이 걸린 관문은 열지 않는 편이 낫다.

대신 IDLE 이 `_seek_return_yaw` 와 `_seek_deadline` 을 들고 있게 된다. 이 둘은
접근이 성사되거나 창이 만료되면 즉시 청산된다.

### 상수

| 이름 | 값 | 근거 |
| --- | --- | --- |
| `SEEK_LOOK_SEC` | **6.0** `[TARGET]` | 회전 후 YOLO 가 사람을 "안정"으로 인정하기까지 필요한 시간. `detection_gate` 는 5 Hz 로 stable 1.0 s + still window 3.0 s 를 본다. 실측으로 확정한다 |
| `SEEK_TURN_TIMEOUT_SEC` | 15.0 | 기존 `APPROACH_TURN_TIMEOUT_SEC` 과 같은 값. 회전이 시작조차 안 되면 상태에 갇힌다 |

### 진입 조건

`State.IDLE` · E-stop 아님 · `nav_ready`. 셋 중 하나라도 아니면 무시한다.

### `SEEKING` 은 goal 이 살아 있는 상태다

`_GOAL_ACTIVE_STATES` 에 넣는다. E-stop·긴급어가 회전을 취소해야 하기 때문이다.

### 회전 중 YOLO 는 멈춘다

`is_moving` 을 `state in (NAVIGATING, SEEKING)` 으로 넓힌다. 회전 중 영상은
화면이 통째로 흐르므로 `max_displacement 0.3 m` 관문이 어차피 트랙을 계속
깨뜨린다 — 쓰이지 않을 추론에 CPU 를 쓰지 않는다. 이 로봇의 제1 병목은 CPU 다.

`RobotState.msg` 의 `is_moving` 소비자는 `vica_perception/inference_gate.py`
**하나뿐임을 전수 확인했다.** `APPROACHING` 을 넣지 않는 것은 의도된 현행 유지다
— 접근 중에는 목표점 갱신(`APPROACH_GOAL_UPDATE_M=0.5`)에 탐지가 필요하다.

## 5. 각도 변환 — 부호가 미측정이다 `[미검증]`

```text
yaw_rad = wrap_to_pi( s × radians(θ_doa) )      s ∈ {+1, −1}
```

`SpinInPlace` 는 **양수 = 반시계**다(`mission_logic.py:213`).

`s` 는 마이크의 각도 증가 방향이 반시계인지 시계인지에 달렸고, **이 장비에서 잰
기록이 없다.** 틀리면 로봇이 정확히 반대로 돈다. 그래서 **코드보다 먼저 잰다.**

### 선행 측정 (구현 전, 10분)

1. 로봇을 정지시키고 `tools/doa_probe.py` 계열로 DOA 를 읽는다.
2. 로봇 **정면**에 서서 "비카야" — 0° 부근이 나오는지 확인(기준선 재확인).
3. 로봇 **왼쪽 90°**에 서서 "비카야".
   - 약 90° → `s = +1` (반시계 증가)
   - 약 270° → `s = −1` (시계 증가)
4. 로봇 **오른쪽 90°**에서 한 번 더 불러 3의 결론과 어긋나지 않는지 본다.
5. 결과를 이 문서와 `.env` 주석에 실측일자와 함께 남긴다.

측정 전에는 구현을 시작하지 않는다.

## 6. 건드리지 않는 것

- **안전 경로.** 회전은 Nav2 `SpinInPlace`(behavior server) → `/cmd_vel_req` →
  Safety → `/cmd_vel_safe`. 직접 발행은 없다.
- **`/vica/wake` 의 기존 동작.** 안내 중 각성·복귀 브레이크·옛 질문 접기 전부
  현행 유지. 새 흐름은 **IDLE 에서만** 열린다. 안내 중 "비카야"는 지금처럼
  기존 사용자의 명령이다.
- **접근 관문 `check_approach_gate`.** §4 의 이유로 한 줄도 안 바꾼다.
- **접근 후반부 전체.** 질문·판정·180° 회전·온보딩 모두 그대로 쓴다.
- **멘트.** 새 안내 멘트를 만들지 않는다. 호출하면 웨이크워드 노드가 이미
  "네?"라고 답하고, 그 소리가 "지금 움직입니다" 예고를 겸한다.
- **DSP 쓰기 동결(D7).** DOA 는 읽기 전용이므로 저촉되지 않는다.

## 7. 실패와 경계

| 상황 | 처리 | 근거 |
| --- | --- | --- |
| 돌았는데 사람이 없다 | **조용히** 복귀각으로 되돌아 IDLE | 2026-09-10 사용자 결정. 복도 소음 오인에 로봇이 말을 걸면 주변을 놀래킨다 |
| 되돌리는 이유 | 안 되돌리면 오작동 한 번에 카메라가 벽만 보는 자세로 굳는다 | |
| DOA 를 못 읽음 | 발행 안 함 = 아무 일도 없음 | 무음 실패 |
| 회전 중 다시 "비카야" | 무시 | 현재 회전을 끝내고 판단한다. 단순함이 이긴다 |
| **탐색 창** 중 다시 "비카야" | 새 탐색으로 갱신. 복귀각은 **누적한다** | 두 번 부르면 두 번 돈다. 덮어쓰면 첫 회전분이 사라져 원래 자세로 못 돌아온다 (2026-09-10 계획 작성 중 정정) |
| **탐색 창** 중 다른 일이 시작됨 (앱 목적지 요청·음성 목적지 등) | seek 상태를 즉시 청산하고 복귀 회전을 **하지 않는다** | 사용자가 로봇에게 할 일을 줬다. 그 앞에서 로봇이 제자리 돌기를 시작하면 안 된다 |
| 회전이 시작 안 됨 | `SEEK_TURN_TIMEOUT_SEC` 후 IDLE | 기존 TURNING 의 시계 탈출과 같은 방식 |
| 회전 중 E-stop | goal 취소 → 기존 E-stop 경로 | `_GOAL_ACTIVE_STATES` |
| 거절한 사람이 다시 잡힘 | 기존 `REAPPROACH_SUPPRESS_SEC=60` 이 막는다 | 현행 |
| 사람이 이미 핸들 쪽(뒤)에 서 있음 | **로봇이 두 번 돈다** (확인하러 한 번, 핸들 내주러 한 번) | 감수한다. "반드시 카메라로 확인한다"의 비용이다 |

## 9. 시험

**단위 (자동)**

- 각도 변환: 0°/90°/180°/270° 가 `s` 양쪽 부호에서 `wrap_to_pi` 범위에 드는지.
- `SEEKING` 전이: IDLE 에서만 진입 · E-stop 이면 거절 · 회전 완료 후 IDLE +
  창 보유 · 창 만료 시 `SpinInPlace(−θ)` 정확히 1회.
- 창 안에 접근 요청이 오면 복귀 회전이 **발행되지 않는지**.
- 창 안에 목적지 요청이 오면 seek 상태가 청산되고 복귀 회전이 없는지.
- 창 안에 재호출이 오면 복귀각이 **두 회전분으로 누적**되는지.
- E-stop 이 `SEEKING` 의 spin 을 취소하는지.
- `is_moving` 이 SEEKING 에서 true 인지.

**실기 (사용자 판정)**

1. 대기 중인 로봇의 **왼쪽·오른쪽·뒤** 각각에서 "비카야" → 그쪽으로 도는가.
   (부호가 틀리면 여기서 즉시 드러난다)
2. 돌고 나서 접근·질문·수락·180° 회전·온보딩까지 **끊김 없이** 이어지는가.
3. 아무도 없는데 복도 소음으로 돌았을 때 **조용히** 제자리로 오는가.
4. 안내 중 "비카야"가 **종전대로** 동작하는가(회귀 확인).

시험 전 `git log feat/…..dev` 로 기능 브랜치가 dev 에 뒤처지지 않았는지 본다.
