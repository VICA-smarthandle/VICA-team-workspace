## 2. A22 IIC 통신규격 — PDF 전사

### 2.1 모델

출력 방식은 **출고 시 고정**이며 나중에 바꿀 수 없다. 선 4가닥은 모든 모델이 같아
**겉모습으로 구분되지 않는다.**

| # | 모델 | 출력 |
| --- | --- | --- |
| 1 | DYP-A22YYUW-V1.0 | UART auto |
| 2 | DYP-A22YYTW-V1.0 | UART controlled |
| 3 | DYP-A22YYMW-V1.0 | PWM |
| 4 | DYP-A22YYGDW-V1.0 | Switch |
| **5** | **DYP-A22YYCW-V1.0** | **IIC ← 우리 것** |
| 6 | DYP-A22YY4W-V1.0 | RS485 |

> 데이터시트 각주: "Lead wire, pin function and output mode of product model correspond
> one-to-one, and **cannot coexist with other output modes**."

### 2.2 전기 사양

| 항목 | 값 |
| --- | --- |
| 동작 전압 | 3.3 / **5(typ)** / 12 V DC |
| **피크 전류** | **≤150 mA (센서 1개당)** |
| 평균 동작 전류 (IIC) | ≤10 mA |
| 입력 리플 | ≤50 mV p-p |
| 입력 노이즈 | ≤100 mV p-p |
| ESD | ±4 kV / ±8 kV (IEC61000-4-2) |

센서 2개 = **피크 300 mA**. `devlog/2026-07-28-smart-handle-guidance-plan.md` 에
"별도 5V 전원(서보 + NeoPixel 60개) 준비 완료"가 기록돼 있으므로 **거기서 급전한다.**
나노의 5V 핀(USB 경유 500 mA 공유)에서 따면 서보·LED 와 경합한다.

### 2.3 성능

| 항목 | 값 | 비고 |

| 사각지대 | ≤2 cm | |
| 측정 범위 | 2~300 cm | 평면 물체 기준 |

| 온도 보상 | 내장 | |

> **[미확인 · 젯슨에서 볼 것]** 케이블이 **32 cm 뿐**이다. 스마트핸들 나노가 손잡이

> 센서는 앞범퍼(+0.305 m)에 있으므로 직선거리만 **약 72 cm** 다(배선 경로는 더 길다).
> 연장이 필요하면 I2C 신호 품질이 걸린다 — §5.2.

### 2.5 배선

| PIN | 색 | 데이터시트 표기 | **IIC 모델에서** | 나노 |
| --- | --- | --- | --- | --- |
| 1 | 빨강 | VCC | 전원 | 별도 5V |
| 2 | 검정 | GND | 접지 | GND (공통) |
| 3 | 노랑 | RX / B | **SCK (클럭)** | **A5** |
| 4 | 흰색 | TX / A | **SDA (데이터)** | **A4** |

- **외부 풀업 필수**: SDA·SCK 각각 VCC 로. 데이터시트 권장 **3 k~10 k**
- 통신 레벨 = VCC. 나노가 5 V 이므로 센서도 5 V 로 급전하면 **레벨시프터 불필요**
- 나노에서 A4/A5 는 현재 미사용 (`smart_handle_firmware.ino`: SERVO 7, LED_A 8, LED_B 9) — **핀 충돌 없음**

### 2.6 I2C 파라미터

| 항목 | 값 |
| --- | --- |
| 역할 | 슬레이브. 다중 병렬 연결 지원 |
| 통신 속도 | **10 ~ 100 kbit/s** |
| 브로드캐스트 주소 | `0x00` |
| 기본 주소 | `0xE8` (8비트 표기) = **`0x74` (7비트, 코드에서 쓰는 값)** |
| 변경 가능 주소 20종 | `0xD0 D2 D4 D6 D8 DA DC DE E0 E2 E4 E6 E8 EA EC EE F8 FA FC FE` |

> 이 문서 계열은 주소를 **8비트 표기**로 쓴다. 리눅스·Arduino `Wire` 는 **7비트**를
> 받으므로 항상 `>> 1` 한다. `0xE8 → 0x74`, `0xD0 → 0x68`.

### 2.7 레지스터

데이터는 **상위 바이트 먼저**(big-endian).

| 주소 | 권한 | 기능 | 형 | 설명 |
| --- | --- | --- | --- | --- |
| `0x00~0x01` | R | 펌웨어 버전 | uint16 | |
| `0x02~0x03` | R | **거리값** | uint16 | mm 또는 µs (트리거 명령이 결정) |
| `0x05` | R/W | 슬레이브 주소 | uint8 | 8비트 표기로 씀 |
| `0x06` | R/W | 전원 노이즈 저감 레벨 | uint8 | 기본 **1** |
| `0x07` | R/W | **지향각 레벨** | uint8 | 기본 **4** |
| `0x09` | R | Hold | | |
| `0x0A~0x0B` | R | 온도 | int16 | 단위 0.1 ℃, 분해능 0.5 ℃. 측정 트리거 후 읽을 것 |
| `0x10` | W | 명령 제어 | uint8 | §2.8 |

**노이즈 저감 레벨 (`0x06`)** — 높일수록 잡음에 강하지만 약한 반사체를 놓친다.

| 값 | 용도 |
| --- | --- |
| 1 | 배터리 전원 (기본) |
| 2 | USB 전원 (고주파 잡음 있음) |
| 3 | 장거리 USB 전원 |
| 4 | 스위칭 전원 |
| 5 | 스위칭 + 복잡한 환경간섭. **일반 권장 안 함** |

**지향각 레벨 (`0x07`)**

| 값 | 공칭 각도 | rad (`field_of_view`) |
| --- | --- | --- |
| 1 | 약 30° | 0.524 |
| 2 | 약 40° | 0.698 |
| 3 | 약 50° | 0.873 |
| 4 | 약 60° (기본) | 1.047 |

### 2.8 측정 명령 (`0x10` 에 1바이트 쓰기)

| 명령 | 최대거리 | 반환 단위 | 측정 소요 |
| --- | --- | --- | --- |
| `0xBD` | 50 cm | mm | 15~80 ms |
| `0xBC` | 150 cm | mm | 20~90 ms |
| `0xB8` | 250 cm ※ | mm | 25~100 ms |
| `0xB4` | 350 cm | mm | 35~110 ms |
| `0x05` | 50 cm | µs | 15~80 ms |
| `0x0A` | 150 cm | µs | 약 115 ms |
| `0x0F` | 250 cm | µs | 20~90 ms |
| `0xB2` | 350 cm | µs | 35~110 ms |
| `0xB0`, `0xB9` | — | Hold ※ | |
| `0x5A` → `0xA5` | — | 센서 재시작 | 즉시 |

µs 단위를 **5.75 로 나누면 mm** 가 된다(음속 348 m/s 기준).

### 2.9 측정 절차

```
① write   [7bit 0x74] → reg 0x10 → TRIG            측정 시작
② 대기    명령별 최대 측정시간 (예: 0xBC 면 90ms)   ← 지키지 않으면 0xFFFF
③ write   [7bit 0x74] → reg 0x02
   read    2바이트 (High, Low)
   거리 = High*256 + Low  [mm]
```

| 반환값 | 의미 | 처리 |
| --- | --- | --- |
| `0xFFFF` | 측정 미완료 (너무 일찍 읽음) | 폐기 |
| `0xFFFE` | 동주파수 간섭 감지 | **폐기. 거리로 쓰면 안 된다** |

**통신 예제** (Output-Interfaces 17p)

```
버전 읽기   : write 0x00        → read 2B → 0x0001
거리 읽기   : write 0x10, 0xB0  → 50ms 대기 → write 0x02 → read 2B → 0x04E9 = 1257 mm
주소 변경   : (0xE8 에) write 0x05, 0xD0
지향각 변경 : write 0x07, 0x04
```

### 2.10 데이터시트 자체 오류 3건 — 실기 확인 필요

| # | 위치 | 문제 |
| --- | --- | --- |
| 1 | 명령표 `0xB8` | "range level 3(about **150** cm)" 이라 적혀 있으나 대응하는 µs 명령 `0x0F` 는 250 cm 다. **250 cm 오타로 판단** |
| 2 | `0xB0` | 명령표에서는 "Hold" 인데 **바로 다음 장 Example 2 에서는 0.5 m 측정 트리거로 사용**한다. 문서끼리 모순 |
| 3 | `0x05` 설명 | 주소 목록에 `0xFEE` 가 있다. 8비트에 존재할 수 없는 값 |

→ **트리거 명령은 실기에서 확정한다.** `0xBC`(150 cm) 를 1순위로 시험하고, `0xFFFF` 가
계속 나오면 `0xB4`·`0xB8` 로 바꿔 본다.

**[2026-08-31 실기 확정 — 젯슨, 실물 센서 2개]** `usonic_addr_setup` 순환 시험 결과:

| 명령 | 결과 |
| --- | --- |
| `0xBC`·`0xB8`·`0xB4` | 실거리 반환 (0x74: ~1.10 m 안정, 0x68: 0.70/1.06 m 두 에코 오감) |
| `0xB0` | **실거리 반환 — Hold 가 아니라 트리거로 동작.** 모순 #2 실기 해소 |
| `0xBD` | `0xFFFD` — **데이터시트에 없는 값. "범위 내 에코 없음" 마커로 확정**(같은 날 2차 시험: 50 cm 안 물체 213·440 mm 는 실거리, 밖 597 mm 는 `0xFFFD`) |

**채택: `0xBC`(150 cm·대기 100 ms).** `0xFFFD` 는 실패가 아니라 clear 로 처리한다(§6.2).
부수 발견: 두 센서 주소가 **이미 0x68/0x74 로 구워져 있었다**(앞선 조사자 작업 추정) —
주소 굽기 단계 생략, 물리 좌우 대응만 확인하면 된다.

### 2.11 실측 빔 패턴은 공칭보다 넓다

데이터시트 7~8 p 의 유효 감지 범위 그래프(Ø7.5 cm PVC 파이프 기준)를 읽으면, X = 1000 mm
지점의 Y 폭이 공칭 각도보다 크다.

| 레벨 | 공칭 반각 | 그래프 실측 반각 |
| --- | --- | --- |
| 1 | 15° | 약 **16.7°** |
| 3 | 25° | 약 **27°** |
| 4 | 30° | 약 **34.6°** |

→ **바닥 오검출 거리 계산은 공칭보다 약 10 % 가까워진다.** §5.1 의 틸트 각을 정할 때
공칭값만 믿지 말고 여유를 둘 것.

### 3.1 이 배치에서 나오는 수치

**바닥 오검출 시작 거리** (센서 91.3 mm, 수평 장착, 공칭 각도)

| 지향각 레벨 | 바닥 에코 시작 |
| --- | --- |
| 4 (출고 기본) | **0.16 m** |
| 3 | 0.20 m |
| 2 | 0.25 m |
| 1 | 0.34 m |

> **출고 기본값(레벨 4) 그대로 전원을 넣으면 16 cm 앞부터 바닥이 장애물로 찍힌다.**
> `local_costmap` 은 rolling window 6×6 m 라 로봇이 전진하는 내내 유령이 창에 쌓인다.
> **지향각을 좁히거나 브래킷을 기울이는 것은 선택이 아니라 필수다.**

**좌우 커버리지** (센서 간 214 mm)

| 레벨 | 정중앙 빈틈이 메워지는 거리 | 범퍼 끝(±227.5 mm) 도달 |
| --- | --- | --- |
| 1 (30°) | 0.399 m | 0.450 m |
| 2 (40°) | 0.294 m | 0.331 m |
| 3 (50°) | 0.229 m | 0.258 m |
| 4 (60°) | 0.185 m | 0.209 m |

→ 센서 2개가 안쪽(±10.7 cm)에 몰려 있어 **좁힐수록 코앞 정중앙이 빈다.** 최종 8개
구성에서 좌우 센서가 메워줄 몫이며, 지금 2개로는 이 대가를 안고 간다.

**빔 겹침** — 두 센서의 빔은 위 표의 "정중앙" 거리부터 겹친다. 레벨 3 이면 **0.229 m**
부터다. 실사용 구간(0.2~1.0 m)이 통째로 겹침 구간이다 → §4.2 순차 발사.

## 4. 건네받은 `ultrasonic-ros2-handoff.md` 검증 결과

앞선 조사자의 문서다. **완성도가 높고 대부분 그대로 쓸 수 있다.** 다만 그 문서가 쓰인
시점에는 **장착 배치와 통합 방식이 미정**이었고, 그 사이에 둘 다 확정됐다. 그 결과 전제가
깨진 항목이 있다.

### 4.1 그대로 채택

| 항목 | 왜 맞는가 |
| --- | --- |
| `sensor_msgs/Range` 로 발행 | Nav2 `RangeSensorLayer` 가 받는 타입과 정확히 일치 |
| **타임스탬프 보정** (`measurement_delay`) | MCU 에 시계가 없다. 수신 시각을 그대로 쓰면 costmap 이 낡은 값을 새것으로 착각한다 |
| 워치독 시 **발행 중단** | `range=0` 이나 마지막 값 재발행 금지. costmap 이 스스로 만료시키게 둔다. **이 문서에서 가장 잘 판단한 부분** |
| 무효 채널만 개별 중단 | 한 센서 고장이 다른 채널을 죽이지 않는다 |
| MCU 가 `0xFFFE`/`0xFFFF` 폐기 + 3점 중앙값 | 역할 분담이 명확하다. 노드에서 중복하지 말 것 |
| 8→7비트 주소 변환 | `0xD0→0x68`, `0xE8→0x74` 맞다 |
| 주소를 하나만 굽는 절차 | S2 를 공장 기본값으로 두는 판단이 합리적 |
| 나노 자동리셋 2초 유예 | 실무적으로 옳다 |
| 채널 수·갱신율 하드코딩 금지 | 8개 확장 대비 |

### 4.2 고쳐야 할 것

#### (1) 동시 발사 → **순차 발사**

원문 §4:

```cpp
for(uint8_t i=0;i<2;i++) wr8(ADDR[i], 0x10, TRIG);   // 동시 발사
```

> 원문 §4: "두 센서를 **동시에 발사**하므로 … (**간섭이 없다는 전제**)"
> 원문 §8: "동주파수 간섭 0회 — **단, 빔이 겹치지 않는 배치였으므로 간섭 검증은 아님**"

**그 전제가 확정된 배치에서 깨진다.** §3.1 대로 간격 214 mm·레벨 3 이면 0.229 m 부터
빔이 겹치고, 실사용 구간 전체가 겹침이다. 동시에 쏘면 서로의 메아리를 자기 것으로 읽는다.
이때 나오는 것은 오류 코드가 아니라 **그럴듯해 보이는 틀린 거리**이며 `0xFFFE` 도 뜨지
않는다.

| | 동시 (원문) | 순차 |
| --- | --- | --- |
| 사이클 | 115 ms (8.7 Hz) | **225 ms (4.4 Hz)** |
| 0.5 m/s 에서 사이클당 이동 | 5.8 cm | 11.2 cm |
| 간섭 | 발생 | 없음 |

`local_costmap` 의 `update_frequency` 가 5.0 Hz 이므로 4.4 Hz 는 무리 없다.

#### (2) `measurement_delay_ms` 를 채널별 배열로

순차 발사에서는 두 채널의 측정 시각이 다르다. 패킷 수신 시점 기준 **S1 은 225 ms 전,
S2 는 110 ms 전**이다. 원문의 단일값 `115` 를 쓰면 S1 이 115 ms 어긋나고, 0.5 m/s 에서
**5.8 cm 위치 오차**가 된다.

```yaml
measurement_delay_ms: [225, 110]    # 원문: 115 (단일)
```

#### (3) 지향각·`max_range` 가 실제 높이와 안 맞는다

원문 §3 은 `0x07 = 0x03`(50°), §6 은 `max_range: 1.50` 이다. 그런데 §3.1 대로 높이
91.3 mm 에 **수평**으로 달면 바닥 에코가 **0.196 m** 에서 시작한다. `max_range` 1.5 m
중 1.3 m 가 통째로 허위 장애물이 된다.

원문 §9 의 정지 임계값 표와 대조하면 더 분명하다 — 실제 `max_vel_x` 가 0.5 이므로
그 표의 **0.5 m/s 행이 우리 값**이고, 필요 임계값은 **0.32 m** 다.

| | |
| --- | --- |
| 필요 임계값 | 0.32 m |
| 레벨 3 수평의 유효거리 | **0.196 m** ❌ |

→ **틸트가 사실상 필수다.** §5.1.

#### (4) `Wire.setClock(100000)` → 50 kHz 권장

데이터시트 상한이 정확히 100 kbit/s 이고, 원문 §8 의 무오류 200회는 **10 kHz 에서만**
검증됐다. 케이블 연장(§2.4)이 들어가면 100 kHz 는 위험하다. 50 kHz 로 시작해 올린다.

### 4.3 폐기 — 통합 방식이 바뀌었다

**사용자 결정(2026-08-31): 초음파를 기존 스마트핸들 나노에 올린다.** 별도 보드를 두지
않는다. 따라서 아래 항목은 무효다.

| 원문 항목 | 왜 폐기 | 대체 |
| --- | --- | --- |
| `/dev/ttyUSB0` 하드코딩 | 스마트핸들이 이미 `/dev/vica_smart_handle` 로 고정돼 있다 | 기존 심볼릭 링크 재사용 |
| CH340 전제 | 스마트핸들 나노는 **FTDI FT232R, serial `B003UMKG`** | `99-vica-smart-handle.rules` 그대로 |
| 새 udev 규칙 | 불필요 | — |
| §4 펌웨어의 `delay(MEAS_MS)` | **치명적** — §5.3 | 논블로킹 상태머신 |

## 5. 미결 — 젯슨에서 결정할 것

### 5.1 [결정 완료 2026-08-31] 틸트 불가 — 차선책 경로가 기준이다

**사용자 확정: 브래킷 틸트는 불가능하다.** 아래 차선책으로 간다:

- 지향각 **레벨 1(30°)** + `max_range` **0.30 m** (레지스터 쓰기만, 기구 변경 없음)
- 유효거리 0.30 m < 필요 임계값 0.32 m → **`max_vel_x` 0.5 → 0.45 인하가 필요하다.
  이 항목은 아직 미결(사용자 판정)**
- 정중앙 ±2.7 cm 사각지대를 안고 간다
- ⚠️ 여유가 거의 없다: §2.11 실측 빔(레벨 1 반각 약 16.7°) 기준 바닥 에코가
  **0.304 m** 에서 시작해 `max_range` 0.30 과 4 mm 차이다. 실기에서 두 가지를 꼭
  실측한다 — ① **현재 장착 각도가 정말 0°인지**(우연히 위로 들려 있으면 유리)
  ② 바닥 에코가 실제로 시작되는 거리

원래 조사 내용은 아래에 보존한다.

**센서는 이미 물리적으로 부착돼 있다**(2026-08-31 사용자 확인). 따라서 순서는
"기울일 수 있는가"가 아니라 **"지금 몇 도인가를 먼저 재고, 필요하면 조정 가능한지
판단"** 이다.

- 각도기나 스마트폰 수평계를 센서 상면에 대고 **지면 기준 앙각**을 잰다
- **0°(수평)로 나오면 아래 계산대로 바닥 오검출이 확실하다.** 조정이 불가능하면 차선책
- 이미 위로 기울어 있으면 그 각도를 그대로 쓰고 `max_range` 만 맞춘다

높이 91.3 mm 는 고정됐으므로 남은 손잡이는 **틸트**뿐이다.

**계산 근거**: 부채꼴 아래 경계가 지면과 이루는 각이 약 5° 가 되면 바닥 에코가 1 m 밖으로
밀린다. 필요한 틸트 = (지향각 반각) − 5°.

| 지향각 | 공칭 기준 틸트 | **실측 빔 기준(§2.11)** | 바닥 에코 |
| --- | --- | --- | --- |
| 레벨 3 (50°) | 위로 20° | 위로 **22°** | 약 1.0 m |
| 레벨 1 (30°) | 위로 10° | 위로 **12°** | 약 1.0 m |

**권장: 레벨 3 유지 + 위로 20~25°.** 넓은 각이 좌우 커버리지에 유리하고(정중앙 빈틈이
0.229 m vs 레벨1 의 0.399 m), 원문이 정한 `field_of_view: 0.873` 을 고칠 필요도 없다.
`max_range` 만 1.50 → **1.00** 으로 줄인다.

**틸트가 불가능하면** — 차선책은 지향각을 레벨 1(30°)로 좁히고 `max_range` 를 0.30 m 로
자르는 것이다(레지스터 쓰기만, 기구 변경 없음). 대가:

- 유효거리 0.30 m < 필요 임계값 0.32 m → **`max_vel_x` 를 0.5 → 0.45 로 낮춰야 성립**
- 정중앙에 ±2.7 cm 사각지대가 남는다

주행 성능 변경이므로 **사용자 판정 사항**이다.

### 5.2 [확인] 케이블이 나노까지 닿는가

센서 케이블은 **320 mm** 다(§2.4). 앞범퍼(+0.305 m)에서 스마트핸들 나노까지의 실제
거리를 재고, 연장이 필요하면:

- I2C 는 원래 기판 위 몇 cm 용이다. 총 배선이 1 m 를 넘으면 50 kHz 에서도 불안정할 수 있다
- 풀업을 4.7 kΩ → 2.2 kΩ 로 낮추면 상승시간이 개선된다(전류는 늘어난다)
- 꼬임쌍선 사용, SDA/SCK 를 GND 와 함께 묶을 것

### 5.3 [설계] 기존 펌웨어에 논블로킹으로 얹기

`smart_handle_firmware.ino` 는 `delay()` 없이 `millis()` 로만 도는 구조다. 원문 §4 의
`delay(110)` 을 그대로 넣으면:

| 기능 | 주기 | 110 ms 정지 시 |
| --- | --- | --- |
| 서보 스텝 (`SERVO_STEP_MS`) | 14 ms | **8스텝 건너뜀 → 끊김** |
| LED 웨이브 (`WAVE_MS`) | 30 ms | 애니메이션 깨짐 |
| 젯슨 상태코드 수신 | 100 ms | 버퍼링되나 반응 지연 |

또한 **NeoPixel `show()` 는 인터럽트를 끈다** — LED 60개(`NUM_LEDS_A/B` 각 30)면 약
1.8 ms. 그 사이에 I2C 트랜잭션이 걸치면 통신이 깨진다.

→ 상태머신으로 쪼개고, **LED 갱신은 측정 대기 구간 안에서만** 하도록 순서를 강제한다.

```
IDLE → TRIG_S1 → WAIT(110ms) → READ_S1 → TRIG_S2 → WAIT(110ms) → READ_S2 → SEND → IDLE
                  └ 이 구간에서만 LED show()          └ 동일
```

> **⚠️ 이 펌웨어는 이미 한 번 사고가 났다.** `handoff_laptop_firmware_and_apk.md` A-2:
> "했다가 LED 는 맞았지만 **서보가 함께 뒤집혔다** — 아두이노는 상태코드 하나로 LED 와
> 서보를 같이 움직인다." **기존 서보·LED 로직은 한 줄도 건드리지 않고 곁가지로만 붙인다.**
>
> **[2026-08-31 확인]** 그 인수인계의 A-3(LED 두 줄 맞바꾸기)은 **이미 적용 완료**다
> (`vica_ros2_ws` 커밋 6dbf779). 지금 `.ino` 의 `case STATE_LEFT/RIGHT` 가 정본이며,
> `servoMoveTo` 줄의 "건드리지 말 것" 주석도 코드에 박혀 있다.

## 6. 제안 설계 — **미승인**

사용자 승인 전이다. 승인되면 `docs/superpowers/specs/` 에 정본을 쓴다.

### 6.1 구조

```
[A22 ×2] ──I2C(A4/A5, 풀업)──> [기존 스마트핸들 나노]
                                LED 60 · 서보 · 초음파 2
                                        │ USB
                                /dev/vica_smart_handle      ← 기존 udev 재사용
                                        │
                              user_guidance_driver_node
                                ├ 하향  상태코드 1B @10Hz   (기존, 무변경)
                                └ 상향  8B 프레임 @약 5Hz   (신규)
                                        ↓
                    /ultrasonic/front_left   /ultrasonic/front_right
                                sensor_msgs/Range
                                        ↓
                        local_costmap · range_sensor_layer
```

**토픽·frame 명명 (2026-08-31 사용자 확정)** — "어느 면 + 그 면에서의 위치".
TF frame 이름에는 `/` 를 쓸 수 없으므로 밑줄로 통일한다: 토픽
`/ultrasonic/front_left` ↔ frame/URDF 링크 `usonic_front_left` 가 같은 단어를 쓴다.
8개 확장 시: `front_left`·`front_right` / `left_front`·`left_rear` /
`right_front`·`right_rear` / `rear_left`·`rear_right`.
채널 매핑(**2026-08-31 실측 확정**): **ch0 = front_left = 0x68, ch1 = front_right =
0x74(공장 기본)**. 물체 판별 시험으로 물리 대응 확인(마주 보고 왼쪽=로봇 오른쪽 센서가
0x74 에 응답). 센서에 라벨 FL(0x68)/FR(0x74) 부착 권장.

### 6.2 시리얼 프로토콜

지금 `SmartHandleState.msg` 에 이렇게 적혀 있다:

> **[중요] 아두이노 → 젯슨 상향 통신이 없다.**

이 작업이 그 문장을 바꾼다.

| 방향 | 형식 | 변경 |
| --- | --- | --- |
| 젯슨 → 나노 | 1바이트 상태코드 (0~7) @10 Hz | **없음** |
| 나노 → 젯슨 | `AA 55 seq d0L d0H d1L d1H xor` @약 5 Hz | 신규 |

헤더 `0xAA`·`0x55` 는 하향 코드 범위(0~7)와 겹치지 않아 양방향이 섞여도 안전하다.

거리값 규약(2026-08-31 확장): `1`~`3000` = 유효 mm, `0` = 무효(3회 연속 실패 → 그 채널
미발행), **`3001` = 범위 내 에코 없음(clear)** — 노드는 `max_range` 로 발행해 부채꼴을
지운다. clear 를 무효로 치면 앞이 뚫려 있을 때마다 발행이 끊겨 costmap 의 유령을 지울
수 없다(센서 원시값 `0xFFFD` 의 번역, §2.10 실기).

## 9. 부록 — 주소 굽기 스케치 (§7.1-3 용)

> **[2026-08-31] 실행 파일로 옮겼다** — 정본은
> `vica_ros2_ws/src/vica_user_guidance/firmware/usonic_addr_setup/usonic_addr_setup.ino`
> (`feat/ultrasonic-i2c` 브랜치, worktree `~/wt-usonic`). 지향각도 틸트 불가
> 확정(§5.1)에 따라 레벨 3(0x03)이 아니라 **레벨 1(0x01)** 로 바뀌었고, 스캔된
> 센서 전부의 거리를 1초마다 출력하는 점검 기능이 추가됐다. 아래 원문은 참고용이다.

원본 인수인계 `.md` 의 스케치를 §4.2 의 지적(클럭 50 kHz)을 반영해 고친 것이다.
**센서를 하나만 연결한 상태에서** 올린다. 둘 다 연결하면 공장 기본 주소가 충돌한다.

```cpp
#include <Wire.h>

// 8비트 표기 -> 7비트 변환: 0xE8>>1 = 0x74 (공장 기본), 0xD0>>1 = 0x68 (S1 새 주소)
#define ADDR7_DEFAULT  0x74
#define ADDR8_NEW      0xD0
#define ADDR7_NEW      (ADDR8_NEW >> 1)
#define ANGLE_LEVEL    0x03      // 3 = 약 50도. field_of_view 0.873 rad 과 반드시 일치시킬 것

void scan(const char* tag) {
  Serial.print(tag); Serial.print(F(" scan: "));
  for (uint8_t a = 1; a < 127; a++) {
    Wire.beginTransmission(a);
    if (Wire.endTransmission() == 0) { Serial.print(F("0x")); Serial.print(a, HEX); Serial.print(' '); }
  }
  Serial.println();
}

bool wr8(uint8_t addr7, uint8_t reg, uint8_t val) {
  Wire.beginTransmission(addr7);
  Wire.write(reg); Wire.write(val);
  return Wire.endTransmission() == 0;
}

void setup() {
  Serial.begin(115200);
  Wire.begin();
  Wire.setClock(50000);              // 데이터시트 상한 100k. 케이블이 길어 절반으로 시작한다
  Wire.setWireTimeout(25000, true);  // I2C 락업 자동 복구
  delay(1000);

  scan("before");                    // 0x74 가 보여야 한다

  // ── S1 만 연결했을 때: 주소를 0xD0(7bit 0x68)으로 바꾼다 ──
  Serial.print(F("addr write ok=")); Serial.println(wr8(ADDR7_DEFAULT, 0x05, ADDR8_NEW));
  delay(300);
  scan("after ");                    // 0x68 로 바뀌어야 한다

  // 지향각 설정 (두 센서 모두에 해줄 것. S2 는 ADDR7_DEFAULT 로 실행)
  Serial.print(F("angle ok="));      Serial.println(wr8(ADDR7_NEW, 0x07, ANGLE_LEVEL));
}

void loop() {}
```

**절차**

1. S1 만 연결 → 업로드 → `after scan` 에 `0x68` 확인
2. **전원을 껐다 켜고** 다시 실행 → `0x68` 유지 확인 (휘발성이면 여기서 드러난다)
3. **센서에 라벨을 붙인다** — 안 붙이면 나중에 구분할 방법이 없다
4. S1 을 빼고 S2 만 연결 → `before scan` 에 `0x74` 확인 → 주소 변경 줄은 주석 처리하고
   `wr8(ADDR7_DEFAULT, 0x07, ANGLE_LEVEL)` 만 실행
5. 둘 다 연결 → 스캔에 `0x68` 과 `0x74` 가 함께 뜨면 완료

> 지향각을 바꾸면 **ROS 쪽 `field_of_view_rad` 도 같이 바꾼다.** 둘이 어긋나면 costmap 이
> 실제와 다른 부채꼴을 그린다. 대응: 1→0.524, 2→0.698, 3→0.873, 4→1.047 rad.
