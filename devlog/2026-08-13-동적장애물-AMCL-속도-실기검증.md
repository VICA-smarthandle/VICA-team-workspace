### 속도 0.5 는 감속과 한 세트다

속도만 올리면 DWB 가 계획한 정지선을 실제로 넘는다.

```
0.5 m/s 에서
  DWB 예상 정지거리   0.25 / (2 x 2.5) = 5.0 cm    계획은 이걸 믿는다
  smoother 실제       0.25 / (2 x 1.0) = 12.5 cm   실제로는 이만큼 간다
  차이 7.5 cm  >  footprint_padding 5 cm           여유를 넘는다

DWB -1.5 / smoother -1.25 로 옮기면 차이 1.7 cm
```

대가는 승차감이다. `-1.0`은 2026-08-01 에 "시각장애인이 핸들을 잡고 걸으니
정지 충격이 곧 안전"이라는 이유로 정한 값이고, `-1.25`는 그 충격을 25 % 올린다.
되돌릴 때는 속도와 함께 되돌린다.

## 3. 실패한 것 — 전부 "정보를 줄인" 변경이다

### 3.1 `alpha1` 0.4 (되돌림)

사용자 판정: "주춤거림·머뭇거림이 눈에 띄게 늘었다. 위치오차 민감도가 올라가서
그런 것 같다." 주행 길이가 달라 발생률로 환산했다.

| | alpha1 0.2 (611 s) | alpha1 0.4 (209 s) | |
| --- | --- | --- | --- |
| No valid trajectories | 0.046/s | 0.287/s | 6.3배 |
| **lethal space** | 0.0016/s | **0.077/s** | **47배** |

입자를 넓게 퍼뜨리면 자세 추정이 덜 확신하게 되고, planner 가 "로봇이 이미
장애물 안에 있다"고 판단하는 일이 급증한다. **위치 오차를 줄이려던 값이 주행
품질을 깎았다.**

### 3.2 `tsdf_decay_factor` 10 s · 20 s (둘 다 되돌림)

먼저 근거가 된 실측이 있었다(run4, 129~157 s):

```
130.7 s  라이다 전방 최소 0.81 -> 1.21 m   사람이 비켜났다
132.0 s  전방 2.01 m                       완전히 트였다
157.0 s  전방 2.01 m, 명령 vx 0.000        26 초째 서 있다
```

라이다는 즉시 지웠는데 지도가 사람을 붙잡고 있었다. 계산상 소멸 30.6 s 와 맞는다.
그래서 9.6 s(0.85)로 내렸고 — 실패했다.

사용자 판정: "낮은 의자다리 같은 부분을 못 봐서 멈추고, 복구 시간도 크게 차이가
나지 않고 오히려 주행이 불안정하다." 20.1 s(0.925)에서도 같은 의자다리에서
같은 증상이 났다.

실측도 단조롭지 않았다.

| | 30.6 s | 9.6 s | 20.1 s |
| --- | --- | --- | --- |
| No valid trajectories | 210 | **61** | **382** |
| 제어주기 놓침 | 27 | **9** | **45** |

**decay 가 길수록 나빠지는 관계가 아니다.** 20 s 가 30.6 s 보다 나쁘다. 회차마다
사람이 막은 시점·위치가 달라 decay 효과가 그 차이에 묻혔다는 뜻이다.

**왜 복구가 안 빨라졌나**: 소멸을 앞당기면 사람만 지워지는 것이 아니다. 지형
정보도 같이 사라진다. 낮은 장애물(의자다리·책상다리)은 라이다 높이 아래라
nvblox 만 잡으므로 그대로 잃는다. 그 자리를 다시 볼 때까지 planner 가 흔들리고,
그 흔들림이 복구를 새로 부른다. **벌어들인 시간을 다른 곳에서 도로 잃는다.**

이 축은 닫는다. 시간으로 뭉뚱그려 지우는 방식의 한계가 여기까지다.

## 4. 복구 예산 — A/B 를 재고 20회 x 1 s 로 갔다

```
 6회 x 5 s = 15 s, 재계획  6번   Goal failed 회차당 2회
20회 x 2 s = 20 s, 재계획 20번   failed 0. 그러나 비켜난 뒤에도 대기를 다 채운다
10회 x 2 s = 10 s, 재계획 10번   A안
30회 x 1 s = 15 s, 재계획 30번   B안
20회 x 1 s = 10 s, 재계획 20번   확정 (실기 전)
```

A/B 실측(같은 코스):

| | A: 10회 x 2 s | B: 30회 x 1 s |
| --- | --- | --- |
| **No valid trajectories** | 160 | **7** |
| 제어주기 놓침 | 18 | **5** |
| 최장 정지 | 70.9 s | **34.7 s** |
| load average 최대 | 18.50 | **9.99** |
| lethal space | 1 | 53 |

**B 가 A 를 압도했다.** `lethal space` 가 늘어난 것은 분모 차이다 — A 는 10번
시도하고 포기했고 B 는 30번 시도했다. 결과 지표인 궤적 실패는 23배 줄었다.

갈린 것은 총 시간이 아니라 **다시 보는 빈도**다. Wait 가 도는 동안에는 상황을
보지 않으므로 `wait_duration` 이 곧 재출발 지연이고, **1 s 가 이 구조의
최소값**이다(Humble `WaitAction` 은 `InputPort<int>`).

그래서 wait 1 s 를 고정하고 재시도만 30 → 20 으로 줄였다. 30회는 통과 불가능한
자리에서 15 s 를 다 쓰는데 사람에게는 그것이 길다(사용자 판정).

**[미검증]** 총 10 s 는 계약 하한 15 s 에 못 미쳐
`test_recovery_patience_is_long_enough` 에 skip 을 걸어 두었다. 하한 근거는
6회 x 5 s 시절의 Goal failed 2회인데, 그때는 재계획이 6번뿐이라 같은 15 s 가
아니다. 지금은 20번이다. **실기가 이 skip 을 정리한다.**

## 6. Goal failed — 기전과 고칠 방향

### 6.1 확정된 기전 (run3 로그)

```
사람이 앞을 막음
   -> costmap 이 로봇을 감쌈
   -> DWB 궤적 419개 전멸
   -> 0.3 s 뒤 Controller patience exceeded   (failure_tolerance: 0.3)
   -> planner 도 "Starting point in lethal space"
   -> 복구 = ClearingActions -> Wait 순환, 예산 소진
   -> Goal failed
```

**timeout 이 아니라 예산 소진이다.** 그리고 예산을 20 s 로 늘리면 failed 는
0 이 되지만 그만큼 서 있는다. 예산 조절은 증상을 옮길 뿐이다.

### 6.2 진짜 병목은 그 뒤에 있다

B안의 두 정체 구간(34.7 s, 26.6 s)이 같은 모양이었다.

```
planner: Starting point in lethal space! Cannot create feasible plan
controller: Goal was canceled. Stopping the robot.
[follow_path] Client requested to cancel the goal    <- 외부에서 취소
```

**Mission Manager 가 planner 실패를 보고 goal 을 취소하고 다시 보내는
사이클이다.** BT 예산을 어떻게 잡아도 이 시간은 줄지 않는다.

### 6.3 고칠 방향 셋 (우선순위 순)

**① 무엇이 막았는지 구분한다 — YOLO (절차서 4단계)**

오늘 nvblox 실패가 이 필요를 증명했다. 시간으로 뭉뚱그려 지우니 사람과 의자다리가
같이 지워졌다. 사람만 골라 지우면 지형은 그대로 두고 대기만 줄일 수 있다.
`"막혔다"는 nvblox 가 알고 "사람이다"는 YOLO 만 안다.`
조사는 `devlog/2026-08-12-yolo-비전도입-검토와-동적장애물-정지.md` §3(도입 경로
A/B/C)·§4(bbox 되먹임)에 있다. 라이선스 판단이 A/B 를 가른다.

**② Mission Manager 의 취소·재전송 정책**

지금은 planner 가 실패하면 곧바로 취소한다. 얼마나 기다렸다 취소하는지, 취소
대신 대기할 수는 없는지가 정체 길이를 정한다. 취소 로그가
`vica_mission_manager: Nav2 goal 취소 (보조 경로 — 모터 정지 권위는 래치 체인)`
이므로 그 경로부터 읽는다.

**③ `failure_tolerance` 0.3 s**

controller 가 0.3 초 만에 손을 놓는다. 사람이 스쳐 지나가는 1~2 초를 못 버틴다.
올리면 복구 진입 자체가 줄어든다. 다만 **한 번에 하나씩**이므로 ①·② 뒤에 본다.
