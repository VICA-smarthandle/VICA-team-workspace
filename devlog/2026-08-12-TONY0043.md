## 요약

젯슨에서 음성 파이프라인을 처음 기동했다. 노드 4개를 띄우는 데까지 **설치 함정 4건**을
넘어야 했고, 전부 기존 문서에 없던 것이라 절차서에 반영했다.

기동 후 2단계를 일부 수행하다 **자가 되먹임 결함 1건**을 발견했다. 로봇이 자기 인사말
"네?" 를 사용자 발화로 받아 `/vica/user_text` 에 발행한다. 원인은 어제 3-2 측정을 위해
만든 `assets/wake_greeting.wav` 였고, **그 파일의 유무가 안전 특성을 바꾼다.** 파일을
비활성화해 우회했다.

성능 실측 3건을 얻었다. `docs/jetson-handoff.md` §2 의 "Jetson 에서 재측정 필요" 항목에
채울 값이다.

기동을 막은 순서대로 적는다. 증상 → 원인 대조표는 체크리스트 A.1 에 넣었다.

### 1-1. STT CUDA — 재빌드 없이 해결됨

PyPI 의 aarch64 `ctranslate2` 는 **CPU 전용**이다. 이 젯슨의 `~/jetson-builds/` 에
CUDA 로 빌드한 CTranslate2 **4.8.1** 이 있었고 venv 의 CPU 판과 **버전이 같아** 확장모듈과
`libctranslate2.so.4` 만 교체해 해결했다(재빌드 불필요, 약 40~90분 절약).

CUDA 빌드 `_ext.so` 의 RUNPATH 가 `$ORIGIN` 이라 같은 디렉터리에 라이브러리를 두면
`LD_LIBRARY_PATH` 없이 해결된다. CPU 판은 `_ext...so.cpu-backup` 으로 남겼다.

**이 빌드의 존재가 어느 문서에도 없다.** `docs/jetson-handoff.md` §3 에 추가해야 한다.

### 1-2. `VICA_STT_DEVICE` — `.env` 로는 안 된다

웨이크워드 노드·`wakeword_monitor` 는 `load_dotenv` 를 호출하지 않는다. **셸 환경변수만
본다.** `.env.example` 은 "기본 cuda" 라고 적었지만 코드 기본값은 `cpu` 다. 문서-코드
불일치이며 `AGENTS.md` §2 에 따라 코드가 현재 사실이다.

LLM 노드는 다르다 — `langchain_intent_parser.py:23` 이 `load_dotenv()` 를 부르므로
`.env` 를 읽는다. **다만 import 시점 1회라 노드를 다시 띄워야 반영된다.**

## 2. 발견 ★ — 인사 음성 wav 가 자가 되먹임을 만든다

### 증상 (실기 로그)

```text
685.4  TTS 재생[narration]: 비카야            ← 시험용으로 말하게 함
688.5  🙋 비카야 호출 — 청취 창 열림           ← 자기 목소리에 자가 트리거
691.6  🗣️ 호출 발화 -> /vica/user_text: '네'   ← 자기 인사말 "네?" 를 되먹음
       입력='네' -> intent=unknown
```

로봇이 혼자 부르고 혼자 답했다. 청취 창이 열린 뒤 **사용자가 말할 틈이 약 3초 동안 없다.**

### 원인

`audio_cue.py:7-10` 이 설계 의도를 명시한다 — 안내음은 TTS 를 거치지 않아
`/vica/tts_state` 를 켜지 않고, 따라서 긴급어 상시 감시가 쉬지 않는다. **0.15초짜리
순음을 전제한 설계다.**

그런데 `_greet()`(`ros_wakeword_node.py:113`)는 같은 통로로 **1.25초짜리 사람 목소리
"네?"** 를 내보낸다. 그래서 인사말 구간은 mute 가 걸리지 않는다.

| 경로 | 조건 | `/vica/tts_state` | mute |
| --- | --- | --- | --- |
| wav 직접 재생 | `assets/wake_greeting.wav` **있음** | 안 켜짐 | **안 걸림** |
| TTS 폴백 | 파일 **없음** | 켜짐 | 걸림 |

**파일 유무가 안전 특성을 바꾼다.** 그 파일은 2026-08-11 에 3-2("네?" 응답 시간) 측정을
위해 `scripts/make_cue_wavs.py` 로 만든 것이다. 즉 **측정 편의를 위한 조치가 안전 경로를
바꿨다.**

`assets/` 는 `.gitignore` 대상이라 저장소에는 흔적이 남지 않는다. 다른 기기에서
재현되지 않을 수 있다.

### 조치 (임시)

```bash
mv assets/wake_greeting.wav assets/wake_greeting.wav.disabled
```

TTS 폴백으로 돌아가 mute 가 걸린다. 인사 응답이 느려지므로 **3-2 측정값은 이 조건에서
나온 것으로 기록해야 한다.**

### 남은 설계 질문 `[TARGET]`

근본 대책은 **승인이 필요해 구현하지 않았다**(`GOVERNANCE.md` §4). 선택지:

1. 인사말도 TTS 경로로 통일 (느려짐 — 3-2 가 재려던 것을 포기)
2. `audio_cue.play` 에 "음성 재생" 구분을 두어 그때만 `tts_state` 를 켬
3. `tts_state` 가 true 인 동안 들어온 `user_text` 를 노드가 버림
4. 호출 경로에도 STT 검증 추가 (응답이 느려져 설계 의도와 충돌)

## 3. 2-7 부수 발견 — 두 경로의 방어가 다르다

`suppress_during_tts:=false`(계측 모드)에서 TTS 로 긴급어·호출어를 말하게 했다.

| 경로 | 관문 | mute 없을 때 |
| --- | --- | --- |
| 긴급어 | `gate_b` **+ STT 전사 + 문자열 일치** (`wakeword_monitor.py:155`) | **버팀** (오인 관찰 안 됨) |
| 호출 | `gate_a` 통과 **즉시 응답, STT 검증 없음** (`:135`) | **뚫림** |

체크리스트 2-7 은 결과를 "오인 0건 → mute 축소 여지" 와 "오인 잦음 → mute 필수" 로
갈라 두었는데, **긴급어만 보면 전자, 호출까지 보면 후자다.** 호출 채널이 뚫리므로
**mute 축소는 선택지에서 내린다.**

`/vica/tts_state` 가 끊기면 fail-safe 10초 동안 마이크가 실제로 열리므로, 그 구간의
위험이 이 발견으로 구체화됐다.

**실운용 영향은 낮다** — `replies.py`·`config/destinations.yaml` 어디에도 로봇이
"비카야" 를 말하는 문구가 없다. 재현하려면 일부러 말하게 시켜야 한다.

### 4-2. STT / TTS / LLM

| 항목 | 값 | 비고 |
| --- | --- | --- |
| whisper medium, cuda/float16 | 2초 창 추론 **1.84초** | 무음 입력. handoff §2 "예상 ~1.2초" 보다 느림 |
| TTS 합성 (supertonic, **CPU**) | 4.46초 음성에 **3.9~4.1초** (0.88x 실시간) | GPU 면 10배 빠름 (`src/tts.py:19`) |
| LLM (Ollama Cloud, gemma4:cloud) | **1.6~1.8초** | 클라우드 왕복 포함 |
| 단위 시험 | **221 passed** | |

**TTS 가 CPU 로 도는 이유**: `onnxruntime==1.23.2`(handoff §3 핀)에 CUDA provider 가
없다. `src/tts.py:20` 은 `CUDAExecutionProvider` 를 요청하지만 없어서 CPU 로 자동
폴백한다. `requirements.txt` 는 `onnxruntime-gpu` 를 권하고 `[미확정]` 으로 표시해
두었는데, **위 4초가 그 미확정 항목을 닫을 실측값이다.**

Orin NX 의 하드웨어 한계가 아니라 **설치 구성 문제**다.

**2-5 판정에 영향**: "하던 말이 즉시 끊기는가"(선점)와 "긴급 문장이 나오기까지"(합성
지연)를 나눠서 봐야 한다. 체크리스트 2-5 에 반영했다.
