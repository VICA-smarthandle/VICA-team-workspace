## 1. 일시정지 후 아무것도 안 되던 문제 — 원인 셋이 사슬로 묶여 있었다

증상은 "일시정지는 되는데 '다시 출발' 버튼이 **뜰 때도 있고 안 뜰 때도 있고**,
떠도 안 눌리고, 앱을 재연결해도 비상정지를 눌러도 안 되고,
**젯슨에서 rosbridge 를 껐다 켜야만** 풀린다" 였다.

원인이 하나다. 그것이 세 곳에서 각각 증상을 냈다.

### 1.1 `cancelTask()` 에만 시한이 없다

humble 의 `nav2_simple_commander/robot_navigator.py`:

```python
def cancelTask(self):
    if self.result_future:
        future = self.goal_handle.cancel_goal_async()
        rclpy.spin_until_future_complete(self, future)   # 시한 없음
```

같은 파일의 `isTaskComplete()` 에는 `timeout_sec=0.10` 이 있는데 **여기에만 없다.**
Nav2 가 취소에 응답하지 않으면 영영 돌아오지 않는다.

### 1.2 그 호출이 이벤트 발행보다 **앞**에 있었다

```python
def _cancel_nav(self, destination=None, event="goal_canceled"):
    with self._nav_lock:
        if self._nav_active:
            self.navigator.cancelTask()      # 여기서 멈추면
            self._nav_active = False
    if destination is not None:
        self._publish_goal_event(event, destination, reason)   # 이 줄에 도달 못 함
```

앱은 `waiting_reason == '일시정지'` 로만 판단하고, 그 값은 `goal_paused` **이벤트**
한 번으로만 켜진다. **버튼이 뜰 때도 있고 안 뜰 때도 있던 이유가 정확히 이것이다.**

| Nav2 가 취소에 응답하면 | 이벤트 발행됨 → 버튼 뜸 |
| --- | --- |
| 응답 안 하면 | 이벤트 못 감 → 버튼 안 뜸 **+ 노드도 멈춤** |

### 1.3 `_main_group` 이 MutuallyExclusive 라 뒤가 다 막힌다

`pause`·`resume`·`cancel`·목적지요청이 전부 같은 콜백 그룹이다. 하나가 멈추면
나머지가 전부 그 뒤로 줄을 선다.

### 1.4 rosbridge 가 서비스 호출을 본 흐름에서 실행한다

`rosbridge_websocket_launch.xml` 기본값:

```xml
<arg name="call_services_in_new_thread" default="false" />
<arg name="default_call_service_timeout" default="0.0" />
```

`supervisor_bringup.launch.py` 는 `address`·`port` 만 넘겼으므로 이 기본값을 썼다.
**응답하지 않는 호출 하나가 rosbridge 전체를 막는다.** 앱 재연결이 소용없던 이유다 —
막힌 것은 창구지 손님이 아니다.

### 1.5 고친 방법 — 세 곳에서 각각 끊는다

| | 무엇 |
| --- | --- |
| 🅰 방벽 | `supervisor_bringup` 에 `call_services_in_new_thread:=true`, `default_call_service_timeout:=5.0`. 5.0 은 앱의 `callService` 기본 timeout 과 같은 값이다 — 앱이 이미 포기한 호출을 서버가 붙들 이유가 없다 |
| 🅱 근본 | `_cancel_nav` 순서를 뒤집고 `cancelTask()` 를 별도 스레드로. 모터 정지 권위는 원래 이 호출이 아니라 Safety 래치 체인이므로 취소가 늦어져도 안전 경로는 같다. `_start_nav` 는 `_nav_lock.acquire(timeout=2.0)` 으로 시한부로 잡는다 |
| 🅲 표시 | `vica_status_app_node` 가 `/vica/robot_state` 를 구독해 `is_paused` 를 쓴다. Mission Manager 는 같은 사실을 **1 Hz 로 상시 발행하고 있었다.** 이벤트는 빠르고 상태는 확실하므로 둘을 함께 쓴다 |

`RobotState.msg` 에는 목적지 이름이 없으므로 `current_goal` 은 종전대로 goal
이벤트가 담당한다. 이 구독은 `is_paused` 하나만 대체한다.

## 2. 알람 폭주 — **처음 진단이 틀렸다**

### 2.1 철회한 가설

"래치된 결함이 매 tick(1 Hz) 재알림하므로 앱 목록 200칸이 3분 20초면 찬다"

**틀렸다.** 앱이 reminder 를 이미 버리고 있었다.

```dart
bool get belongsInHistory => transition != FaultTransition.reminder;
```

1 Hz 폭주는 **화면이 아니라 네트워크에만** 부담이었다.

### 2.2 진짜 기전 — 히스테리시스가 한 군데도 없다

```python
# event_deduplicator.py — 이번 tick 에 안 보이면 곧바로 '해소'
for key in list(self._records):
    if key in seen_keys: continue
    events.append(Event(..., TRANSITION_CLEARED))
```

임계값 근처에서 오르내리는 관측이 **매 초 "발생 → 해소" 두 건**을 만든다.
실제로 `/odom` 프로브는 `min_hz 20` 인데 CPU 가 모자랄 때 15.5 Hz 까지 떨어진
기록이 있다(`devlog/2026-08-01-drive-tuning-and-duplicate-stack.md`).

형광등이 나간 게 아니라 **깜빡이는** 것이었다.

### 2.3 고친 것

| | 이전 | 이후 | 근거 |
| --- | --- | --- | --- |
| `latched_reminder_interval_sec` | 없음(매 tick) | **10.0** | 현재 상태는 `/robot/health` 의 `active_faults` 가 1 Hz 로 상시 보낸다. 이벤트는 '변화'용이다 |
| `reminder_interval_sec` | 30.0 | **300.0** | 30초마다 같은 알림을 봐도 사람이 할 수 있는 일이 없다 |
| `clear_confirm_ticks` | 없음(1 tick) | **2** | 지연시키는 것은 '해소'뿐. '발생'은 즉시 알린다 — 결함을 늦게 지우는 것은 안전한 방향 |
| 앱 목록 상한 | 200 / 200 | **100 / 100** | |
| 접어보기 | 없음 | 연속 동일 항목 → `×N회` + `처음 hh:mm:ss` | 지우지 않고 접는다 |

`test_flapping_observation_produces_no_event_churn` 이 깜빡임 패턴에서 이벤트가
하나도 안 나오는 것을 잠근다.

## 3. 모드 분리 — 로그인 뒤 무엇을 하러 왔는지 고른다

```
로그인 → [주행 / 지도] → 각 모드
```

저장하지 않는다. 앱을 새로 열 때마다 다시 고른다 — 지난번에 매핑을 했다고 이번에도
매핑일 이유가 없고, **잘못된 모드로 자동 진입하는 편이 더 위험하다.**

### 3.1 중복 실행 감지 — rosapi

중복 실행은 이 프로젝트에서 실제로 회차를 날린 사고다.

- 2026-08-11 20:07 스택이 두 벌 돌아 매핑 두 회차 유실
- Nav2 와 SLAM 은 둘 다 `wheel_ekf.launch.py` 를 include 하므로 동시에 뜨면
  `/odom` 발행자가 둘이 된다

**그런데 그 상태가 되어도 지금까지 아무도 알려주지 않았다.**

판정 근거는 rosapi 다. rosbridge 가 함께 띄우므로(`rosbridge_websocket_launch.xml`
74행) 새로 띄울 것이 없고, 앱의 `callService` 가 이미 범용이라 클라이언트 코드도
그대로다.

```
/rosapi/nodes       종류 충돌 + 같은 이름이 두 번 나오는지
/rosapi/publishers  /odom 발행자가 2개 이상인지
```

두 신호를 함께 보는 이유는 ROS 2 그래프가 같은 이름을 어떻게 돌려주는지에
기대지 않기 위해서다. `/ekf_filter_node`·`/encoder_feedback` 은 두 스택이 공유하므로
'떴는지' 판정에는 쓰지 않는다.

연결이 없으면 막지 않고 **'확인 불가'** 로 둔다. 모드 전환은 앱 화면만 바꾸는 일이라
막아서 얻는 안전이 없고, 막으면 연결이 안 되는 상황에서 사람이 갇힌다. 다만
"확인해보니 없다"와 "확인을 못 한다"를 섞지 않는다.

## 4. 지도 실시간 확인 — RViz 를 가져오지 않는다

### 4.1 왜 RViz 스트리밍이 안 되는가

**보려는 행위 자체가 지도를 나쁘게 만든다.**

> "RViz 하나가 코어 1.5개를 쓴다. CPU 가 모자라 EKF 가 설정 30 Hz 의 절반인
> 15.5 Hz 로 떨어졌다" — `devlog/2026-08-01-drive-tuning-and-duplicate-stack.md:33`

Cartographer 는 오도메트리 예측에 기대므로 EKF 가 느려지면 지도가 직접 나빠진다.

### 4.2 실측 비교 (`vica_map_0630`, 572×443 = 25만 칸)

| 방법 | 한 장 | 젯슨 CPU |
| --- | --- | --- |
| RViz 화면 스트리밍 | — | 코어 1.5개 + 인코딩 |
| `/map` rosbridge JSON | **703 KB** | 직렬화 부담 |
| `/map` cbor-raw | 247 KB | 낮음 |
| **PNG → HTTP** | **4.5 KB** | **1.1 ms/장** |

점유격자는 같은 값이 넓게 이어져 있어 zlib 이 **53배** 줄인다.
저장소의 실제 파일이 증거다 — `vica_map_0630.pgm` 253,411 B vs `.png` 4,860 B.

### 4.3 Pillow 를 쓰지 않는다

젯슨에 없을 수 있다(`vica_map_save.sh` 가 "Pillow 가 없어" 경로를 갖고 있다).
표준 라이브러리(zlib, struct)만으로 쓴 회색조 PNG 가 오히려 더 작고 빨랐다.

```
순수 zlib level 6   4,533 bytes   1.1 ms/장
Pillow              4,740 bytes   1.6 ms/장
raw int8          253,396 bytes
```

### 4.4 갱신 2초면 충분하다

매핑 주행 속도가 0.3 m/s 이므로 2초에 60 cm 다. 지도가 그보다 빨리 변하지 않는다.

### 4.5 파일 하나를 덮어쓴다

여러 장으로 쌓으면 30분 매핑에 900장 22 MB 이고, 앱 이미지 캐시(디코딩하면
572×443×4 = 약 1 MB/장)가 **3분 20초** 만에 상한 100 MB 에 닿는다.

- 원자적 rename 으로 쓴다. 반쯤 쓰인 파일을 HTTP 가 내보내면 잘린 이미지가 간다
- `maps/` 바로 아래가 아니라 `maps/_live/` 하위다. `map_list_node` 가
  `glob("*.png")` 로 **비재귀** 조회를 하므로 미리보기가 저장된 지도인 척 목록에 안 낀다
- 지우는 것은 **매핑 시작 때**와 **저장이 확인된 뒤**뿐이다.
  **저장 실패 때는 남긴다** — 2026-08-12 오전에 아홉 회차가 저장 실패로 사라져
  원인을 화면 캡쳐에서 겨우 찾은 적이 있다. 그때 미리보기는 유일하게 남은 그림일 수 있다

### 4.6 그림보다 숫자가 중요하다

판정 기준이 이미 숫자로 정해져 있다(`docs/cartographer_corridor_mapping.md` §6).

```
합격선: differs by translation 최대 1 m 미만 · 1 m 초과 0건
```

앱에 이 숫자를 표시하는 것(B6)은 아직 안 했다.

## 5. 매핑 실행 — 앱이 무엇을 띄우고 무엇을 안 띄우는가

### 5.1 프로세스의 주인

앱이 `ros2 launch` 를 직접 띄우면 앱이 꺼졌을 때 자식이 고아로 남는다. 젯슨에
상주하는 `mapping_supervisor_node` 가 자식을 소유하고 앱은 서비스만 부른다.

- `start_new_session=True` 로 새 프로세스 그룹을 주고, 종료는 그룹 단위로
  SIGINT → SIGTERM → SIGKILL 로 올린다. launch 가 띄운 손자까지 정리된다
- `destroy_node` 에서도 자식을 정리한다
- **저장은 콜백에서 기다리지 않는다.** `vica_map_save.sh` 는 `map_saver` 제한시간이
  기본 120초라 그만큼 걸릴 수 있다. 1절과 같은 실수를 반복하지 않는다

### 5.2 safety 는 launch 에서 뺐다

터미네이터 `vica_map` 레이아웃의 safety 칸이 **`mode=AUTO`** 라 창을 띄우는 순간
자동 실행된다. launch 가 또 띄우면 **항상** 두 벌이 된다.

motor 칸은 `mode=HOLD`(사람이 엔터를 눌러야 실행)라 사정이 다르다. 그래서 motor 만
`start_motor` 인자로 켜고 끌 수 있게 두고, 감독 노드가 그래프를 보고 정한다.

> safety 가 motor 보다 먼저여야 한다는 순서(bringup manual §4)는 그대로 유효하다.
> 그 순서를 지키는 주체가 launch 가 아니라 터미네이터 레이아웃이 된 것뿐이다.

### 5.3 앱 teleop

젯슨 터미널의 teleop 칸과 **같은 경로**다.
`/cmd_vel_req → Safety Supervisor → /cmd_vel_safe → motor`. 우회하지 않는다.

**데드맨은 이미 두 겹 있었다.**

| 계층 | 값 |
| --- | --- |
| `safety_supervisor_node` | `cmd_timeout_sec: 0.5` |
| `mdrobot_can_control` | `cmd_timeout_sec: 0.5` |

그래서 **누르고 있는 동안만** 발행한다. 한 번 눌러 계속 가게 만들면 그 안전장치가
통째로 무력해진다. `onTap` 이 아니라 `Listener` 의 포인터 이벤트를 쓰고, 포인터
취소(손가락이 미끄러짐·시스템이 가로챔)에도 멈춘다.

속도 상한 0.3 m/s · 0.4 rad/s 를 **앱에서 묶는다.** Safety 상한(1.0/2.0)은 실주행의
3.8~5배라 폭주만 막는다(`nav2_backlog.md` C8). 매핑 속도 근거는
`cartographer_corridor_mapping.md` §4 — 더 빠르면 스캔 사이 이동이 예측 탐색
창(0.1 m)에 닿는다.

## 6. 라이다 사거리 8 → 11 m (NAV2 CM-1) — **dev 에 푸시**

```
TRAJECTORY_BUILDER_2D.max_range               8.0 -> 11.0
TRAJECTORY_BUILDER_2D.missing_data_ray_length 8.5 -> 11.5
```

라이다는 12 m 를 보는데 8 m 에서 자르고 있었다. 복도에서 앞뒤 위치를 알려 주는 것은
**멀리 있는 것들**(복도 끝·문·교차로)인데, 8 m 에서 자르면 그걸 버리고 양옆 벽만
남는다. **양옆 벽은 앞뒤에 대해 아무 말도 하지 않는다.**

2026-08-12 에 44 m 복도에서 최대 7.01 m 가 어긋난 것이 바로 그 앞뒤 미끄러짐이다
(회전은 0.031 로 멀쩡했다. 병진만 틀렸다).

**12.0 이 아니라 11.0 인 이유**: 12.00 은 드라이버 신고 **상한**이고 실내 실측
최대 반사는 9.04 m 다. 12.0 으로 두면 아무것도 안 맞은 빔이 유효한 것처럼 섞인다.

이것만 `dev` 에 따로 넣고 푸시했다(`d692bdb`). 내일 매핑에 바로 필요하기 때문이다.

## 8. 앱 정리 — 지도 삭제와 로봇 관리 제거

### 8.1 지도 삭제 신설

지금까지 앱에 지도 삭제가 없었다. '선택 장소 삭제'는 지도 안의 목적지를 지우는
것이고, `vica_map_save.sh` 가 덮어쓰기를 거부하므로 같은 이름으로 다시 그리려면
젯슨에서 직접 `rm` 을 해야 했다.

**장소 저장 화면 맨 아래**에 둔다(설정에 뒀다가 옮겼다 — 관계가 멀었다).
지도를 고르는 자리(맨 위)에서 멀리 떼어 실수로 눌리지 않게 한다.

노드가 강제하는 안전장치:

- 이름 규칙 `^[A-Za-z0-9_-]+$` — 경로 문자를 막아 `maps/` 밖을 못 건드리게 한다
- **`maps/CURRENT_MAP` 이 가리키는 지도는 거부** — 지우면 초기 위치 스크립트와 앱이
  없는 지도를 가리키고, 그 상태는 조용히 틀린다
- '장소도 함께 지웁니다' 체크박스를 켜야 버튼이 열린다. 선택지가 아니라 **확인 절차**다

### 8.2 로봇 관리 화면 제거

고유한 정보가 하나도 없었다. 상세 시트의 일곱 항목이 전부 다른 화면에 있었고
**현재 위치 화면이 상위집합**이었다(`map_id` 까지 더 보여주고 좌표도 더 정밀하다).

지우면서 **app.dart 의 취약점**이 드러났다. 화면·제목·드로어 항목·사이드바 항목
**네 개의 목록**을 손으로 맞춰 들고 있었고, 인덱스가 숫자로 박혀 있었다.

```dart
static const _systemDiagnosticsIndex = 5;   // 화면 하나 빼면 4가 돼야 한다
```

주석에는 "숫자를 코드에 직접 쓰지 않습니다"라고 적혀 있었는데 실제로는 박혀 있었다.
어긋나도 예외도 경고도 안 난다 — "메뉴는 A 인데 화면은 B" 가 되고 사람이 눈으로
봐야만 안다.

1. 인덱스를 `_titles.indexOf` 로 찾게 했다. 손으로 맞추는 약속은 언젠가 어긋나지만
   찾게 하면 어긋날 수가 없다
2. `supervisor_shell_test` 가 사이드 메뉴를 하나씩 눌러 AppBar 제목이 같은지 본다

2번은 red-green 으로 확인했다. `_titles` 의 두 항목 순서만 바꾸자 실패했고 되돌리자
통과했다.
