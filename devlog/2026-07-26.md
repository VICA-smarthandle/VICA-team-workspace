## 음성 → 주행 종단 첫 성공

- STT → LLM → `/vica/intent` → Mission gate → Nav2 → Safety → motor 경로로 실제 주행이
  처음 확인됐다. 마이크·스피커를 연결한 실기 시험이다.
- 긴급어 경로도 동작했다. 긴급 발화가 TTS 큐를 선점해

- 종단 전체가 검증 완료된 것은 아니다. 아래 문제 5건이 남아 있고, 특히 긴급어 미검출
  사례가 1회 있었다.

## 첫 시험 실패의 원인: `map_id` 절단

- 처음에는 모든 발화가 `matched=None`으로 끝나 주행이 시작되지 않았다.
- 원인은 launch 인자가 `map_id:=vica_map_06`으로 잘려 입력된 것이다. 실제 catalog는
  `~/vica_data/destinations/vica_map_0630/`에만 있다.
- LLM 노드는 시작 시 `목적지 catalog가 없어 빈 목록을 사용합니다` WARN 한 줄만 남기고
  빈 목록으로 계속 진행한다. 그래서 실패가 눈에 띄지 않았다.
- 빈 catalog에서도 LLM은 대답을 생성하지만(`화장실로 안내해 드리겠습니다`)
  `matched_destination_id`가 비어 Mission gate의 `NO_MATCHED_ID`에서 차단된다. 존재하지
  않는 장소(`로봇 충전소`, `정비소`)를 제안하기도 했다.
- STT 인식 품질 자체는 양호했다. 오인식은 `방 2로`→`방위로` 정도였다.
- `vica_goto_goal.py`가 정상 동작한 것은 인자로 `vica_map_0630`을 온전히 넘겼기
  때문이며 음성 경로와 무관하다.

## 음성 실행 환경 정합화

- 실행 가능한 `.venv`가 workspace 정본이 아닌 개인 사본에만 있어, 정본
  (`vica-voice-llm/`, `dev`)에 환경을 새로 구성했다. Python 3.10.12,
  `faster-whisper 1.2.1` + `ctranslate2 4.4.0`(Jetson CUDA 빌드),
  `onnxruntime-gpu 1.24.0`, `langchain 1.3.14`.
- `requirements.txt`는 PC(Python 3.12) 기준 핀이라 ARM64/3.10에서 resolver가 통째로
  실패한다(`networkx==3.6.1`이 3.11+ 요구). 검증된 버전 조합으로 설치했다.
- `src/stt.py`에 Jetson CUDA `ctranslate2` preload를 추가했다. pip의 ARM64 휠은 CPU
  전용이라 `.venv/ct2lib/libctranslate2.so.4`를 `RTLD_GLOBAL`로 먼저 적재한다.
  라이브러리가 없는 환경에서는 기존 CPU 동작을 유지한다.
- STT 모델은 `medium` 고정으로 정했다. `small`은 `식당`→`직당` 류 오인식이 있다. 실측
  로드 시간은 최초 88초(다운로드 포함), 캐시 이후 3초다.
- 개인 사본에만 있던 `vad_filter`·`beam_size` 변경은 이식하지 않았다. 판단이 갈리는
  항목은 `dev` 기준을 따른다.

## 실기 시험에서 발견한 문제 5건

상세 근거와 개선안은 `vica-voice-llm/docs/voice-improvement-backlog.md`에 있다.

| # | 문제 | 성격 |
| --- | --- | --- |
| 5 | "멈춰"를 외쳤는데 멈추지 않음(1회) | 안전, 최우선 |
| 2 | 로봇 자기 목소리가 대화 STT에 녹음됨 | 인식 |
| 1 | TTS 발화 순서가 꼬임 | 대화·신뢰성 |
| 3 | 엔터 push-to-talk → wakeword 전환 필요 | 사용성 |
| 4 | TTS 답변이 정형적 | 대화 품질 |

핵심 판단 세 가지를 기록해 둔다.

- 5번은 인식 실패로 단정할 수 없다. `emergency_monitor`는 TTS 재생 중 감시를 mute하고
  해제 후에도 `window_sec`(2.0초)만큼 판정을 보류한다. 즉 **로봇 발화 종료 후 약 2초의
  구조적 사각지대**가 있다. wakeword 학습 이전에 이 구간을 먼저 확인해야 한다.
- 2·3·5는 모두 마이크 입력 경로를 공유한다. 현재 `emergency_monitor`와 `stt`가 각각
  `sd.InputStream`을 연다. 개별 수정보다 입력 파이프라인 단일화가 선행 과제다.
- 마이크 동시 점유 자체는 문제가 아니다. PulseAudio 경유로 두 스트림이 같은 오디오를
  정상 수신하는 것을 실측했다.
