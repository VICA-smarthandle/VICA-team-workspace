# "비카야" 호출 접근 — 구현과 실기 준비 (2026-09-10)

대기 중인 로봇이 "비카야" 호출을 들으면 **소리 난 방향으로 제자리 회전**해 카메라를
겨누고, 사람이 보이면 **이미 있던** 사람접근 경로가 이어받는다. 못 찾으면 조용히
원래 각도로 되돌아간다.

- 설계: `docs/superpowers/specs/2026-09-10-voice-call-approach-design.md`
- 계획: `docs/superpowers/plans/2026-09-10-voice-call-approach.md`
- 브랜치: ROS2 `feat/voice-call-approach` · 음성 `feat/wake-doa-publish` (둘 다 미푸시)

## 1. 알고 시작한 것 — 만들 것은 방아쇠 하나뿐이었다

dev 를 읽어보니 **후반부가 전부 이미 있었다.**

| 단계 | 상태 |
| --- | --- |
| 사람 발견 → 자동 접근 요청 | 있음 (1.5~8 m, 안정된 사람) |
| 사람 앞 1.1 m 정지 | 있음 (`approach_goal`) |
| "안내를 받으시겠어요?" | 있음 |
| "네/아니오" 판정 | 있음 (규칙 우선 + LLM 폴백) |
| 수락 → **로봇 180° 회전**(핸들을 사람 쪽으로) | 있음 (`approach_turn_yaw_deg=180.0`) |
| 온보딩 → "어디로 가고 싶으신가요?" | 있음 |

없는 것은 **"소리 쪽으로 고개 돌리기"** 하나였다. `/vica/wake` 도 Mission Manager 가
이미 구독하고 있었고, 대기 상태에서만 의도적으로 무시하고 있었다.

호출 순간의 DOA 를 잠그는 코드(`wakeword_monitor.py`, ±15°·2분)도 이미 있었다.
barge-in 판정에만 쓰고 **ROS 로 내보내지 않았을 뿐**이다.

**"손잡이 180도"는 로봇 본체 회전이다.** 핸들 서보(`SERVO_LEFT=180/SERVO_RIGHT=0`)는
주행 중 좌우 안내용이고, 돌려도 핸들이 반대편으로 옮겨가지 않는다.

## 2. 만든 것

- **음성**: 호출 순간의 방향을 `/vica/wake_doa`(`std_msgs/Float32`, 0~359°)로 1회 발행.
  잠금과 통보를 `note_wake_direction` **한 자리**에 묶었다 — `run()` 에서 `on_wake`
  콜백이 방향 잠금보다 **먼저** 불리므로, 노드가 나중에 읽으면 **직전 대화의 방향**을
  내보내게 된다.
- **ROS2**: `State.SEEKING` 추가. 대기 중 방향을 받으면 `SpinInPlace` 로 제자리 회전 →
  회전이 끝나면 **`_to_idle()` 로 IDLE 에 내려놓고 탐색 창만** 든다 → 창 안에 접근
  요청이 오면 기존 경로가 이어받고, 없으면 조용히 복귀.

**IDLE 로 내려놓는 것이 설계의 요점이다.** 접근 관문(`check_approach_gate`)이 IDLE 만
통과시키므로, 그렇게 해야 **그 관문을 한 줄도 안 바꾸고** 합류한다.

회전 중에는 `is_moving` 을 세워 YOLO 추론을 멈춘다. 화면이 통째로 흐르는 동안의
탐지는 변위 관문(0.3 m)에 어차피 걸려 버려진다 — 이 로봇의 제1 병목은 CPU 다.

## 3. DOA 부호 실측 — 3지점은 실패, 걷기는 성공

부호(마이크 각도가 반시계로 커지는가 시계로 커지는가)를 틀리면 **로봇이 정확히
반대로 돈다.** 이 장비에서 잰 기록이 없어 먼저 쟀다.

**1차(3지점 측정) 실패.** 정면 11.8°(기준선 정상)는 나왔는데, 좌우 두 지점이
327.0° / 311.7° 로 **15° 밖에 안 떨어졌다.** 로봇 양옆이면 약 180° 벌어져야 한다.
좌우를 사람 기준으로 잡은 혼동이 있었지만, 그것만으로는 15° 간격이 설명되지 않는다.

**2차(걷기 관찰) 성공.** 지점을 찍는 대신 **로봇 주위를 걸으며 각도 흐름**을 봤다.

- 로봇을 마주 보고 **사용자 기준 오른쪽**으로 이동 → 0° → 119° (뒤쪽 절반 표본 0)
- 사용자 기준 **왼쪽**으로 이동 → 210~359° 대역
- 8/12 구역에 표본 → 마이크는 정상. 1차 실패는 **서는 위치 문제**였다.

마주 본 사람이 자기 오른쪽으로 가면 거울처럼 **로봇의 왼쪽**이고, 그때 각도가
**커졌다**. 즉 마이크는 **반시계로 증가**하며 Nav2 규약(양수=반시계)과 같다.

**결론: `wake_doa_sign = +1.0`** (기본값 그대로).

교훈: 방향 센서의 회전 방향은 **지점 두 곳을 찍는 것보다 한 바퀴 걸으며 흐름을 보는
쪽이** 확실하다. 지점 측정은 서는 위치 오차에 통째로 무너진다.

## 4. 리뷰가 잡은 것 — 상태 목록 누락 두 번

**작업 리뷰(Task 5)**: `_GOAL_ACTIVE_STATES` 에는 `SEEKING` 을 넣었는데
`_APPROACH_STATES` 에는 빠뜨렸다. `on_intent` 가 이 튜플로만 거부하므로, **회전 중
음성 목적지 명령이 통과해 진행 중 `SpinInPlace` 를 취소하지 않고 `Navigate` 를
낸다** → Spin 과 NavigateToPose 가 동시에 `/cmd_vel_req` 로. `TURNING` 은 이미 이
튜플에 있어 거부되는데 `SEEKING` 만 비대칭이었다.

**최종 전체 리뷰(Critical)**: 더 나쁜 것이 하나 더 있었다.

`/vica/wake` 가 **항상 먼저** 도착하고(같은 콜백 그룹이라 순차 처리), 그 처리 중
`on_wake` 가 WAITING·CONFIRMING·ASKING_NEXT·AWAITING_USER 를 `_to_idle()` 로 내린다.
그 **직후** `/vica/wake_doa` 의 "IDLE 일 때만" 관문은 **이미 IDLE 이 된 상태**를 보고
통과시킨다. 리뷰어가 5개 상태에서 실행으로 재현했다.

> 결과: 도착 후 대화 중에 "비카야, 다음은 도서관"이라고 부르면 —
> **사용자가 핸들을 잡은 채 로봇이 최대 180° 제자리 회전한다.** 예고 멘트도 없다.

온보딩 멘트가 사용자에게 **"돌아오시면 '비카야'라고 말씀해 주세요"** 라고 직접
시키므로 실제로 밟게 되는 경로였다.

**수리**: `on_wake`·`on_return_brake` 가 **실제로 상태를 바꿨을 때만** 소비 시각을
찍고(`_wake_consumed_at`), `on_wake_doa` 가 `WAKE_CONSUMED_GUARD_SEC = 2.0` 이내면
거절한다. 두 토픽의 도착 순서와 무관하게 결과가 같아진다 — 먼저 오면 상태로, 나중에
오면 시각으로 거절. **원래 IDLE 이던 정당한 호출은 도장이 안 찍히므로 그대로 열린다**
(재검토어가 이 부작용 부재를 직접 확인).

같은 파도에 Important 6건도 고쳤다: 낡은 탐색 창이 `exit_arrival_dialog` 를 타고
살아남는 문제, 앱 선점 시 회전 미취소, launch 파라미터 미노출, 무판정 로그 부재,
계약 문서 누락, 창 시간 6→8초(1 Hz 상태 발행 지연 + `detection_gate` 연속 관측 3초를
빠뜨린 계산이었다).

교훈: **상태를 하나 더하면 그 상태가 들어가야 할 목록을 전부 찾아야 한다.** 두 번 다
같은 종류의 누락이었고, 두 번 다 개별 작업 리뷰가 아니라 **넓게 보는 리뷰**가 잡았다.

## 5. 실기 준비

빌드 완료(메인 워크스페이스에 `feat/voice-call-approach` 체크아웃). 시험 384 통과 /
음성 446 통과. `wake_doa_sign` 실측값 `+1.0` 이 기본값이라 따로 넣을 것 없다.

### 시작 전

- **바퀴를 띄우고** 첫 회전 확인. 바닥에서 바로 돌리지 않는다.
- **모터 노브가 0 % 가 아닌지** 본다(0 이면 회전이 안 나가는데 로그는 다른 문제처럼 보인다).
- **반경 1.5 m 안에 사람·기물이 없는 곳**에서. 핸들이 뒤로 길어 실제 스윕이 차체보다 크다.

### 볼 것

| # | 항목 | 기대 |
| --- | --- | --- |
| 1 | `ros2 topic echo /vica/wake_doa` 켜고 "비카야" | 부를 때마다 값 1회 |
| 2 | 왼쪽·오른쪽·뒤에서 호출 | **부른 쪽으로** 회전 (반대면 `wake_doa_sign:=-1.0`) |
| 3 | **2 m 이상** 떨어져 호출 후 대기 | 회전 → 접근 → 질문 → "네" → 180° 회전 → 온보딩 |
| 4 | **안내 중·도착 대화 중** 호출 | **핸들이 절대 안 돈다** (Critical 회귀 확인) |
| 5 | 아무도 없는 쪽으로 유도 | **조용히** 원래 각도로 복귀 |

### "돌긴 도는데 안 온다" 가 나오면 — 세 갈래로 가른다

구분용 로그를 심어 두었다. 읽을 것 3종:
미션 `'비카야' 방향 …` · 인지 `추론 게이트`/`too_near`/`insufficient_history` ·
음성 `🧭 호출 방향 N°`.

| 원인 | 가르는 법 |
| --- | --- |
| 너무 가까움 (1.5 m 관문) | 뒤로 물러나 재시도 |
| 모델이 못 알아봄 | 흰지팡이 들고 재시도 |
| 8초 안에 판정 미완 | `seek_look_sec:=12.0` |

## 6. 남겨 둔 것

- **근접 호출(2순위).** 부른 사람이 1.5 m 안이면 `TOO_NEAR` 로 거절돼 끝까지 안 간다.
  `min_distance_m` 을 낮추지 **않는다** — 그 값의 근거는 "이보다 가까우면 접근
  goal(1.1 m)이 이미 지나간 자리다" 이고, 낮추면 검증된 접근 동작이 무너진다.
  대신 **접근 단계를 건너뛰고 바로 질문**한다. 신호는 이미 나가고 있다
  (`/vica/person_detection` 에 `stable=true`·`approachable=false`·`distance_m`).
  착수는 실기 1회차 뒤.
- **감지 대상 — 두 경로의 눈이 달라야 한다 (2순위, 근접 호출과 한 묶음).**
  `person_detector_node` 에 **클래스 필터가 없다** — 전용 모델이 내놓는 것을 그대로
  쓴다. 그 모델은 **"지팡이를 잡은 사람"** 을 검출한다(2026-09-10 사용자 확인).

  자동 발견 경로에는 이것이 옳다 — 아무한테나 말 걸면 안 되니 확인이 필요하다.
  **호출 경로에는 맞지 않는다.** 부른 사람은 이미 목소리로 의사를 밝혔는데 지팡이가
  보이느냐로 다시 걸러진다. 실패는 "지팡이가 없어서"가 아니라 **"지팡이가 안 보여서"**
  난다 — 부르는 자세에서 몸에 가림, 접어 든 상태, 그리고 **직원·보호자가 대신 부르는
  경우**는 아예 안 잡힌다.

  **방향(사용자 제안): 호출 경로만 기성 YOLO 의 `person` 검출로 돌린다.**
  `person_geometry` 의 거리·좌표 계산은 **bbox 와 depth 배열만** 받고 어느 모델이 그린
  상자인지 따지지 않으므로(`body_depth_median_m`·`bbox_center`), 기성 모델의 상자를
  그대로 꽂을 수 있다.

  비용 둘: ① 모델 하나가 **상시 메모리** 상주(추론은 회전 뒤 8초 창에서만 도므로 CPU
  부담은 작다) ② 엔진 준비 — 전용 모델은 TensorRT `.engine` 으로 돌고 엔진은 만든
  기기에 묶인다. `.pt` 로 느리게 돌리면 8초 안에 판정이 안 설 위험이 있다.

  **1.5 m 근접 호출과 같은 뿌리**(호출 경로가 자동 발견 경로의 관문을 물려받았다)이므로
  **한 작업으로 묶어 설계한다.** 실기 1회차 결과가 그 설계의 입력이다 — 지팡이 검출이
  호출 상황에서 얼마나 잡는지에 따라, 두 번째 모델이 필요한지 아니면 창 시간만 늘리면
  되는지가 갈린다.
- **근접 응대 — 하드웨어를 기다린다 (2026-09-10 사용자 결정).**
  마이크는 거리를 모르므로 부르는 순간에 "가까운가"를 판단할 수 없다. 그래서
  **거리를 재지 말고 순서로 가르는** 안을 검토했다:

  ```
  "비카야" → "네?" → (안 돎) 접근 질문 + 손잡이 진동
      답이 온다  → 온보딩            (답이 왔다 = 가까이 있었다는 증거)
      침묵       → 그때 돌아서 찾기   (지금 구현된 경로가 폴백으로 내려간다)
  ```

  **지금은 만들지 않는다.** 진동모터(`haptic_ok = False # 진동 모터 미장착`,
  09-05 에 펌웨어를 햅틱 없는 버전으로 원복)와 터치센서(`fb25c24` 로 꺼짐)가
  둘 다 없어서, 남는 것이 음성 안내뿐이다. **진동이 없으면 시각장애인이 손잡이를
  찾을 수단이 없다** — 소리는 어디서 나는지 헷갈리지만 진동은 손이 닿은 자리에서
  난다. 그 수단 없이 "잡아주세요"만 하는 것은 반쪽이다.

  **멘트는 이미 정해졌다: 기존 접근 질문(`MSG_APPROACH_QUESTION`,
  `assets/approach_question.wav` 10.6 s)을 그대로 재사용한다** (2026-09-10 사용자
  결정). **새 멘트도 새 녹음도 필요 없다.** 바로 앞 사람에게는 조금 길지만, 멘트를
  늘리지 않는 값이 그보다 크다.

  착수 조건: 진동모터 장착 + 펌웨어에 햅틱 복원. 터치센서까지 살아나면 "네" 응답
  없이 **잡은 것만으로** 넘어가게 만든다.

- **터치센서.** 이 관문의 참뜻은 "사용자가 손잡이를 잡고 있는가"다. 터치센서가 이상적
  신호이지만 `fb25c24`(09-05)에서 꺼져 있고 **고장이 위험한 쪽으로 난다** — 상향이
  끊기면 `user_contact` 는 규약상 항상 false 라 "아무도 안 잡았다 → 돌아도 된다"가
  된다. 살아나면 **덧댄다(이중 잠금)**, 대체하지 않는다.
- **로그 사유 오귀속(Minor, park).** `_on_wake_doa` 의 사유 체인에 시각 관문 분기가
  없어, **guard 거절 + 각도 10° 미만**이 겹치는 좁은 경우 사유가 "10도 미만"으로
  잘못 찍힌다. 로봇 동작은 두 경우 모두 "안 돎"으로 같아 안전 무관.
