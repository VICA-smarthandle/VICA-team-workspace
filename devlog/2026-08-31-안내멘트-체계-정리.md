# 2026-08-31 안내 멘트 체계 정리 — 첫 인사부터 홈 복귀까지

## 왜 정리하나

8/23(사람접근)부터 8/30(도착 후 대화)까지 멘트가 세 갈래 작업에서 따로
자랐다. 이 문서는 **로봇이 말하는 모든 고정 멘트를 사용자 여정 순서로**
한 곳에 모은 정본 색인이다. 문구 자체의 정본은 코드다 —
미션 `mission_logic.py` 의 `MSG_*` 상수, 음성 `replies.py`. 여기 문구와
코드가 다르면 **코드가 맞다** (캐시가 글자 일치로 동작하므로 문구 수정은
반드시 코드에서).

  같은 목소리 결이라 이중인격 없음
- 발화 주체 규칙: **상태를 아는 쪽이 말한다** — 도착·출발·E-stop 등은
  미션, 확인 질문·접수 신호는 음성. affirm/deny/wait/finish 의 reply 는
  빈 문자열(음성이 말하면 두 번 말하게 된다)

## 6. 홈 위치 저장 방식 — A안 확정 (2026-08-31)

**홈은 destinations.yaml 이 아니라 별도 `home.yaml`** (지도 폴더별 1개,
id `__home__`)로 관리한다. 근거:

1. **안전을 "거름"이 아니라 "부재"로 보장** — LLM 목적지 목록에 홈이
   아예 없으니 거름망 버그가 원천 불가능. `__home__` 은 UUID 가 아니라
   미션 게이트에서도 이중 차단. (E-stop reset 을 앱에서만 받는 것과 같은
   구조적 차단 사상)
2. destinations 로더의 UUID v4 강제 검증을 완화할 필요가 없다.
3. "지도당 홈 1개"가 파일 구조로 자동 보장.
4. 앱팀 홈 저장 기능(SaveHome srv·visited_ok 수명주기)이 이미 이 설계 —
   그대로 이어받는다.

재검토 조건: 홈이 여러 개가 되거나(층별 대기소) 음성으로 홈을 보낼
계획이 생길 때.

## 7. 미션 동작 원리 — 멘트 뒤의 상태기계

멘트는 전부 미션 상태기계(`mission_logic.py`)가 상태 전이 때 낸다.
시간은 전부 인자(now)로 받아 시험에서 시계를 주입한다.

### 상태 지도

```
IDLE ─ 확인 필요 ─▶ CONFIRMING ─ "그래" ─▶ NAVIGATING ─ 도착 ─▶ ASKING_NEXT
 │                  (30초 창)        │                        │
 │                                   ├ 실패 ▶ FAILED(재시도 2회) ├ wait ▶ WAITING
 ├ 사람 감지 ▶ APPROACHING ▶ AWAITING_USER                     │    │ "비카야" ▶ ASKING_NEXT
 │              ("네" ▶ TURNING ▶ 온보딩 ▶ IDLE)               │    └ 시간초과 ▶ RETURNING
 │                                                            ├ finish/침묵 ▶ RETURNING ▶ IDLE
 └ E-stop(어느 상태든) ▶ ESTOPPED ─ 관리자 reset ─▶ IDLE       └ navigate ▶ NAVIGATING
```

### 도착 후 대화의 핵심 장치 4개

1. **질문 태그** — ASKING_NEXT 진입 때 "이 질문은 대기형인가 종료형인가"
   (`_asking_is_finish`)를 함께 기억한다. 같은 "네"라도 restroom 질문 뒤엔
   대기, entrance 질문 뒤엔 종료가 되는 이유. **말의 뜻은 intent 가 아니라
   상태+질문 태그가 완성한다.**
2. **귀 홀드** — 무응답 시계는 `/vica/listen_state`(open/speech/closed/
   empty)를 보고 귀가 바쁘면 멈춘다. closed(전사 성공) 후엔 LLM 처리
   유예 6초, 닫힘 신호 유실 대비 상한 20초.
3. **무응답 사다리** — 못 알아들음(unknown/빈손)은 재질문 1회, 완전 침묵
   8초는 재질문 없이 떠나기 예고 → 3초 유예(끼어들면 산다) → 복귀.
4. **복귀 브레이크·그물** — RETURNING 중 "비카야"(브레이크: 취소 후 재개
   질문) 또는 wait/navigate 답 도착(그물: 조용히 취소 후 그 답을 즉시
   처리). 늦게 도착한 답이 로봇을 되돌리는 이중 안전망.

### 시계 일람

| 시계 | 값 | 기점 |
| --- | --- | --- |
| 확인 창 (CONFIRMING) | 30초 | 확인 질문 발화 |
| 도착 질문 응답 대기 | 8초 | **질문 재생 완료**(tts_done) — 재생 중은 안 센다 |
| 귀 홀드 LLM 유예 / 상한 | 6초 / 20초 | 전사 성공 / 귀 바쁨 시작 |
| 떠나기 예고 유예 | 3초 | 예고 발화 |
| 대기(WAITING) 상한 | 30분 | 대기 확정 (LLM 요청은 깎아서 수락) |
| 접근 질문 응답 대기 | 8초 | 질문 재생 완료 |
| 도착 dwell (대화 꺼짐일 때) | 2초 | 도착 |

### 노드 라우팅 규칙 (mission_manager_node)

들어온 intent 는 **미션의 현재 상태가 행선지를 정한다**:

1. RETURNING + wait/navigate → 복귀 그물 (조용한 브레이크 후 아래로)
2. 도착 후 대화 중(ASKING_*) → 전부 `on_arrival_answer` 로. **예외**:
   navigate 제안(need_confirm=True)은 대화를 닫고 일반 확인 흐름으로
   합류 — 제안 단계에서 출발하면 확인 질문 전에 달린다(8/30 실기).
3. cancel/pause/resume → 명령 경로 (취소는 되물어 확인)
4. affirm/deny → 접근 질문(AWAITING_USER) 답 경로
5. 그 외(navigate 등) → 일반 게이트 (UUID·공개여부·지도경계·Nav2 준비
   5중 검증 후에만 goal 생성)

앱 주행은 별도 서비스(RequestDestination)로 들어와 같은 게이트를 탄다 —
출처 구분(도착 후 대화 스킵)은 앱팀 상의 후 추가 예정. 홈 복귀는
`return_destination`(home.yaml)이 없으면 제자리 대기로 폴백하며, 복귀
실패도 완료로 친다(복귀는 안전 사건이 아니다).
