## 1. 2026-08-11 회차를 근거로 쓰지 않는 이유

그날 드라이버 가변저항이 0 %였다. `speed_ratio = knob_pct/100`이므로 teleop·Nav2가 무엇을
보내든 `clamp`로 0이 된다(`motor-knob-zero-blocks-all-motion` 참조).

로그만 보면 전형적인 costmap 교착으로 읽힌다. **전부 바퀴가 안 돈 결과다.**

| 지표 | 2026-08-11 | 2026-08-02 확정본 |
| --- | --- | --- |
| `No valid trajectories out of 419` | 954회 | 2회 |
| `Starting point in lethal space` | 16회 | 0회 |
| `Controller patience exceeded` | 60회 | — |
| `Passing new path` | 627회 | — |
| Spin 시도 | 30회 (29회가 `Collision Ahead`로 중단) | — |

연쇄는 이렇다.

```text
바퀴가 안 돎
 ├─ 장애물에서 못 벗어남          → ObstacleFootprint 1.00 (419개 궤적 전부 충돌)
 ├─ oscillation_reset_dist 못 채움 → Oscillation critic이 탈출 방향을 계속 거부
 ├─ 목표에 못 감                   → 재계획 폭증 (Passing new path 627회)
 └─ Spin 명령만 나가고 안 돎       → Collision Ahead - Exiting Spin 29회
```

**교훈**: 주행 실패를 Nav2·nvblox 설정 문제로 진단하기 전에 그 회차의 knob부터 확인한다.
로그·영상만으로는 "명령을 못 만든 것"과 "명령은 냈는데 바퀴가 안 된 것"이 구분되지 않는다.

2026-08-10 회차와의 비교도 성립하지 않는다. 그 세션은 `Received a goal`이 0건이라 주행
목표를 준 적이 없다(매핑용으로 보인다).

## 3. 설정에서 확인한 정적 사실

로그와 무관하게 성립하므로 knob 결함의 영향을 받지 않는다.

### 3.1 두 costmap의 레이어 구성이 다르다

정본: `vica_ros2_ws/src/vica_nav2/config/nav2_params.yaml`

```text
global_costmap (map frame, 1.0 Hz)                                  plugins :1107
├── static_layer      ← SLAM 지도.  지우기 없음 (영구)
├── obstacle_layer    ← LiDAR /scan. observation_persistence 0.5 s        :1138
└── inflation_layer   ← radius 0.55 (:1197), cost_scaling_factor 3.5
    ※ nvblox_layer 블록(:1102)은 있으나 plugins 목록에 없다 → 로드되지 않는다

local_costmap (odom frame, 5.0 Hz, rolling 6×6 m)                   plugins :747
├── voxel_layer       ← LiDAR /scan. observation_persistence 0.5 s         :831
├── nvblox_layer      ← 카메라 esdf slice                                  :742
└── inflation_layer   ← radius 0.55 (:1028), cost_scaling_factor 3.5
```

**global에는 nvblox가 없다.** 따라서 `Starting point in lethal space`는 nvblox로 설명되지
않는다. 그쪽은 static 지도 또는 LiDAR 또는 위치 추정 오차다.

### 3.2 지우는 속도가 레이어마다 60배 차이 난다

정본: `vica_ros2_ws/src/vica_nvblox_bringup/config/vica_nvblox_overrides.yaml`,
`isaac_ros-dev/src/isaac_ros_nvblox/nvblox_examples/nvblox_examples_bringup/config/nvblox/nvblox_base.yaml`

```text
projective_integrator_max_weight : 5.0    (nvblox_base.yaml:78)
tsdf_decay_factor                : 0.95   (overrides)
esdf_integrator_min_weight       : 0.1    (nvblox_base.yaml:95)
decay_tsdf_rate_hz               : 2.5    (overrides. 기본값은 5.0)
exclude_last_view_from_decay     : false  (overrides. 기본값 true에서 바꾼 것)

5.0 × 0.95ⁿ ≤ 0.1  →  n ≥ 76.3 tick  →  76.3 ÷ 2.5 Hz ≈ 30.5초
```

실질 소멸 시점을 정하는 것은 `tsdf_decayed_weight_threshold`(0.001)가 아니라
`esdf_integrator_min_weight`(0.1)다. ESDF가 weight 0.1 미만 복셀을 아예 보지 않는다
(`esdf_integrator.cu:115  return tsdf_voxel.weight >= min_weight`).

| 레이어 | 지나간 사람을 지우는 데 | 근거 |
| --- | --- | --- |
| voxel_layer / obstacle_layer (LiDAR) | **0.5초** | `observation_persistence: 0.5` |
| nvblox_layer (카메라) | **약 30.5초** | 위 계산 |

costmap은 레이어를 `updateWithMax`로 합치므로, LiDAR가 0.5초에 지워도 nvblox가 LETHAL을
유지하면 결과는 LETHAL이다. **[미검증]** 이 30.5초가 실제로 관측되는지는 §7 3단계에서
측정한다.

### 3.3 slice 밴드가 사람 전신을 바닥에 투영한다

```text
esdf_slice_min_height : 0.05
esdf_slice_max_height : 0.9     ← 사람 전신이 이 밴드에 들어온다
esdf_slice_height     : 0.10    ← 밴드 전체의 최소 거리가 0.10 m 평면에 투영된다
```

높이 0.9 m에 있는 것이 바닥 높이 장애물처럼 costmap에 찍힌다.

### 3.4 카메라가 자기 앞 높은 곳을 못 본다

`vica_description/urdf/VICA.xacro` 기준 기하다.

```text
카메라 높이 = 0.320 m,  전방 오프셋 = +0.287 m,  틸트 없음
D455 수직 FOV 58° (반각 29°, tan 0.554)
거리 d에서 보이는 높이 = 0.320 ± 0.554 d
```

로봇이 장애물 앞에서 멈추는 거리를 더한다. footprint 전방은 0.305이고(`nav2_params.yaml:608`
육각형 첫 꼭짓점) 여기에 `footprint_padding: 0.05`가 붙어 0.355다.

```text
0.305 (footprint 전방) + 0.05 (padding) + 0.55 (inflation) = 중심에서 0.905 m
카메라는 중심보다 0.287 앞  →  카메라~장애물 ≈ 0.62 m
0.320 ± 0.554 × 0.62        →  보이는 높이 0 ~ 0.66 m
```
**0.66~0.9 m 밴드가 사각지대**이고 사람의 가슴~머리가 그 대역이다.

즉 멈춘 자리에서는 그 높이의 유령을 카메라로 덮어쓸 수 없다. `exclude_last_view_from_decay`
를 false로 바꿔 decay 경로는 열어 두었으므로 **지금은 시간(30.5초)으로만 지워진다.**

### 3.5 planner와 controller가 253 밴드를 다르게 본다 — 우회 실패의 구조적 원인

`nav2_params.yaml:425-434` 주석이 두 구현의 디스어셈블 확인 결과를 기록해 두었다.

```text
dwb_critics  ObstacleFootprintCritic::pointCost
    cmp w1, #0xfe (254 LETHAL) / #0xff (255 UNKNOWN) → 예외
    0xfd(253 INSCRIBED) 비교가 없다               → 253을 통과시킨다

nav2_smac_planner  GridCollisionChecker::inCollision
    cmp w1, #0xfc (252 초과 = 253 이상)           → 충돌 (footprint 전체)
```

**253 밴드는 controller에게 합법이고 planner에게 금지다.** 그래서 이런 일이 생긴다.

```text
DWB가 footprint를 253 밴드에 넣으며 정상 주행
  → 그 자리에서 planner가 "Starting point in lethal space"
  → 부딪히지도 않았고 나갈 공간이 있는데 굳는다
```

활성 planner는 `GridBased` = `nav2_smac_planner/SmacPlannerLattice`(:1396)다.
`GridBasedAlt`(= Hybrid, :1289)는 `planner_plugins` 목록에 없어 로드되지 않는다.
`ObstacleFootprint.scale`은 0.15다(:506. 2026-08-02에 0.6을 시험했다가 되돌렸다).

**이것은 knob 결함과 무관한 코드 수준 사실이므로 2026-08-11 회차가 무효여도 그대로 남는다.**
2026-07-30 실측(bins36_people)도 있다 — 정지 지점의 로봇 중심 셀 값이 74~79(경사 안, 합법)
였고 중심이 99 이상인 샘플은 36개 중 0개였다.

**[미검증]** 이 비대칭이 이번 증상(주춤거림·우회 실패)에서 실제로 몇 번 발동하는지는
기준선 측정에서 `lethal space` 횟수로 센다.

## 4. 왜 파라미터 조정만으로는 닫히는가

`mapping_type: static_tsdf`는 **decay 손잡이가 하나뿐이다.** 벽·가구는 기억해야 하고 사람은
잊어야 하는데 같은 값이 둘을 함께 정한다.

- decay를 빠르게 → 사람은 빨리 지워지지만 벽·가구도 잊는다
- decay를 느리게 → 벽은 남지만 사람이 30초간 벽이 된다

`vica_nvblox_overrides.yaml`이 이미 이 문장을 남겨 두었다.

> 하나의 decay로 둘을 만족시킬 수 없다는 것이 요점이다.

`dynamic` 모드가 두 mapper를 나눠 각자 decay를 갖지만 **3회 시도해 모두 실패한 이력이
있다**(같은 파일 주석 47~101행). 그래서 static_tsdf + `exclude_last_view_from_decay: false`
조합으로 되돌아온 상태다.

## 5. YOLO 비전 도입 검토

### 5.0 역할 분담 — 두 시스템은 별개다

2026-08-12 사용자 확정이다.

| 시스템 | 용도 | 대상 |
| --- | --- | --- |
| **YOLO** | **주행 안내** | 별개 기능. 장애물 회피 경로에 넣지 않는다 |
| **nvblox** | **장애물 감지** | 사람을 포함한 동적 장애물 |

**따라서 동적 장애물 정지 문제는 YOLO 도입과 무관하게 nvblox 쪽에서 풀어야 한다.**
"YOLO를 붙이면 사람 회피가 좋아진다"는 경로가 아니다. 두 시스템의 유일한 접점은
**같은 GPU를 쓴다**는 것뿐이고, 그래서 §5.4의 부하 확인이 필요하다.

아래 5.1~5.3은 그 전제 위에서 읽는다. `human_*` 모드는 **선택지로만** 남겨 둔 것이고,
채택하려면 mask 공급자가 따로 필요하다(§5.2).

### 5.1 nvblox가 사람을 분리하는 길은 둘이고, 요구 조건이 다르다

`isaac_ros_nvblox/nvblox_ros/src/lib/mapper_initialization.cpp:71-80`이 받는 값은 5개다.

| mapping_type | 성격 |
| --- | --- |
| `static_tsdf` | 현재값. mapper 하나 |
| `static_occupancy` | 점유 격자 방식 |
| `dynamic` | 정적/동적 분리. **3회 실패 이력** |
| `human_with_static_tsdf` | **정적 + 사람 분리.** 사람은 별도 mapper |
| `human_with_static_occupancy` | 위의 occupancy 판 |

`human_*` 모드는 사람을 **별도 mapper**로 관리하므로 §4의 "손잡이가 하나뿐" 문제가 구조적으로
풀린다. 벽은 느리게, 사람은 빠르게 잊게 만들 수 있다.

### 5.2 그러려면 mask가 필요하다

`nvblox_node.cpp:242`가 조건을 명시한다.

```cpp
// We subscribe to the masks if we enable segmentation
// We call depth/color+mask queue if segmentation is enabled.
```

nvblox가 요구하는 것은 **픽셀 단위 segmentation mask 이미지**다. 바운딩 박스가 아니다.

| 후보 | 출력 | nvblox 직접 연결 |
| --- | --- | --- |
| YOLOv8 (detection) | 바운딩 박스 | **불가.** 박스 → mask 변환 노드가 따로 필요하다 |
| YOLOv8-seg | 인스턴스 mask | 가능 [미검증] |
| PeopleSemSegNet (Isaac ROS 기본 경로) | 시맨틱 mask | nvblox 예제가 쓰는 조합 |

**"YOLO를 붙인다"는 말은 세 갈래로 갈린다.** 어느 것을 쓰느냐에 따라 작업량과 GPU 부하가
다르므로 도입 전에 갈래를 먼저 정해야 한다.

### 5.3 현재 워크스페이스에 없는 것

```bash
# 2026-08-12 확인: 둘 다 검색 결과 0건
find ~/workspaces/isaac_ros-dev/src -maxdepth 2 -iname "*yolo*"
find ~/workspaces/isaac_ros-dev/src -maxdepth 3 -iname "*human*" -o -iname "*people*"
```

`isaac_ros_nvblox`, `isaac_ros_common`, `realsense-ros`, `vica_nvblox_bringup`,
`vica_visual_slam` 다섯 개뿐이다. 객체 감지·분할 패키지는 설치되어 있지 않다.

### 5.4 도입 전에 답해야 할 것

GPU 경합 이력이 있다(`devlog/2026-07-30-gpu-nvblox-stt-contention.md`). 세그멘테이션 모델은
nvblox·STT와 같은 GPU를 쓴다.

| 질문 | 왜 필요한가 |
| --- | --- |
| 어느 모델인가 (YOLOv8-seg / PeopleSemSegNet) | 작업량·정확도·라이선스가 다르다 |
| GPU 여유가 있는가 | 2026-08-02에 `missed its desired rate`가 최대 골칫거리였다 |
| mask 없이 파라미터로 얼마나 개선되는가 | **기준선이 없으면 도입 효과를 측정할 수 없다** |

**순서는 사용자가 확정했다(2026-08-12).**

```text
1. 동적 장애물 회피·우회를 잡는다   ← 지금 여기. §7·§8
2. 그 뒤 YOLO 기반 객체 인지를 얹는다
```

## 7. 원인을 가르는 관찰 — 젯슨에서 바로 쓸 것

### 0단계 — 주행 전 30초 (필수)

knob이 0이면 그날 데이터는 전부 못 쓴다. 2026-08-11이 그랬다.

**knob은 토픽으로 나오지 않는다.** motor node가 발행하는 토픽은 `/motor/can_ok` 하나뿐이고,
knob 값은 콘솔 로그로만 보인다(`mdrobot_can_keyboard_knob_node.py:556`).

```bash
# ① motor node를 띄운 터미널의 로그. 48 % 근처여야 정상이다
#    knob1= 48%  limit=(0.26m/s,0.40rad/s)  cmd=(+0.00,+0.00)  out=(+0.00,+0.00)
#    knob1=  0%  limit=(0.00m/s,0.00rad/s)  ← 이 상태면 그날 데이터는 못 쓴다

# ② CAN에서 직접: 701 프레임의 d[6]이 knob 값
candump can1 | grep -m3 " 701 "
#   can1  701  [8]  F1 00 58 18 05 04 00 00
#                                    ↑ d[6]=0x00 → knob 0 %
```

### 1단계 — 기록을 켜고 주행한다

`/cmd_vel_safe`(명령)와 `/wheel/odom`(실제 이동)을 **둘 다** 넣는다. 이 둘이 있어야
"명령을 못 만든 것"과 "바퀴가 안 된 것"이 구분된다.

```bash
ros2 bag record -o base_$(date +%H%M) \
  /cmd_vel_req /cmd_vel_safe /wheel/odom /odom \
  /local_costmap/costmap /global_costmap/costmap \
  /nvblox_node/static_map_slice /plan /scan \
  /behavior_tree_log /tf /tf_static
```

### 2단계 — 정지 중 무엇이 도는지 본다

```bash
# 복구가 실제로 도는가
ros2 topic echo /behavior_tree_log | grep -iE "Wait|Spin|Clearing|RoundRobin"

# 명령은 나가는가 (0이 아닌 값이 보이면 Nav2는 살아 있다)
ros2 topic echo /cmd_vel_safe --once
```

| 관찰 | 가리키는 곳 |
| --- | --- |
| `/cmd_vel_safe`가 0이 아닌데 로봇이 안 움직임 | **구동계.** knob·CAN·드라이버 전원 |
| `/cmd_vel_safe`가 계속 0 | Nav2가 명령을 못 만듦 → 3·4단계로 |
| 좌우로 조금씩 회전 (±17.2°) | BT 복구가 도는 중 |
| 미동 없음 | costmap이 계속 막혀 있음 |

### 3단계 — nvblox가 사람을 언제 지우는지 잰다 (§3.2의 30.5초 검증)

로봇을 **정지**시킨 채 카메라 앞을 사람이 지나가게 하고, slice에서 사라지는 시각을 잰다.
주행이 필요 없으므로 knob이 고쳐지기 전에도 할 수 있다.

```bash
# 슬라이스가 오고 있는지부터
ros2 topic hz /nvblox_node/static_map_slice

# 사람이 떠난 시각을 기록하고, 그 지점 값이 free로 바뀔 때까지 센다
ros2 topic echo /nvblox_node/static_map_slice --field header.stamp
```

계산값 30.5초와 비교한다. **크게 다르면 §3.2의 전제가 틀린 것이므로 A 후보를 내린다.**
