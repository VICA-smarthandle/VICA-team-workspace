## 1. 복귀 기계는 이미 있었고 갈 곳만 없었다

이 작업이 작았던 이유다. 사람 접근 기능(8/23 설계)을 만들 때 "거절당하면 대기
위치로 돌아간다"를 함께 만들어 뒀다.

```python
mission_logic.py:543   return_destination: Optional[Destination] = None
mission_logic.py:1166  self.state = State.RETURNING
mission_logic.py:1173  if self.return_destination is not None:
                           actions.append(Navigate(self.return_destination))
```

그런데 `mission_manager_node.py` 가 이 값을 **한 번도 넘기지 않았다.** launch
인자도 없었다. 그래서 항상 `None` 이었고, 코드 주석이 그 상태를 이렇게 적어 뒀다.

> 대기 위치 좌표는 아직 **[미정]** 이라 없을 수 있고, 없으면 제자리에서 접근만
> 끝낸다 — 상태만 지나가고 다음 tick 에 IDLE 로 내려간다.

**주차장은 지었는데 주소를 안 적어 둔 상태**였다. `home.yaml` 을 읽어 그 자리에
넣었고, **복귀 주행 코드는 한 줄도 새로 쓰지 않았다.**

## 2. 홈을 목적지에 넣지 않은 이유

`destinations.yaml` 에 `is_home: true` 플래그를 하나 넣는 편이 더 간단해 보인다.
그렇게 하지 않았다.

**거르는 방식은 언젠가 새는 방식이다.** 홈을 목적지 목록에 넣으면 "홈이면 사용자
요청을 거른다"를 **모든 진입점마다** 넣어야 한다 — 음성 경로, 앱 경로, 재시도
경로, 일시정지 복귀 경로. 한 곳만 빠뜨려도 사용자가 로봇을 홈으로 보낼 수 있게
되고, **그 실수는 예외도 경고도 내지 않는다.**

이 프로젝트에 같은 사고가 이미 있었다 — 앱 목적지 요청이 게이트를 우회해
**음성만 위치 검증을 받고 앱은 안 받았다**
(`devlog/2026-07-31-home-return-implementation.md` §4.3).

그래서 파일을 나눴다.

```
~/vica_data/destinations/<map_id>/destinations.yaml   목적지 (기존)
~/vica_data/destinations/<map_id>/home.yaml           홈    (신규)
```

**파일이 하나라서 "지도당 1개"가 저절로 지켜진다.** 개수를 세는 코드가 없다.
경로는 운영 매뉴얼의 `home_yaml` 인자(`docs/vica_robot_bringup_manual.md:540`)가
이미 정해 둔 것을 그대로 따랐다 — 문서가 코드보다 먼저 있었던 셈이다.

## 3. `visited_ok` 가 이 설계의 핵심

`home.yaml` 에 담기는 값은 이렇다.

```yaml
map_id: vica_map_0630
pose: {frame_id: map, x: -5.83, y: -0.04, yaw: 90.0}
source: robot_standing      # robot_standing | map_pick
score: 84.2                 # map_pick 이면 0
visited_ok: false           # ★
saved_at: "2026-08-26T14:03:00"
label: "충전 스테이션 앞"
```

나머지 필드는 "어떻게 정했나"의 기록이고, **`visited_ok` 하나만이 "실제로 갈 수
있는 자리임을 확인했나"** 를 답한다.

### 새로 저장한 홈은 항상 `false` 다

로봇을 실제로 세워놓고 잡았어도 그렇다. 그 자리에 서 있다는 것은 **"지금 여기가
지도와 맞다"만 말하고, "Nav2 가 거기까지 경로를 그릴 수 있다"는 말하지 않는다.**
좌표를 정하는 일과 도달할 수 있다는 사실은 별개다.

`test_home_storage.py::test_new_home_is_never_visited_even_when_robot_was_standing_there`
가 이것을 박제한다.

### 실패도 기록한다

'홈으로 가보기'가 실패하면 `false` 로 되돌린다. **한 번 확인된 홈도 가구가
놓이거나 문이 잠기면 못 가는 자리가 된다** — 좌표는 그대로인데 도달할 수 없다.

## 4. 지도가 바뀌면 — 세 경우 중 하나만 코드가 필요했다

| 상황 | 결과 | 어떻게 |
| --- | --- | --- |
| 새 이름으로 저장 | 홈이 없는 새 지도 | 이름에 날짜(`%m%d`)가 붙어 **새 map_id** 라 폴더가 다르다 |
| 지도 삭제 | 홈도 함께 사라짐 | `map_list_node` 가 지도별 폴더를 `shutil.rmtree` 한다 |
| **같은 map_id 로 파일만 교체** | **재확인 요구** | `invalidate_if_map_is_newer` |

셋째만 남는다. 같은 날 같은 이름으로 다시 저장하거나 젯슨에서 파일을 직접 바꾸면
그렇게 되고, 그때 **좌표는 그대로인데 벽 위치가 옮겨져 홈이 벽 속에 들어갈 수
있다.**

지도 파일의 mtime 과 `saved_at` 을 비교해 판정한다. 홈에 새 필드를 더하지 않고도
이 경우를 잡을 수 있어서다. 노드가 뜰 때 한 번만 검사하고, 시각을 읽을 수 없으면
아무것도 하지 않는다 — 확신 없이 확인 상태를 내리면 관리자가 이유 없이 다시
확인하게 된다.

**좌표는 지우지 않는다.** 같은 공간을 다시 그린 것이면 홈 자리도 대체로 그대로이고,
지워 버리면 관리자가 처음부터 다시 잡아야 한다.

## 5. 관리자만 홈으로 보낼 수 있게 — 문을 없앴다

권한을 검사해서 막는 것이 아니라 **사용자 쪽에 문이 없게** 만들었다.

```
사용자(음성)  말 → LLM → /vica/intent 토픽 → Mission
                                └ 목적지를 UUID 로 지목한다

관리자(앱)    버튼 → /vica/mission/return_home → Mission
                     └ UUID 없이 "홈으로" 하나만 보낸다
```

홈은 목적지 카탈로그에 없어 **UUID 가 없다.** 사용자 쪽 길로는 **지목할 대상
자체가 존재하지 않는다.** 홈에 붙인 id 도 일부러 UUID 형식이 아닌 `__home__` 이라,
혹시 이 id 로 목적지 요청을 해도 UUID 검증에서 먼저 걸린다.

**LLM 노드는 토픽만 발행하고 서비스 클라이언트가 없다.** 새 intent 를 만들지 않는
한 음성으로는 홈에 보낼 수 없다.

### 안내 주행 중에는 거부한다

사용자가 **핸들을 잡고 로봇을 따라 걷는 중**이다. 로봇이 홈으로 방향을 틀면
**사용자는 자기가 어디로 끌려가는지 모른다** — 눈으로 확인할 수 없고 로봇이
목적지 변경을 말해 주지도 않는다.

대신 두 걸음으로 가능하다: `[주행 취소]` → 로봇이 안내 종료를 말함 →
`[홈으로 복귀]`. **막는 것이 아니라 사용자에게 알린 뒤 하게** 만든 것이다.

### 복귀 종류를 플래그로 가른다

접근 뒤 복귀와 관리자 홈 복귀는 **가는 곳이 같아서** `State.RETURNING` 을 함께
쓴다. 하지만 **끝낼 때 할 일이 다르다.**

접근 뒤 복귀는 방금 거절한 사람에게 다시 다가가지 않도록 재접근 억제를 걸어야
하는데, 관리자 홈 복귀에는 억제할 사람이 없다. 구분하지 않으면 **마지막에
만났던 track_id 가 걸려 다음 사람을 이유 없이 무시한다.**

### `[GAP]` — "관리자만"의 한계

앱 로그인은 **ROS 서비스에 신원을 전달하지 않는다.** 젯슨 터미널에서
`ros2 service call` 하면 누구든 부를 수 있다. `/safety_reset` 과 똑같은 상태다.

**사용자(음성)로부터는 구조로 막히고, 터미널 접근자로부터는 안 막힌다.**
지금 필요한 분리는 앞쪽이라 이대로 두고, 인증이 생기면 같이 붙는다.

## 6. 주행 실패 알림 — 코드가 없었던 게 아니라 사유가 버려졌다

원격 주행 화면에서 주행이 실패하면 목적지가 그냥 사라져 원인을 알 수 없었다.
조사해 보니 Mission Manager 는 **제대로 내고 있었다.**

```
Mission Manager → /vica_goal_event  {event, name, reason}   ← 정상
                        ↓
              vica_status_app_node.handle_goal_event
                        ↓  current_goal 을 비우기만 하고 reason 을 버린다  ← 여기
              /robot_status  {current_goal: ""}
                        ↓
                      앱: 목적지가 그냥 사라짐
```

그리고 **앱은 `/vica_goal_event` 를 구독조차 하지 않았다.**

### 고친 방법 — 앱이 직접 구독

`/robot_status` 스키마는 **그대로 두었다.** 앱이 `/vica_goal_event` 를 직접 본다.
`/robot/health`·`/robot/events` 를 직접 구독하는 것과 같은 방식이며,
`vica_architecture.md` 10.3절의 "세부 결함 표시는 앱이 직접 구독해 담당하며 이
노드를 거치지 않는다"와 같은 방향이다.

### 성공에는 팝업을 띄우지 않는다

도착은 로봇이 사용자에게 말로 알리고 앱 상태에도 드러난다. 팝업까지 띄우면
관리자가 **팝업 닫기에 익숙해지고**, 그러면 정작 중요한 실패 팝업도 읽지 않고
닫는다.

| 이벤트 | 팝업 |
| --- | --- |
| `goal_failed` · `goal_rejected` · `goal_canceled` | 뜬다 |
| `return_home_failed` · `return_home_canceled` | 뜬다 |
| `goal_succeeded` · `goal_sent` · `goal_accepted` | 안 뜬다 |
| `goal_paused` | 안 뜬다 ('다시 출발' 버튼이 이미 보인다) |

홈 복귀 이벤트를 따로 낸 이유는 같은 이름을 쓰면 앱이 **"화장실 주행이
실패했다"처럼 잘못 표시하기** 때문이다.

### 문구에 다음 할 일을 적는다

사유 문자열만 보여주면 관리자가 **무엇을 해야 할지 모른다.**

```
주행 실패

남자 화장실(으)로 가는 도중 주행이 실패했습니다.
경로가 막혔거나 로봇이 자기 위치를 잃었을 수 있습니다.
로봇 주변을 확인하고 다시 요청하세요.
위치가 어긋난 것 같으면 초기 위치를 다시 잡으세요.

사유: Nav2 task failed
```

팝업과 별개로 알림 목록에도 남는다. 팝업은 그 자리에서 닫히지만 목록은 나중에
되짚을 수 있어야 한다.

## 7. 앱 홈 카드 — 두 방식을 한 흐름으로

지정 방식이 둘이고 **서로 다른 축에서 강하다.**

| | 실제 자리에서 | 지도에서 찍기 |
| --- | --- | --- |
| 위치 | AMCL 을 믿어야 한다 — 복도에서 앞뒤로 밀려 있어도 모른다 | **사람 의도 그대로** |
| 방향 | **정확하다** | 90도 단위 4칸 |
| 채점 | `PoseCheck` 로 점수가 나온다 | 없다 (로봇이 거기 없다) |
| 저장값 | **채점이 바로잡은 자세** | 찍은 좌표 그대로 |

**복도 맹점은 오히려 "실제 자리에서"의 약점이다.** 8/25 실기에서 복도 방향으로
1.5~2.9 m 를 틀려도 73~82점으로 통과했다. 로봇을 실제로 세워도 그 순간 AMCL 이
밀려 있으면 밀린 값이 저장된다.

그래서 경쟁이 아니라 한 흐름으로 잇는다.

```
① 지도에서 찍는다        위치를 의도대로. 방향은 대충
        ↓  (저장 · visited_ok=false)
② [ 홈으로 가보기 ]      실제로 보낸다 — 도달 가능이 실증된다
        ↓  (성공하면 visited_ok=true)
③ 어긋났으면 조작판으로 미세조정
        ↓
④ [ 지금 선 자리로 갱신 ]  채점 + 정밀 확정
```

②는 새 기능이 아니다. **관리자 홈 복귀와 똑같은 서비스**를 부른다.

### Nav2 주행이 필요 없다

"실제 자리에서 잡는다"가 로봇을 Nav2 로 보내야 한다는 뜻이 아니다. **AMCL 은
로봇이 어떻게 움직이든 따라온다** — 바퀴가 굴러가면 엔코더가 세고 라이다가
보정한다. 차 안의 내비게이션과 같아서, 안내를 켜든 안 켜든 차가 움직이면 현재
위치는 갱신된다.

**홈 카드 안에 '끌고 다니기' 조작판을 넣었다.** 지도 모드에 있던 것과 같은
위젯이고 `/cmd_vel_req` → Safety → motor 경로를 그대로 쓴다. Nav2 를 켜는 이유는
주행이 아니라 `/map` 을 얻어 채점하기 위해서다.

### "아직 가 본 적이 없습니다"를 화면에 남긴다

지도에서 찍기만 하고 확인을 안 했다는 사실이 **보여야** 한다. 안 보이면 관리자는
다 된 줄 알고, **실제 안내가 끝난 뒤에야 로봇이 엉뚱한 데로 가는 것을 본다.**

## 8. 음성 파트가 이어받을 것

**로봇은 홈으로 갈 수 있지만 스스로 가지는 않는다.** 지금은 관리자가 버튼을
눌러야 간다. 사용자와 대화해서 "안내를 종료합니다" 하고 스스로 돌아가는 부분이
음성 파트의 몫이다. **복귀를 실행하는 코드는 이미 있으니, 만들 것은 언제 그것을
부를지 정하는 대화다.**

### 흐름

```
ARRIVED → ASKING_NEXT   "다음 목적지로 안내해드릴까요, 대기를 원하시나요?"
            ├ 다음 목적지 → CONFIRMING → NAVIGATING
            ├ 대기 → ASKING_WAIT_TIME → WAITING
            ├ 종료 → RETURNING (구현됨)
            └ 무응답 → 1회 재질문 → 또 없으면 RETURNING
```

### 새 상태 셋

`ASKING_NEXT`, `ASKING_WAIT_TIME`, `WAITING`.

**새로 발명하는 구조가 아니다.** 사람 접근의 `AWAITING_USER` 가 정확히 같은
모양이다 — 질문을 던지고, **재생이 끝난 시점부터** 시한을 세고, 답이 오면 갈래를
만든다(`on_approach_question_spoken` / `on_approach_answer`).

### 새 intent 둘

| intent | 알아들을 말 | 담을 값 |
| --- | --- | --- |
| `wait` | "기다려", "대기해줘", "20분만" | `wait_minutes` (없을 수 있음) |
| `finish` | "이제 됐어", "안내 끝", "그만할래" | — |

`cancel` 과 `finish` 를 나눈 이유: 둘 다 "그만"이지만 **일어나는 일이 다르다.**
`cancel` 은 주행 중간에 "이 목적지 안 갈래"이고 오인식하면 안내가 끊기므로
되묻는다. `finish` 는 도착 후 "오늘 안내 다 끝났어"이고 그 뒤 **홈으로 복귀**한다.

시간 표현은 LLM 이 뽑되 **Mission 이 상한(30분)을 강제한다.** LLM 이 "300분"을
뽑아도 30으로 깎는다.

### 확정된 규칙

1. **대기 중에는 사람 접근 기능을 끈다.** 지금 사람 접근은 `IDLE` 에서 사람이
   보이면 다가간다. 대기를 `IDLE` 로 구현하면 **기다리라고 해놓고 지나가는 사람을
   쫓아간다.** `WAITING` 을 별도 상태로 두는 것은 코드 정리 취향이 아니라 **안전
   요구사항**이다.

2. **대기 안내에 웨이크워드를 반드시 말한다.**

   ```
   "20분 대기하겠습니다. 돌아오시면 '비카야'라고 말씀해 주세요."
    └── 확정 시간              └── 반드시 포함 ★
   ```

   시간만 말하고 끝내면 사용자가 돌아와 로봇 앞에 서 있는데도 안내가 다시
   시작되지 않고, **시각장애인은 무엇을 해야 할지 알 방법이 없다.**

3. **무응답은 둘 다 1회 재질문 후 홈 복귀.** 대기 시간을 못 들었을 때 기본값으로
   기다리지 않는다 — **확인되지 않은 약속으로 로봇을 묶어 두지 않는다.**
   "대기"라고 말한 뒤 답이 없다는 것은 이미 자리를 떴다는 신호일 가능성이 높고,
   그 상태로 복도에 20분 서 있으면 **아무에게도 쓸모가 없으면서 통로만 막는다.**

4. **대기 중 로봇은 도착한 자리에 그대로 선다.** 옆으로 비키면 **사용자가 로봇을
   못 찾는다.**

5. **복귀 감지는 웨이크워드로.** 핸들 터치센서는 상향 통신이 없어 불가능하고,
   사람 탐지는 지나가는 사람과 구별 못 한다(복도에서 30분이면 수십 명이 지나간다).

6. **홈이 없어도 서비스가 멈추면 안 된다.** `return_destination` 이 `None` 이면
   복귀 갈래가 제자리 대기로 바뀔 뿐 안내는 그대로 동작한다.

## 11. 내일 실기에서 확인할 것

- 홈을 **두 방식으로 각각 잡아 비교** — 지도에서 찍은 것과 세워놓고 잡은 것이
  실제로 얼마나 차이 나는지. **복도 맹점의 크기가 여기서 드러난다**
- 홈 좌표로 **3회 왕복**해 도착 산포를 잰다 — 8/25 기준선은 축 39 cm
- 안내 주행 중 홈 복귀 버튼이 **잠기는지**
- 홈 복귀 중 **E-stop → 해제** 시 스스로 다시 출발하지 않는지
- 사람 접근을 거절당했을 때 **제자리가 아니라 홈으로** 가는지
- **주행을 일부러 실패시켜** 원격 주행 화면에 팝업이 뜨는지
- 같은 map_id 로 지도를 다시 저장했을 때 **"아직 가 본 적이 없습니다"가
  되살아나는지**
