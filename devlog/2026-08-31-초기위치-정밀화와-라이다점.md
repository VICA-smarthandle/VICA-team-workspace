## 2. 초기 위치는 왜 부정확했나 — 원인이 둘이었다

증상: 앱에서 초기 위치를 잡으면 되긴 되는데 **몇 십 cm 씩 어긋난다.**

### 원인 A — 격자가 성겼다

탐색이 2단계였다.

```python
FINE_XY_STEP = 0.025        # 2.5 cm 간격
FINE_YAW_STEP = 1도
```

**2.5 cm 간격으로만 답을 고르니 답도 2.5 cm 단위로 튄다.** 밀리미터 눈금 없이
2.5 cm 눈금만 그은 자로 길이를 재는 것과 같다.

### 원인 B — 이쪽이 더 컸다. 공분산을 너무 좁게 신고했다

초기 자세를 AMCL 에 넘길 때 **"내 말이 얼마나 확실한지"** 를 함께 보낸다.
그게 공분산이다.

우리 값이 `0.1 m` 였다. **"이 자세는 10 cm 안에 확실히 있다"** 고 우긴 셈이다.
RViz 의 기본값은 `0.25 m` — 분산으로 치면 우리가 **6배 좁게** 신고하고 있었다.

좁게 신고하면 AMCL 은 입자를 그 좁은 범위에만 뿌린다.
**로봇이 스스로 고칠 여지를 우리가 빼앗은 것이다.**

### RViz 는 매칭을 아예 안 한다

여기서 중요한 사실을 확인했다.

> **RViz 의 `2D Pose Estimate` 는 스캔 매칭을 하지 않는다.** 사람이 찍은 좌표를
> 공분산과 함께 `/initialpose` 로 그냥 던진다. 정확도는 전부 **AMCL 이 입자를
> 퍼뜨려 스스로 찾아내는 데서** 나온다.

그런데 우리는 매칭까지 해 놓고 **입자 퍼뜨릴 자리를 좁혀 버렸다.**
잘하려다 오히려 RViz 보다 불리해진 구조였다.

### 복도 맹점 — 점수가 못 보는 축이 있다

2026-08-25 문서 3절에 이미 적혀 있던 것이다.

```
복도를 가로질러 0.5 m 어긋남  ->  60% 미만   확 떨어진다
복도를 따라   1.0 m 어긋남  ->  15%p 안     거의 그대로
```

양옆 벽은 앞뒤에 대해 아무 말도 하지 않는다. **점수가 80% 라고 앞뒤가 맞다는
뜻이 아니다.** 그래서 공분산을 넓히는 일이 더 중요했다 — 점수가 못 보는 축은
AMCL 이 달리면서 봐야 하고, 그러려면 입자가 그 방향으로 퍼져 있어야 한다.

## 3. 3단계 탐색 + 포물선 보간

### 비유 — 산 정상 찾기

| 단계 | 하는 일 | 비유 |
| --- | --- | --- |
| **거친 훑기** | ±50 cm 를 10 cm 간격, 각도 5도 간격 | 헬기로 넓게 내려다본다 |
| **후보 고르기** | 상위 10곳을 **서로 떨어뜨려** 뽑는다 | 봉우리 10개를 고른다 |
| **중간 훑기** | 후보마다 ±6 cm 를 1.5 cm 간격 | 각 봉우리를 걸어 올라가 본다 |
| **정밀 훑기** | 우승자 주변 ±1.5 cm 를 3 mm 간격 | 정상 주변을 기어 다닌다 |
| **포물선 보간** | 격자 사이 진짜 꼭대기를 계산 | 세 점을 잇는 곡선으로 꼭대기를 짚는다 |

```python
COARSE_XY_RADIUS = 0.5     COARSE_XY_STEP = 0.1      COARSE_YAW_STEP = 5도
TOP_K = 10                 PEAK_MIN_XY = 0.15        PEAK_MIN_YAW = 10도
MID_XY_RADIUS = 0.06       MID_XY_STEP = 0.015       MID_YAW_STEP = 0.5도
FINE_XY_RADIUS = 0.015     FINE_XY_STEP = 0.003      FINE_YAW_STEP = 0.1도
```

### 후보를 고를 때 같은 봉우리를 세지 않는다 — `_pick_peaks`

점수 상위 10개를 그냥 뽑으면 **전부 같은 봉우리의 이웃 칸**이 뽑힌다.
한 산에서 열 명을 뽑는 셈이라 후보를 나눈 의미가 없다.

`PEAK_MIN_XY = 0.15` · `PEAK_MIN_YAW = 10도` — 이미 뽑힌 후보와 이만큼 떨어져
있어야 새 후보로 센다. **위치가 같아도 각도가 다르면 다른 후보다.** 복도에서
0도와 180도를 둘 다 살려 두기 위해 필요하다.

### 포물선 보간 — 격자보다 정밀해지는 이유

3 mm 격자면 **3 mm 안쪽은 원래 볼 수 없다.**
왼쪽·가운데·오른쪽 세 점수를 곡선으로 이으면 진짜 꼭대기가 어디인지 나온다.

```python
got_x   += _refine_axis(cube[yaw_i, :, y_i], x_i, FINE_XY_STEP)
got_y   += _refine_axis(cube[yaw_i, x_i, :], y_i, FINE_XY_STEP)
got_yaw += _refine_axis(cube[:, x_i, y_i],  yaw_i, FINE_YAW_STEP)
```

**안전장치를 달았다.** 보간한 자세를 다시 채점해서 **원래보다 점수가 낮으면
격자 값으로 되돌린다.** 보간은 봉우리가 매끄럽다는 가정 위에 서 있는데, 가구가
많은 방에서는 그 가정이 깨질 수 있다.

```python
refined = score_pose(...)
if refined >= score:  score = refined
else:                 # 격자 값으로 복귀
```

가운데가 최고점이 아니면 `_parabola_offset` 은 애초에 0을 돌려준다.

## 4. 공분산을 RViz 값으로 넓혔다

```python
self.declare_parameter('position_sigma_m', 0.25)   # 0.1 이었다
self.declare_parameter('yaw_sigma_deg', 10.0)      # 3.0 이었다
```

`covariance[0]` · `[7]` · `[35]` 에 제곱해서 넣는다(x · y · yaw).

**주의 — 이건 "정확도를 낮췄다"가 아니다.** 자세 자체는 3절 때문에 더 정확해졌고,
공분산은 *"이 정도 오차는 있을 수 있으니 알아서 다듬어라"* 라는 여지다.
**자세는 정밀하게, 신고는 겸손하게.**

launch 파라미터로 열려 있으므로 실기에서 되돌리기 쉽다.

## 5. 라이다 점을 앱 지도에 겹친다

### 왜 앱이 직접 못 하나 — 닭과 달걀

앱이 `/scan` 을 받아 지도 위에 그리려면 **각 빔을 지도 좌표로 옮겨야** 한다.
그러려면 **로봇이 지금 어디 있는지** 를 알아야 한다.

그런데 그걸 정하려는 중이다. **답을 알아야 그림을 그리고, 그림을 봐야 답을
고를 수 있다.**

서버는 이미 알고 있다. 점수를 매기면서 **모든 빔의 지도 좌표를 구해 놓는다.**
그래서 그걸 응답에 실어 보내기로 했다.

```
PoseCheck.srv    float32[] hit_x    float32[] hit_y
PoseCommit.srv   float32[] hit_x    float32[] hit_y
```

`beam_hits()` 는 채점 함수 `_score_translations` 와 **같은 순서로** 변환한다.
따로 구현하면 언젠가 어긋난다.

### RViz 와 같은 방식 — 한 장만

RViz 에서도 처음부터 점이 보이지는 않는다. 한 번 자세를 잡으면 **그 자세 기준으로**
점이 뜬다. 똑같이 했다.

- **확인 버튼을 누른 그 순간의 한 장.** 실시간 갱신이 아니다
- 확정 뒤에도 남는다 — 그때는 AMCL 이 받은 자세 기준
- 화면을 다시 열면 지운다

### 색과 크기

```dart
static const Color _coral = Color(0xFFE06055);   // 산호빛 붉은색
canvas.drawCircle(point, 1.6, paint);            // alpha 0.85
```

지도 배경이 **흰색과 검은색**뿐이라 완전한 빨강은 눈이 아프다. 단색 하나로 간다 —
거리별로 색을 나누면 "맞았나 틀렸나" 라는 원래 목적이 흐려진다.

**마커보다 아래 레이어**에 그린다. 점이 홈·목적지 마커를 덮으면 안 된다.
