## 2. 도착 정렬

### 2.1 도착축 4개가 헌팅을 만든 기작 (run41)

`planner tolerance 0.05 · PoseProgressChecker · rotate_to_heading_angular_vel 0.5 ·
max_angular_accel 2.0`. bag 을 0.5 s 간격으로 풀어 보면:

```
409호  d=0.18~0.30 m 에서  +18.6 → −18.1 → +18.8 → −19.2 → +16.1 → −17.6 °  반복
테스트1 d=0.18~0.20 m(반경 안)에서도 ±17~21° 반복, 54.8 s 뒤에야 성공
명령 w 와 odom w 가 0.3~0.5 s 어긋남(모터 응답 지연)
```

- RPP `rotateToHeading` 은 `sqrt(2·a·θ)` 로 제동한다. a 2.0·상한 0.5 이면 θ < 3.6° 에서야
  감속이 시작되고, 지연 0.3~0.5 s × 0.5 rad/s = 9~14° 가 더해져 허용 14.3° 를 넘는다.
  0.35/1.2 이면 넘침 ≈ 10° 로 허용 안에 선다(run42 실측 9°).
- StoppedGoalChecker 는 **멈춘 상태에서** 허용 안이어야 성공이라, 0° 를 지나칠 때는 성공이
  안 되고 넘친 뒤 되돌아온다.
- 반경 0.25 경계를 넘나들면 RPP 가 당근 **위치** 쪽으로 돌아 −110°·−154° 까지 크게 돈다.
- planner tolerance 0.05 는 목적지 근처 "no valid path" 15회 → 컨트롤러 취소 → Wait →
  14 s 정지 · "Invalid path, Path is empty" 18회를 만들었다.
- **[정정]** run40 의 ±30° 는 TF 지연 탓으로 봤으나, TF 가 정상인 run41 에서 재현됐다.
  원인은 이 넘침이다.

| 409호 | 2.1 s | −7° | — |

작은 각 반복 헌팅은 0회. 남은 것은 **반경 경계 대회전**이다(run39 테스트1 29.4 s 도 같은
설정·같은 모양). RPP 는 회전 목표 전환 거리와 도착 판정 반경이 같은 값(xy 0.25)이라
경계에서 두 모드를 오간다.

**다음 설계(선승인)**: BT 에서 FollowPath 가 xy 로 끝나면 남은 yaw 오차를 계산해
behavior_server `Spin(spin_dist)` 을 한 번 부른다. 한 방향으로 한 번 돌고 끝나 헌팅이
구조적으로 없다. 커스텀 BT 노드 1개(새 프로세스 아님). 위험: Spin 의 충돌 검사
("Collision Ahead - Exiting Spin")가 벽 옆에서 중단할 수 있다. 사용자 제안은 135° 이상에만
쓰는 것이었으나, 헌팅은 ±18° 에서 났으므로 허용치를 넘는 모든 오차에 쓰는 편을 권한다.

### 3.2 run38·run43 — 왜 서는가

```
                 초음파     collision ahead/분   완전정지(≥1s)/분
run38            8층        143                  1.7
run43            6층        110                  1.5
run39 · run42    off        2 · 0                0.2 · 0
```

run43 완전 정지 9회, 전부 같은 순서다(14:48:34 사례).

```
14:48:33.99  RegulatedPurePursuitController detected collision ahead!   (라이다 전방 1.26 m)
   … 10 s 동안 cmd 0 …
14:48:44.19  Controller patience exceeded → Aborting → local_costmap 전체 지우기
14:48:44.39  cmd +0.25 → 14:48:45 +0.50 m/s   (지우자마자 출발 = 실제로는 안 막혀 있었다)
```

- RangeSensorLayer 는 새 측정이 **그 센서의 지금 부채꼴 안**만 다시 쓴다. 로봇이 움직이거나
  서면 옛 마크가 부채꼴 밖에 남아 영원히 안 지워진다. 라이다는 자기 층만 지우므로 못 지운다.
  지도는 층 중 최댓값을 쓰니 RPP 가 선다. Humble RangeSensorLayer 에는 시간 소멸 파라미터가
  없다(설치 헤더 확인: phi·inflate_cone·clear/mark_threshold·clear_on_max_reading·
  no_readings_timeout 뿐).
- 원인 분류(사건 12개): 유턴·회전 중 뒤 사용자(후방 0.2~0.3 m) + 옆/뒷바퀴 옆 0.35~0.64 m
  **4** · 사람 앞 0.6~0.7 m(라이다) + 앞/옆 초음파 **4** · 근처 없음 **1**(run38 은 14).
- 10 s 는 `failure_tolerance 10.0` — DWB 시절 "앞 사람을 지도 안 지우고 조용히 기다린다"는
  값이다. 줄이면 정지 시간은 줄지만 정지 횟수는 그대로이고 복구 진입이 잦아진다.

### 3.4 결정 — collision_monitor 로 이전 (413c8dd)

검토한 셋:

| 방법 | 옛 마크 | 피해 가기 | 정지 | 작업 |
|---|---|---|---|---|
| failure_tolerance 10→3 | 그대로 | 가능 | 3~4 s 로 짧아짐 | 1줄 |
| 같은 2D 층(라이다+초음파 LaserScan) | 0.5 s 안 소멸 | 가능 | 1 s 안쪽 | 드라이버 수정+설정 |
| collision_monitor Range 소스 | 생기지 않음 | 초음파만 보는 것은 불가 | 감속 위주 | 설정만 |

- 같은 2D 층 방식: Nav2 장애물 층은 매 갱신 "지우기 → 표시하기" 순이라, 초음파가 계속
  보는 물체는 라이다가 지워도 다시 칠해지고 사라진 것은 0.5 s 안에 지워진다. 단 지금 라이다
  층은 3D voxel(5 cm 층)이고 라이다 0.382 m · 초음파 0.091 m 라 다른 층에 적혀 라이다가 못
  지운다 → 별도 2D 층과 드라이버의 LaserScan 발행이 필요.
- **사용자 결정: 짧게라도 서는 것 자체가 주행을 불안정하게 한다 → collision_monitor 먼저.**

적용 내용:
- local costmap 초음파 층 6개 `enabled: False`(블록은 되돌리기용으로 남김).
- collision_monitor `observation_sources` 에 `us_front_left/right`, `us_left/right_wheel`
  (`type: range`, `obstacles_angle 0.05`). 뒷바퀴 옆·후방은 넣지 않는다 — Humble 폴리곤은
  진행 방향을 가리지 않아 뒤 사용자를 찍으면 선다.
- Humble 1.1.20 `range.cpp`: range 가 [min,max] 밖이면 버리고, 안이면 fov 호 위에 점을 찍는다.
  에코 없음(1.5 m)도 점이지만 x 1.65 m 라 폴리곤 밖. `source_timeout 1.0` 보다 오래된 소스는
  무시(fail-open, WARN).
- **폴리곤이 앞(x 0.206~0.946, 폭 ±0.28/±0.32)에만 있어 실제로 발동하는 것은 앞 두 개다.**
  센서 x 0.151 → 거리 0.055~0.295 m 정지, ~0.795 m 감속(40 %). 바퀴 옆 둘은 연결만 됐고
  옆 폴리곤을 만들기 전엔 반응하지 않는다.

run44 판정(미리 정한 숫자):
- 주행 중 collision ahead(분당) ≤ 10, 완전 정지(≥1 s) ≤ 0.3/분.
- collision_monitor 감속 로그 수와 사람 사건의 최근접 거리(≥ 0.5 m).
- 초음파 소스 "Ignoring the source" 경고 수(주기 지연 확인).
- CPU ≤ 60 %.

### 9.2 우리 방식의 위치

논문 C 의 분류로 우리는 이미 **시간 분할**이다. 등진 짝만 동시에 쏘고(A 앞왼+후오 · B 앞오+후왼 ·
C 바퀴옆 둘 · D 뒷바퀴옆 둘), 감지 범위가 겹치는 센서(앞 둘, 옆 앞·뒤)는 105 ms 떨어져 쏜다.
150 cm 왕복은 8.7 ms 라 잔향 여지가 작다. RViz 부채꼴 겹침은 같은 물체를 두 센서가 보는 중복
감지이지 간섭이 아니다. run43 대조에서 짝과 같은 값 0~4건 → 간섭 증거 없음.

**주의**: 펌웨어는 `0xFFFE`(센서가 스스로 알린 간섭)를 `0xFFFF`·I2C 실패와 함께 `usFail` 로
뭉뚱그린다(smart_handle_firmware.ino 466~478행). 3회 연속이면 값이 0(무효)이 되므로 간섭은
"유령"보다 **"구멍(감지 누락)"**으로 나타난다. 지금은 이를 셀 방법이 없다.

### 9.4 제안 (현실성 순)

1. **`0xFFFE` 채널별 계수**(펌웨어 + 파서, 1~2시간) — 간섭이 있는지 센서가 직접 답한다. 먼저 잰다.
2. 필요하면 **짝 내 교대 지연**(EERUF 발상, Borenstein & Koren 1995 — 원문 미열람, 초록 기준): 짝 중
   하나를 매 주기 0/약 3 ms 번갈아 늦게 쏘면 동기 혼선이 주기마다 흔들려 기존 중앙값이 걸러낸다.
   주기 약 2.4→2.3 Hz. 반나절 + 실기 1회.
3. 판정용 **완전 순차 8라운드 A/B**(1.19 Hz, 상시용 아님).
4. 논문 B 적응 허용치는 1번에서 튀는 값이 확인될 때만. KNN·위상 복조는 하드웨어상 부적합.
