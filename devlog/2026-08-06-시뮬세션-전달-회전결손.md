## 0. 한 줄 결론

**측정 오류 가설이 산술로 정확히 맞는다.** RTF 0.6 × 0.5 rad/s = 0.300 rad/s = 17.2°/s이고
관측값이 17.4°/s다. 물리를 건드리기 전에 이것부터 배제해야 한다. 3분이면 끝난다(2절).

## 1. 쉬운 설명 — 왜 측정을 먼저 의심하는가

### 용어: RTF

**RTF(Real-Time Factor, 실시간 계수) = 시뮬 안에서 흐른 시간 ÷ 현실에서 흐른 시간.**

`1.0`이면 시뮬과 현실이 같은 속도다. `0.6`이면 시뮬이 느리다 — 물리 엔진이 "1/60초
분량의 계산"을 실제로 1/60초 안에 못 끝내면 이렇게 된다. PhysX 부하, 렌더링,
카메라·LiDAR 센서 시뮬, GPU 경합이 겹치면 0.5~0.7까지 쉽게 떨어진다.

### 무슨 일이 벌어지고 있나

시뮬레이터가 **실시간의 0.6배**로 돌고 있다(RTF 0.6). 이 말은:

```
시뮬 안에서 1초가 흐르는 동안   →   현실에서는 1.67초가 흐른다
현실에서 1초가 흐르는 동안      →   시뮬 안에서는 0.6초만 흐른다
```

로봇은 시뮬 안의 시간을 산다. 시뮬 안에서 `0.5 rad/s`로 정확히 돌고 있어도, **현실
스톱워치로 1초를 재면 그동안 로봇에게는 0.6초만 흘렀으므로 0.3 rad만 돈다.**

영화를 0.6배속으로 재생하면서 스톱워치로 배우의 걸음 속도를 재는 것과 같다. 배우는
정상 속도로 걷고 있지만 측정값은 60 %가 나온다. 배우의 다리에 문제가 있는 게 아니다.

### 숫자가 얼마나 잘 맞나

| 가설 | 예측 각속도 | 비율 |
| --- | --- | --- |
| RTF 0.6을 벽시계로 측정 | 17.2°/s | 60.0 % |
| **관측값** | **17.4°/s** | **60.7 %** |
| 컨트롤러 0.293 / 물리 0.364 | 23.1°/s | 80.5 % |
| 컨트롤러 0.364 / 물리 0.293 | 35.6°/s | 124.2 % |

관측을 RTF만으로 설명하려면 RTF = **0.607**이다. 보고된 "0.6배"와 소수점 둘째 자리까지
맞는다. 그리고 트레드 불일치로는 61 %가 **나올 수 없다** — 어느 방향으로 틀려도
80.5 % 아니면 124 %다.

### 이 팀이 똑같은 오진을 이미 한 번 겪었다

`devlog/2026-07-31-health-monitor-implementation.md:1065-1069`:

> "위 표의 '바퀴 실측 속도'는 **최댓값**이라 기동 스파이크에 취약했다. 0.26을
> 명령했는데 **0.534가 찍혀 환산 오류를 의심했으나, 정착 후 평균으로 다시 재니
> 정확했다.**"

명령의 2배가 찍혀서 환산 계수를 고치려 했는데, 원인은 물리가 아니라 **측정 방식**이었다.
이번 61 %는 방향만 반대인 같은 부류다.

### 핵심 요령: 나눗셈을 하지 마라

시계 문제는 **"각도 ÷ 시간"을 직접 계산할 때만** 생긴다. `/odom`의
`twist.twist.angular.z`는 시뮬레이터가 물리 스텝 기준으로 이미 계산해 둔 값이라
**벽시계와 무관하다.** 그 값을 그냥 읽으면 시계 문제가 통째로 사라진다.

## 2. 지금 당장 할 것 — 3분 판별

### 2-1. `/odom`의 각속도를 직접 읽는다 (제일 중요)

터미널 A에서 회전 명령:

```bash
ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.5}}"
```

> 토픽 이름은 시뮬 구성에 맞출 것. 실물은 `/cmd_vel_req` → Safety → `/cmd_vel_safe`
> 체인이지만 시뮬은 Safety를 거치지 않을 수 있다. `ros2 topic list`로 확인한다.

터미널 B에서 실제 각속도:

```bash
ros2 topic echo /odom --field twist.twist.angular.z
```

기동 스파이크가 지나고 **정착한 값**을 본다(첫 0.5초는 버린다).

| 정착값 | 판정 |
| --- | --- |
| **0.5 근처** | 물리 정상. **결손은 측정 오류였다.** 여기서 끝난다 |
| **0.30 근처** | 진짜 결손이다. 3절로 |

### 2-2. RTF를 실제로 잰다

```bash
python3 - <<'PY'
import subprocess, time, yaml
def sim_now():
    out = subprocess.check_output(
        ['ros2', 'topic', 'echo', '/clock', '--once'], text=True)
    # echo 는 메시지 끝에 '---' 를 붙이므로 safe_load 가 아니라 safe_load_all 이다
    c = next(yaml.safe_load_all(out))['clock']
    return c['sec'] + c['nanosec'] * 1e-9

w0, s0 = time.monotonic(), sim_now()
time.sleep(10.0)
w1, s1 = time.monotonic(), sim_now()
rtf = (s1 - s0) / (w1 - w0)
print(f'RTF = {rtf:.3f}   (벽시계 {w1-w0:.2f} s 동안 sim {s1-s0:.2f} s)')
print(f'이 RTF로 0.5 rad/s를 벽시계로 재면 {0.5*rtf:.3f} rad/s로 보인다')
PY
```

RTF가 0.607 근처로 나오고 2-1의 정착값이 0.5 근처면 **가설이 확정된다.**

### 2-3. 원래 측정을 sim time으로 다시 한다

각도를 시간으로 나눠야 한다면, 나눌 시간은 **`/odom`의 `header.stamp`** 차이여야 한다.
`time.time()`이나 `datetime.now()`를 쓰면 안 된다 — 그것이 벽시계다.

노드를 띄운다면 `use_sim_time: true`가 켜져 있어야 한다. 이 파라미터가 켜진 노드는
컴퓨터 시계 대신 `/clock`이 알려주는 **시뮬 시간**을 쓴다. 모든 노드가 켜져 있으면
시계가 통일되어 RTF가 얼마든 상관없어진다.

```bash
ros2 param get <노드이름> use_sim_time
```

nvblox 예제는 launch에서 이것을 강제한다 — `SetParameter('use_sim_time', True)`가
`launch/isaac_sim_example.launch.py:56`과
`launch/navigation/nvblox_carter_navigation.launch.py:32`에 있다(후자는 `:78`에서
nav2 bringup에도 `'use_sim_time': 'True'`를 넘긴다).

**직접 띄운 노드나 `ros2 topic pub`으로 만든 임시 퍼블리셔에는 적용되지 않는다.**
2절의 측정용 명령들이 여기 해당하므로, 그 값으로 시간 나눗셈을 하면 안 된다 —
`/odom`의 `twist.angular.z`를 그냥 읽으라는 것이 이 때문이다.

## 3. 결손이 진짜일 때 — 확인 순서

2절에서 `/odom` 정착값이 0.30 근처로 나왔다면 물리 문제다. **이 순서로** 좁힌다.

### 3-1. `WHEEL_DISTANCE`가 0.364인지 (여기가 1순위)

`add_drive_odom_graphs.py`의 `WHEEL_DISTANCE`가 아직 **0.293**이면 여기서 약 20 %가
나온다. 이 지시는 이미 문서에 있다 —
`docs/superpowers/specs/2026-08-04-urdf-geometry-tf-launch-design.md:404-416`:

> `add_drive_odom_graphs.py`의 `WHEEL_DISTANCE`: `0.293` → **`0.364`**
>
> **마지막 항목을 빠뜨리면 수정 A가 무의미해진다.** USD와 컨트롤러가 모두 0.364여야
> 한다. 시뮬레이터는 물리 엔진이 바퀴를 직접 굴리므로 실물의 보정 상수 0.37이 아니라
> 기하값을 쓴다.

**주의:** 이 장비(개발 노트북)에서 지금 로드되는 URDF는 **아직 0.293**이다.

| 위치 | 구동륜 y | 트레드 |
| --- | --- | --- |
| `vica_ros2_ws/install/.../VICA.xacro:204,211` | `±0.1465` | **0.293** |
| `src/.../VICA.xacro` (`feat/home-return` 체크아웃) | `±0.1465` | **0.293** |
| `dev`의 `VICA.xacro:22` | `wheel_separation` | **0.364** |

USD를 이 장비의 URDF에서 export했다면 0.293이 들어갔다. **USD와 컨트롤러 양쪽 다**
확인해야 한다.

**코드를 뒤지지 않고 판별하는 법.** 0.5 rad/s를 명령한 상태에서 `/joint_states`의
바퀴 각속도를 보면 컨트롤러가 쓰는 트레드가 바로 나온다.

```bash
ros2 topic echo /joint_states --field velocity
```

| 바퀴 각속도 | 컨트롤러가 쓰는 트레드 |
| --- | --- |
| **1.400 rad/s** | 0.364 — 맞다 |
| **1.127 rad/s** | **0.293 — 여기가 범인** |

`ω × d / (2 × 0.065)` 이다. 0.5 × 0.364 / 0.13 = 1.400, 0.5 × 0.293 / 0.13 = 1.127.

### 3-2. 캐스터 collision 반지름이 0.042인지

같은 문서 9.1절:

> 캐스터 collision 반지름 **0.042** — CAD상 캐스터가 4.5 mm 떠 있어 접지 보정이
> 필요하다. 0.0375를 그대로 쓰면 PhysX가 로봇을 뒤로 **0.635° 기울여 세운다**

기울면 구동륜 하중이 바뀌어 회전 마찰이 달라진다. 실물 쪽에는 "캐스터가 회전을
방해한다"는 관측이 **한 건도 없으므로**, 이 항목이 잡히면 순수한 시뮬 문제다.

### 3-3. 3단 비교 — 어디서 새는지 좁히기

3-1, 3-2를 통과하고도 결손이 남으면 그때 세 숫자를 나란히 놓는다.

| # | 무엇 | 어떻게 | 0.5 rad/s 명령 시 기대값 |
| --- | --- | --- | --- |
| 1 | 명령된 바퀴 목표 각속도 | `ω × d / (2 × 0.065)` (계산) | **1.400 rad/s** (d=0.364) |
| 2 | 실제 바퀴 각속도 | `ros2 topic echo /joint_states --field velocity` | 1.400 rad/s |
| 3 | 실제 yaw rate | `ros2 topic echo /odom --field twist.twist.angular.z` | 0.500 rad/s |

- **1 ≠ 2** → 조인트 드라이브 문제 (damping / maxForce). 바퀴가 목표를 못 따라간다
- **1 = 2 인데 3이 작음** → 바퀴는 도는데 안 나아감 = 미끄러짐 또는 캐스터 저항
- **1 자체가 1.127** → 트레드 0.293. 3-1로 돌아갈 것

`/odom`이 바퀴 엔코더 기반으로 계산된다면 3번은 미끄러짐을 검출하지 못한다. 그 경우
ground truth pose(USD의 실제 prim transform)를 3번으로 써야 한다.

### 3-4. 하지 말 것

**MPPI 파라미터로 보상하지 않는다.** 시뮬에서 `wz_max`를 올려 맞추면 그 값을 실물에
올리는 순간 과회전한다. 고칠 곳은 물리다.

단, 4-1을 함께 읽을 것 — "실물은 100 % 돈다"가 아직 실측이 아니다.

## 4. 정정 두 가지

### 4-1. "실물은 100 % 돈다"는 근거가 저장소에 없다

**명령 각속도 대비 실측 각속도의 배율을 잰 기록이 devlog·docs 어디에도 없다.**
검증된 것은 선속도뿐이다(`devlog/2026-07-31-health-monitor-implementation.md:1071-1077`):

| 명령 | 보고 평균 | 배율 |
| --- | --- | --- |
| 0.10 m/s | +0.104 m/s | 1.04 |
| 0.26 m/s | +0.262 m/s | 1.01 |

가장 가까운 회전 기록인 제자리 360° 시험은 총 회전각이 ±1 % 이내로 맞았지만
(`devlog/2026-07-30-gpu-nvblox-stt-contention.md:146-172`), 방법이
**"encoder가 목표에 도달하면 정지"** 하는 폐루프라 **각속도 결손을 검출할 수 없는
설계**다. 각속도가 느려도 각도는 맞게 나온다. 소요 시간도 기록되지 않았다.

sim-to-real 논리의 방향은 여전히 옳다. 다만 **기준선 자체가 아직 측정되지 않았다.**
Jetson이 되면 재야 한다(6절).

### 4-2. `wz 표준편차 0.1273 rad/s`는 이 워크스페이스에 없는 값

존재하는 값은 `docs/nav2_tuning_log_2026-07-28.md:91`의 **0.136 rad/s**
(`max_vel_theta` 0.4의 34 %)다. 정지 중에는 0.002 rad/s로 깨끗하므로 센서 잡음이 아니라
주행 중 거동이다.

## 5. 시뮬에 넣을 실물 값

| 항목 | 값 | 성격 |
| --- | --- | --- |
| 바퀴 반지름 | **0.065** | 부품 스펙(MDH100 Ø130 mm). 세 곳 전부 일치. 안심하고 쓸 것 |
| 바퀴 중심 간격 | **0.364** | 줄자 실측. **시뮬은 이 값** (USD·컨트롤러 양쪽) |
| 오도메트리 유효 트레드 | 0.370 | 실물 회전 시험 보정 상수. **시뮬에 쓰지 말 것** |
| 캐스터 축 높이 / 반지름 | **0.042** | 접지 보정 포함 값 |
| 기어비 | 없음 | 바퀴 RPM을 CAN에 직접 전송 |
| DWB `max_vel_theta` | 0.4 rad/s | 실물 주행 각속도 상한 |
| `behavior_server` 회전 | max 0.4 / min 0.15 | Spin용 (`dev` 기준) |

**0.364와 0.370이 다른 것은 오류가 아니다.** 타이어 폭 67.8 mm가 접지면에서
미끄러지므로 오도메트리 유효 트레드가 기하값보다 6 mm 크다. 통일 대상이 아니다
(`...urdf-geometry-tf-launch-design.md:94-119`, 3.1.1절).

실물 각속도 파이프라인(참고):

```
DWB max_vel_theta 0.4 → smoother ±1.0 → Safety clamp ±2.0 → knob 스케일 → 바퀴 RPM
```

실효 제약은 **DWB의 0.4 rad/s**이고 뒤는 전부 느슨한 안전망이다. 시뮬에서 0.5를
명령한 것은 실물 주행 상한보다 큰 값이라는 점도 참고할 것.

## 6. Jetson에서 재야 할 것 (실물 기준선)

4-1 때문에 필요하다. 5절 선속도 표를 만든 방식을 그대로 wz에 적용한다.

1. `/cmd_vel_safe`에 일정 wz(0.2 / 0.3 / 0.4 rad/s)를 걸고 **정착 후** 구간만 사용한다.
   실물은 wz 지연이 **300 ms**(vx는 200 ms)이므로 명령 후 최소 0.5 s를 버린다
   (`docs/nav2_tuning_log_2026-07-28.md:59-72`).
2. 같은 구간 `/odom` `twist.angular.z`의 **평균**과 표준편차를 낸다.
   **최댓값을 쓰면 안 된다** — 1절의 0.534 오진이 그 방식 때문이었다.
3. 배율 = 실측 평균 / 명령. 선속도가 1.01~1.04였으므로 같은 범위면 "실물 100 %"가
   비로소 실측이 된다.
4. 시험 전 Safety 연결과 E-stop 해제를 확인한다. Safety가 DDS 그래프에서 이탈했는데
   모른 채 "바퀴가 한 번도 안 돌았는데 값만 나온" 사고가 있었다.

bag은 `~/vica_data/bags/`, 분석 스크립트는 `~/vica_data/analysis/`에 있고 **둘 다 저장소
밖**이다.
