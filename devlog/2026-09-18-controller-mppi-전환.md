## 3. controller 를 MPPI 로 (`bc7ab15`)

### 3.1 왜
레일까지 온 뒤 남은 축이 controller 다. run23 에서도 코너 조향이 펄스로 남았고(버스트 3.9·반전
2.7), 원인은 **1 Hz 로 바뀌는 planner 경로를 DWB 가 이산 속도 격자에서 매번 새로 쫓는 구조**다.
MPPI 는 이전 명령에 잡음을 얹어 궤적 수천 개를 굴리고 가중평균을 내므로 경로가 바뀌어도 명령이
튀지 않는다. 2026-08-29 실측(브랜치 `nav2/mppi2` `5a6acc7`, 4회차):

| 잣대 | DWB | MPPI |
| --- | --- | --- |
| 손잡이 횡속도 | 0.055 | **0.018~0.029** |
| 회전 방향 반전 | 8.1 회/분 | **1.1~1.6** |
| 경로 이탈 | 0.043 m | 0.031 |
| 제어주기 놓침 | 566 | **95** |

### 3.2 그때 왜 못 썼고 지금은 무엇이 다른가
미채택 사유는 "도착을 못 한다"(화장실 4/4 실패)였다. `|w|` 가 DWB 의 1/3(0.132 → 0.043)이라
유턴을 못 했고, planner 가 **목적지까지** 그린 긴 경로를 쫓다 금지구역에 들어가면 회복하지
못했다. 지금은 둘 다 다르다 — ① 레일 8판-3 이라 planner 목표가 **3 m 앞 당근**이고
② 0903_d 는 복도가 넓다(주행 중 벽 여유 평균 1.27 m).

### 3.3 08-29 가 남긴 교훈 셋 (이번 값의 근거)
1. **탐색 폭(vx_std·wz_std)이 회전의 진짜 노브다.** MPPI 는 '지금 명령 + 잡음'으로 후보를 만들어
   critic 으로 고를 뿐이라, 후보에 없는 동작은 벌점을 0 으로 해도 못 고른다. wz_std 0.3→0.5 가
   제자리 회전을 1.5 → **4.1 s 로 늘렸다**.
2. **CPU 는 문제가 아니다.** batch 1000 이 DWB 의 2.5배 계산량인데 제어주기 놓침은 6배 적었다.
3. `rotation_penalty`(planner) 5.0 은 그대로 뒀다 — 컨트롤러가 회전을 실행할 수 있게 된 뒤
   그 값을 함께 낮추는 조합은 아직 미시험이다.

소스에서 확인한 것 하나 더: **`PreferForwardCritic` 은 후진에만 벌점**을 준다
(`max(-vx, 0)`). `vx_min: 0.0` 인 우리 설정에서는 사실상 아무 일도 하지 않으므로
**제자리 회전을 막지 못한다**. `TwirlingCritic` 은 반대로 `|wz|` 평균에 벌점이라 제자리와 호를
구분하지 않는다. 그래서 "제자리 대신 호" 는 **PathFollow/PathAngle 의 기준점 거리**로 만든다.

### 3.4 값과 그 이유

| 사용자 요구 | 값 | 전 → 후 |
| --- | --- | --- |
| ① 제자리 대신 최소 호로 유턴 | `PathFollowCritic.cost_weight` | 5.0 → **6.0** |
| | `PathFollowCritic.offset_from_furthest` | 5 → **8** (먼 점을 보면 완만한 호) |
| | `PathAngleCritic.offset_from_furthest` | 4 → **6** (유턴 각을 완만하게 계산) |
| | `TwirlingCritic.cost_weight` | 3.0 → **2.0** |
| | `vx_std` / `wz_std` | 0.30 → **0.35** / 0.50 → **0.45** |
| ② 코너에 안 붙기 | `ObstaclesCritic.repulsion_weight` | 1.5 → **2.2** |
| ③ 손잡이 흔들림 | MPPI 구조 + `temperature` 0.3 | 그대로 |
| ④ 동적 장애물 회피 유지 | `critical_weight` 20 · `collision_cost` 10000 · `collision_margin_distance` 0.10 | 08-29 값 그대로 |
| ⑤ 초음파 8개 예정 | local costmap 의 range 레이어가 그대로 `ObstaclesCritic` 입력 | 변경 불필요 |

나머지는 DWB 와 같은 물리 한계로 맞췄다(A/B 성립 조건): `vx_max` 0.5 · `wz_max` 0.5 ·
`ax_max` 2.0 · `az_max` 2.0 · `vx_min` 0.0(후진 금지, 뒤에 사람이 손잡이를 잡고 있다).
지평은 36 × 0.05 = 1.8 s 로 DWB `sim_time` 2.0 과 거의 같다. `batch_size` 1000.

### 3.5 [미해결·안전] inflation < 외접반경
```
inflation_radius 0.55  <  외접반경 0.620 (footprint_padding 0.05 포함)
```
08-29 에 손잡이 축소로 풀렸던 전제(그때 외접 0.4727)가 **09-15 base_link 이동으로 되살아났다**.
벽에서 0.55~0.62 m 구간은 costmap 비용이 0 이라 **어떤 critic 도 보지 않는다** — DWB 의
`ObstacleFootprint` 가 막던 자리다. MPPI 는 `ObstaclesCritic.consider_footprint: true` 로 메우지만
한계가 있다: `ObstaclesCritic`·`CostCritic` 모두 **중심 셀 비용이 1 미만이면 그 점을 건너뛴다**
(`if (pose_cost < 1) continue`). 즉 로봇 중심이 벽에서 0.58 m 일 때 뒤쪽 모서리(0.570 m)가 벽에
닿아도 검사되지 않는다. 폭 0.07 m 의 위험이다.

**대응(사용자 결정 09-18)**: 이번 MPPI 시험은 **0903_d(넓은 복도)에서만** 한다. 0630 처럼 좁은
지도로 가기 전에 `inflation_radius` 를 0.62 이상으로 올린다. backlog `NAV2-B3` 의 "controller 를
바꾸려면 그 전에 inflation 을 올려야 한다" 문단은 **다시 유효**하다(그 문서의 "2026-08-29 해소됨"
표시는 갱신이 필요하다).

### 3.6 되돌리는 법
DWB 설정은 지우지 않고 `FollowPathDWB` 로 이름만 바꿔 뒀다(`controller_plugins` 에 없으므로
로드되지 않는다). 되돌리기는 MPPI 블록을 지우고 `FollowPathDWB` → `FollowPath` 로 이름만
되돌리면 끝이다.

### 3.7 계약 시험
컨트롤러를 바꾸면 DWB 키를 직접 읽던 시험 8건이 깨진다. 그 시험들이 지키는 것은 "컨트롤러가
계획한 가·감속을 velocity_smoother 가 막지 않는가", "완만한 정지가 goal tolerance 안에서 끝나는가"
같은 **관계**이지 키 이름이 아니므로, 컨트롤러 종류와 무관하게 값을 읽는
`_controller_limits()` 헬퍼를 넣고 옮겼다(대응표는 그 함수 주석). planner–controller 충돌 모델
일치 시험은 MPPI 의 `consider_footprint` 를 보게 했다. **125 통과**, 실패 3건은 기존 표류
(nvblox 플러그인·turning_radius·recovery patience).

### 5.1 [철회] "따라가는 힘↑ + 감쇠↓ 가 진동을 만든다"

`bc7ab15` 에서 08-29 와 다르게 고른 값이 정확히 7개였다(구조 파라미터는 동일).
제어의 교과서대로 이득↑·감쇠↓ 를 동시에 한 것이 범인이라고 보고 **7개를 전부**
08-29 실측 조합으로 되돌렸다(`eef2aa0`). 4개만 되돌리면 검증 안 된 새 조합이 된다.

```
ObstaclesCritic.repulsion_weight    2.2  -> 1.5
PathAngleCritic.offset_from_furthest  6  -> 4
PathFollowCritic.cost_weight        6.0  -> 5.0
PathFollowCritic.offset_from_furthest 8  -> 5
TwirlingCritic.cost_weight          2.0  -> 3.0
vx_std                             0.35  -> 0.3
wz_std                             0.45  -> 0.5
```

**run25 결과: 이 가설은 반증됐다.** 직진 조향 반전 46.3 → **47.9** 로 그대로였다.
**critic 가중치는 이 축이 아니다.** 다만 나머지가 전부 좋아졌다(6절).

### 5.2 `offset_from_furthest` 의 덫 (새 사실, 유효)

경로 점 간격은 **5 cm** 라 offset 8 은 "8 개 점 = 40 cm"다. 게다가 이 값은 로봇이
아니라 **궤적이 닿는 가장 먼 경로점**에서 더 나아간 거리다. 달릴 때는 기준점이
1.2 m 앞이지만 **제자리에서 돌면 궤적이 안 나아가 0.4 m 까지 무너진다.** 코앞을
보면 크게 돌라는 답이 나오고, 크게 돌면 또 안 나아간다. 제자리가 제자리를 부른다.
offset 을 올려 호를 유도하려는 시도는 이 덫 때문에 실패한다.

### 5.3 MPPI 가 보는 경로는 1.5 m 뿐 (구조, 유효)

`prune_distance` 가 경로를 로봇 앞 1.5 m 로 자른다(nav2 기본값). DWB 는 local
costmap 전체(3 m)의 경로를 본다. 그리고 `PathFollowCritic` 은 경로 끝이
`threshold_to_consider`(1.4 m) 안이면 **꺼지고**, `GoalCritic` 은 같은 1.4 m 에서
**켜진다**. 즉 10 cm 차이로 그 스위치 옆에 산다. 이 축을 건드릴 거면 threshold 가
아니라 `prune_distance` 를 늘려야 한다.

레일은 이 약점을 정확히 찌른다 — 경로를 초당 1.3~1.5 회 새로 준다(레일 없을 때

것이다. run24 실측으로 /plan 638 개 중 **324 개가 로봇 발밑에서 시작**(자유주행),

## 7. 잔떨림의 정본 원인 = 표본 잡음 (run26 으로 확정)

MPPI 출력은 궤적 1000 개의 **가중평균**이라 표본 잡음이 남는다. 실측이 식을 그대로
따른다.

```
주기당 |Δw| ≈ 1.9 x wz_std / √batch_size
  run24 wz_std 0.45 → 0.0216  (예측 0.0142, 배수 1.91)
  run25 wz_std 0.50 → 0.0238  (예측 0.0158, 배수 1.89)
```

배수가 두 회차에서 같다 = 모형이 맞다. `N_eff = 1000/1.9² ≈ 277`. 그리고 warm start
가 이 잔떨림을 이어받아 **누적**시킨다(무작위 걸음).
`0.0238 x √(2.8 s / 0.05 s) = 0.22 ≈ 실측 직진 w 표준편차 0.239`. 사슬이 닫힌다.

DWB 와의 차이는 **평균이냐 선택이냐**다. DWB 는 이산 속도 후보 중 하나를 고르므로
같은 후보가 또 이기면 값이 한 치도 안 바뀐다(76.4 %). MPPI(run25)는 4.7 %.

### 7.1 `temperature` 0.3 → 0.6 (`f7ffa0e`) — 예측대로 맞았다

`temperature` 는 softmax 가중치의 평평함을 정한다. 올리면 더 많은 표본이 평균에
실제로 참여해 N_eff 가 오르고 잔떨림이 준다. **CPU 를 한 푼도 안 쓴다**(batch 2배도
같은 x0.71 인데 controller CPU 는 16 → 31 % 다).

| | run25 | run26 | 예측 |
| --- | ---: | ---: | ---: |
| 주기당 \|Δw\| | 0.0238 | 0.0159 | **x0.67 (예측 x0.68)** |
| 직진 조향 반전 | 47.9 회/분 | **34.4** | 33 |
| 직진 w 표준편차 | 0.239 | 0.204 | 0.16 |
| 흔들림 한 주기 | 2.8 s | 3.1 s | — |
| N_eff 환산 | 442 | **986** | — |

**temperature 축은 이것으로 닫혔다** — N_eff 가 1000 중 986 이라 더 올려도 1.4 % 뿐이다.
잔떨림에 남은 값은 `batch_size`↑(x1/√N, CPU 정비례)와 `wz_std`↓(비례, 공짜지만
회전 권한이 준다) **둘뿐**이다.

### 7.2 대가 — 코너 속도

높은 temperature 는 평균에 느린 궤적도 싣는다. 상한 0.5 에 걸려 잘리는 쪽은
위뿐이라 평균이 아래로 끌린다.

| | run23 DWB | run25 | run26 |
| --- | ---: | ---: | ---: |
| 직선 중앙값 | 0.500 | 0.500 | 0.499 |
| 직선 하위 10 % | 0.474 | 0.476 | **0.405** |
| **일반코너 평균 속도** | **0.464** | 0.397 | **0.407** |
| U턴 평균 속도 | 0.307 | 0.346 | 0.313 |
| 코너/직선 비 | 0.94 | 0.82 | 0.91 |

깨끗한 직선에서는 여전히 0.5 를 낸다. 느려지는 곳은 **코너**이고, DWB 대비 12 % 낮다.
이유는 맞바꿈이다 — MPPI 는 1.5 m 창 안의 굽은 경로에 붙어 있으려 하고(그래서 벽
여유가 0.56 → 0.75 m 로 좋다), DWB 는 코너를 질러가며 속도를 지킨다.
