## 1. 무엇이 잘못돼 있었나

넷 다 증상이 하나다 — **Nav2가 죽었는데 앱에 "주행 준비 완료"가 뜬다.**

| # | 결함 | 원인 |
| --- | --- | --- |
| A | `"Nav2 is inactive"`를 활성으로 읽음 | `'active' in message` 부분 문자열 검사. `in`**active**에 걸린다 |
| B | 낡은 진단·STALE 등급을 계속 믿음 | 항목의 수신 시각과 `level`을 둘 다 보지 않았다 |
| C | 응답 없는 호출에서 폴링이 영구 정지 | fallback이 '서비스 미준비' 가지에만 있었고 `_nav2_in_flight`를 푸는 시한이 없었다 |
| D | 위치추정 매니저를 주행으로 오인 | 두 `lifecycle_manager`가 같은 `Nav2 Health` 이름·같은 문구를 쓴다 |

A의 문자열은 `libnav2_lifecycle_manager_core.so`에서 직접 확인했다(`Nav2 is `, `Nav2 is inactive`).
D의 두 매니저는 `nav2_bringup/bringup_launch.py`가 `navigation_launch.py`와
`localization_launch.py`를 모두 포함하기 때문에 동시에 존재한다.

## 2. 이 변경이 주행에 닿지 않는 이유

검증 전에 확인해 둘 것. `robot_health_monitor_node`는 **관측과 보고만 한다.**

- 발행: `/robot/health`, `/robot/events` 둘뿐이다. `/cmd_vel_req`·`/cmd_vel_safe`·
  `/emergency_stop`·미션 명령을 내지 않는다.
- 호출: `<lifecycle_node>/get_state` 하나뿐이며 상태를 **읽기만** 한다.
- 소비자: `/robot/health`를 구독하는 ROS 2 노드가 워크스페이스에 없다. 유일한 소비자는
  관리자 앱(`VICA_Supervisor`)의 진단 화면이다.

브링업 매뉴얼 `⑪-1`의 승인 기준과 같다 — *이 노드는 모터를 세우지 않는다.*
따라서 이 검증에서 **로봇을 주행시킬 필요가 없다.** 7절 회귀 확인만 배선을 본다.

## 6. 시험

### 시험 A — Nav2를 비활성으로 만든다 (가장 중요)

**주의.** `ros2 lifecycle set /bt_navigator deactivate`로는 재현되지 않는다.
`lifecycle_manager`의 진단은 자기 내부 `system_active_` 플래그를 보고 나오므로,
매니저 자신의 서비스로 내려야 한다.

```bash
ros2 service call /lifecycle_manager_navigation/manage_nodes \
  nav2_msgs/srv/ManageLifecycleNodes "{command: 1}"     # 1 = PAUSE
```

| 확인 | 고치기 전 | 고친 뒤 (기대) |
| --- | --- | --- |
| `/diagnostics_agg`의 `Nav2 Health` | `Nav2 is inactive`, level 2 | 같음 (입력이라 안 바뀐다) |
| `navigation_readiness` | **2 (READY)** ← 결함 | **1 (NOT_READY)** |
| `active_faults` | Nav2 항목 없음 | `NAV2_NOT_ACTIVE` |
| 앱 진단 화면 | 초록 | 주행 불가 표시 |

되돌린다.

```bash
ros2 service call /lifecycle_manager_navigation/manage_nodes \
  nav2_msgs/srv/ManageLifecycleNodes "{command: 2}"     # 2 = RESUME
```

`navigation_readiness`가 2로 돌아오면 A 통과다.

### 시험 B — 진단이 끊긴 뒤 낡은 값을 붙들지 않는가

`lifecycle_manager_navigation`을 통째로 죽여 진단 발행 자체를 끊는다.

```bash
ros2 node list | grep lifecycle_manager_navigation      # 살아 있는지 먼저 확인
pkill -f lifecycle_manager_navigation
```

`diagnostics_timeout_sec`(5.0초)가 지난 뒤를 본다.

- 기대: `navigation_readiness`가 **1 (NOT_READY)** 로 떨어진다.
- 고치기 전에는 마지막 `"Nav2 is active"`가 `diag_items`에 남아 **2 (READY)로 고정**됐다.
  이 dict는 만료 제거를 하지 않는다.

aggregator가 level만 STALE(3)로 덮어 재발행하는 경우도 같은 결과여야 한다.
`/diagnostics_agg`에서 해당 항목의 level이 3으로 바뀌는지 함께 본다.

확인 후 bringup을 다시 올린다.

### 시험 C — 응답 없는 호출에서 폴링이 되살아나는가

2026-08-01에 `/bt_navigator/get_state`가 10분간 반환되지 않았던 그 경로다.
서버는 떠 있고 응답만 오지 않는 상태를 만들어야 한다.

**먼저 시한을 2.0초로 낮춘다.** `lifecycle_manager`의 `bond_timeout` 기본값이 **4.0초**라
(VICA `nav2_params.yaml`에 미지정 → nav2 코드 기본값), 시한을 5.0으로 두면 bond가 먼저
끊어져 무엇 때문에 판정이 바뀌었는지 갈라 볼 수 없다.

```bash
ros2 param set /robot_health_monitor_node nav2_call_timeout_sec 2.0
```

> 이 파라미터는 생성자에서 한 번만 읽으므로 `param set`으로는 반영되지 않는다.
> `config/required_components.yaml`의 값을 2.0으로 고쳐 모니터만 재기동하는 것이 확실하다.
> 시험이 끝나면 5.0으로 되돌린다.

```bash
ros2 node list | grep bt_navigator
BT_PID=$(pgrep -f bt_navigator | head -1)
kill -STOP $BT_PID          # 죽이지 않고 멈춘다. 서비스는 광고된 채 응답만 없다
```

기대 동작을 두 국면으로 나눠 본다.

**국면 1 — 멈춘 직후 ~4초 이내 (bond는 아직 살아 있다)**

1. 시한(2.0초) 뒤 모니터 로그에 경고가 뜬다.
   `Nav2 lifecycle 조회가 시한 내에 응답하지 않아 진단으로 판정한다`
2. 경고 뒤에도 **폴링이 계속 돈다.** 2초마다 판정이 갱신된다.
3. `lifecycle_manager`가 아직 `"Nav2 is active"`를 내고 있으므로
   `navigation_readiness`는 **2 (READY)** 를 유지한다. 이게 이 fallback의 존재 이유다 —
   서비스 하나가 막혔다고 Nav2 전체를 죽은 것으로 보고하면 안 된다.

**국면 2 — 약 4초 뒤 (bond가 끊어진다)**

`bt_navigator`가 heartbeat를 못 내므로 `lifecycle_manager`가 bond 끊김을 잡고
`system_active_`를 내린다. 진단이 `"Nav2 is inactive"`로 바뀌고
`navigation_readiness`는 **1 (NOT_READY)** 로 떨어진다. **이것은 정상 동작이다** —
이 시점에는 Nav2가 실제로 비활성이다.

이 시험에서 보는 것은 3번의 READY 유지가 아니라 **1·2번, 즉 경고가 뜨고 폴링이 되살아나는
것**이다. 고치기 전에는 이 지점에서 `_nav2_in_flight`가 true로 래치돼 **폴링이 영영
멈췄고**, fallback도 '서비스 미준비' 가지에만 있어 끝내 실행되지 못했다. 국면 2의 전환도
관측되지 않았다.

풀어 준다.

```bash
kill -CONT $BT_PID
```

멈춤을 푼 뒤 늦게 도착하는 응답이 판정을 흔들지 않는지도 본다. `navigation_readiness`가
한 번 튀었다가 돌아오는 일이 없어야 한다(포기한 호출은 future 동일성으로 무시한다).

시험이 끝나면 `nav2_call_timeout_sec`를 5.0으로 되돌리고 모니터를 재기동한다.

### 시험 D — 위치추정 매니저가 주행을 덮지 않는가

주행 매니저만 내리고 위치추정 매니저는 살려 둔다.

```bash
ros2 service call /lifecycle_manager_navigation/manage_nodes \
  nav2_msgs/srv/ManageLifecycleNodes "{command: 1}"     # navigation 만 PAUSE
ros2 topic echo /diagnostics_agg | grep -B2 -A3 "Nav2 Health"
```

`Nav2 Health` 항목이 **둘** 보여야 한다. 이름만 다르고 문구는 같다.

```
lifecycle_manager_localization: Nav2 Health   →  Nav2 is active
lifecycle_manager_navigation:   Nav2 Health   →  Nav2 is inactive
```

- 기대: `navigation_readiness` **1 (NOT_READY)**.
- 고치기 전에는 이름을 `lifecycle_manager`로만 걸러서, 위쪽 항목 하나만 보고
  **2 (READY)** 로 판정했다. AMCL만 멀쩡해도 주행이 정상으로 읽혔다.

되돌리는 것은 시험 A와 같다(`command: 2`).

### 8.1 실행하며 드러난 것

절차서를 그대로 따르면 걸리는 지점이 셋 있었다. 다음 사람을 위해 남긴다.

- **시험 C의 시한 2.0은 국면 1을 관측할 수 없다.** 첫 경고까지 걸리는 시간이 폴링
  주기(2.0)에 시한(2.0)을 더한 최대 4.0초인데, `bond_timeout`도 4.0초라 창이 닫힌다.
  실제로 bond 끊김이 첫 경고보다 1초 빨랐다. **시한을 1.0으로 두면** 첫 경고가 최대
  3초에 뜨고 약 1초의 창이 생긴다. 이 값으로 국면 1을 확인했다.
- **경고 간격은 시한이 아니라 폴링 2회분이다.** 시한을 넘긴 tick에서는 포기만 하고
  재호출은 다음 tick이므로, 폴링 2.0 + 시한 1.0 조합에서 경고는 4초마다 나온다.
  노드 주석의 "다음 tick에 다시 묻는다"와 같은 말이다.
- **`SIGSTOP`을 겪은 `bt_navigator`는 스스로 복구되지 않는다.** `SIGCONT` 뒤
  `lifecycle_manager`가 자동 재기동을 시도하지만 BT XML 로딩에서 실패한다
  (`Error loading XML file: navigate_through_poses_w_replanning_and_recovery.xml`).
  시험 C 뒤에는 Nav2 재기동이 필요하다. nav2 쪽 성질이며 이 변경과 무관하다.

지도에 없는 장소에서도 검증할 수 있다. AMCL 초기 pose는 실제 위치와 달라도 되며,
`map → odom` 변환만 나오면 costmap이 활성화를 끝낸다. 주행을 하지 않으므로 위치
정확도는 판정에 영향을 주지 않는다.

## 11. 이 검증으로 덮지 않는 것

- `/VICA/Other` 그룹 헤더로 거짓 ERROR가 남는지 — 별건이며 런타임 확인이 필요하다.
  `ekf_filter_node`의 `odometry/filtered topic status`를 `agg_parser`가 항목 단위로
  버리는데, `diagnostic_aggregator`가 그 항목을 품은 **그룹 헤더**를 따로 발행하면
  ERROR가 이름만 바뀐 채 살아남을 수 있다.
- 앱(`VICA_Supervisor`) 쪽 표시 문구. 이 변경은 `/robot/health` 값만 바꾸며 앱 코드는
  건드리지 않았다.
