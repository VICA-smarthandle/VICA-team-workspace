## 2. run28 — 10 Hz 전환 (`5ee7ad9`)

`controller_frequency 10.0` · `model_dt 0.1` · `time_steps 28` · `temperature 1.2`.

**`model_dt` 는 선택이 아니다.** `optimizer.cpp setOffset()`:

```
controller_period >  model_dt  ->  throw runtime_error   (노드가 안 뜬다)
controller_period == model_dt  ->  shift_control_sequence = ON (warm start)
controller_period <  model_dt  ->  WARN, shifting OFF
```

1/10 = 0.1 이 유일한 값이다. 0.05 로 두면 컨트롤러가 기동에서 죽는다.
지평은 28 x 0.1 = 2.8 s 로 그대로. 초당 궤적 점 2,240,000 → **560,000 (x1/4)**.
공식 README 확인: 지평 x vx_max = 1.4 m < local costmap 반경 3.0 m.
낮춘 또 다른 근거: local costmap 이 애초에 초당 5회만 갱신된다 — 20 Hz 는 같은 지도를
네 번 다시 보고 있었다.

## 4. DWB vs MPPI — 여섯 회차 종합

공식 README: MPPI 는 "가우시안 분포에서 무작위로 흔든 제어를 앞으로 굴려 궤적 묶음을
만들고 critic 으로 점수를 매겨 **소프트맥스로 섞는다**". DWB 는 속도 격자에서
**하나를 고른다**. 고르기 vs 섞기 — 성격 차이가 전부 여기서 나온다.
(DWB 는 76.4 % 의 주기에서 명령이 한 치도 안 바뀐다. MPPI 는 5 % 안팎.)

| | DWB | MPPI 최선 조합 |
|---|---|---|
| 흔들림 크기 | 0.210 | **0.186** |
| 코너 조향 | 2.8·2.0 | **2.1·2.0** |
| 사람 첫 포착 · 사건당 정지 | 1.24 m · 0.64 s | **2.03 m · 0.58 s** |
| 벽 여유 | **0.56 m** | 0.43~0.85 (설정 따라 요동) |
| U턴 제자리 | **38 %** | 51~65 % |
| 일반코너 속도 | **0.464** | 0.398~0.417 |
| 완주 | **12/12** | 7/8 ~ 8/8 |
| 궤적 전멸 | 5회 | **0회** |
| controller CPU | 19.1 % | **17.6 %**(10 Hz 면 더 적음) |

**MPPI 가 이기는 것**: 동적 장애물(더 멀리서 더 짧게), 코너 조향 매끄러움, 궤적 전멸 없음.
**DWB 가 이기는 것**: 유턴, 코너 속도, **결과의 안정성**.

**MPPI 의 진짜 비용은 CPU 가 아니라 값들의 얽힘이다.** 공식 README 는 "구형 i5 에서
50 Hz 이상" 이라 하고 우리 젯슨에서도 DWB 보다 적게 썼다. 대신 나흘간 드러난 얽힘:

- `temperature` 는 `time_steps` 가 바꾼다 (§1)
- `temperature` 는 부드러움과 경계심을 **같이** 돌린다 (§2.2)
- `wz_std` 는 잔떨림과 유턴을 **반대로** 돌린다 (§1)
- `model_dt` 는 제어 주기와 정확히 같아야 하고 아니면 노드가 죽는다 (§2)
- `offset_from_furthest` 는 미터가 아니라 점 개수, 기준도 로봇이 아니다 (09-18 §5.2)

**비카에 성격은 맞다** — 사람이 손잡이를 잡고 따라오므로 섞어서 내는 쪽이 손에 낫고,
사람을 더 멀리서 알아보고 덜 멈추는 것도 안내에 맞다.
**다만 지금 상태로는 못 쓴다** — 완주 7/8 에 벽 0.11 m 다.

### 6.6 제어 주기 20 → 10 Hz 는 모터에 닿지 않았다

`/cmd_vel_safe` 발행 주기는 **모든 회차에서 30 Hz** 다(collision_monitor 가 자기 주기로
다시 낸다). controller 가 10 Hz 로 계산해도 velocity_smoother(20 Hz)와
collision_monitor(30 Hz)가 사이를 메운다. **모터가 받는 명령의 촘촘함은 안 변했다.**
얻은 것은 제어주기 놓침 225 → 1. 잃은 것은 반응 지연 2.2 → 4.4 cm 인데,

### 6.7 pose_bootstrap_node — 실행기 스레드 28개

`MultiThreadedExecutor()` 가 인자 없이 만들어져 rclpy 가 CPU 코어 수만큼 스레드를 깔았다.
세션이 하나도 안 열린 대기 상태에서 **코어 하나의 12.6 %**(run30 CPU 상위 소비의 15 %).
콜백은 다 가벼웠다 — 절약 설계(스캔 구독 개폐·30초 청소 타이머·지도 키 검사)는 정상이었다.
`num_threads=2` + `/amcl_pose` 구독도 세션 개폐로 옮겨 **1 스레드 0.0 %** 가 됐다(`9ef3541`).
**[미검증] 실제 pose_check/commit 왕복은 실기 확인 필요.**

## 7. MPPI 파라미터는 사실상 바닥났다

| 축 | 상태 | 근거 |
|---|---|---|
| critic 가중치 7개 | **닫힘** | run25 에서 전부 08-29 값으로 되돌렸는데 46.3 → 47.9 로 무효 |
| `offset_from_furthest` | **닫힘** | 점 개수 단위 + 기준이 궤적 도달점 → 제자리에서 0.4 m 로 붕괴 |
| `PreferForwardCritic` | **무효** | 소스상 후진에만 벌점, `vx_min 0.0` 이라 작동 안 함 |
| `temperature` | **닫힘** | 0.3·0.6·0.9·1.2 네 점. 0.9 가 자리 |
| `gamma` | **닫힘** | 0.015·0.03·0.05 세 점. 올릴수록 나쁨 |
| `batch_size` | **모형대로** | 잡음 ∝ 1/√N. 2000 에서 CPU 와 균형 |
| `model_dt`·`controller_frequency` | **강제** | setOffset() 이 같기를 요구. 10 Hz 로 놓침 해결 |
| `prune_distance` | 3.0 유지 | 부작용 증거 없음 |
| `wz_std` | **유일한 활성 축** | 잔떨림과 제자리 회전을 **반대로** 움직인다 |

**아직 안 건드린 것 둘** — 둘 다 작다.
- `PathAlignCritic.use_path_orientations: true` — 소스 확인: 비용이
  `√(dx²+dy²)` 에서 `√(dx²+dy²+dyaw²)` 로 바뀐다. 경로의 **방향**까지 맞추므로
  U턴 호에 유리할 수 있는 **유일하게 남은 후보**다. 다만 경로 점의 yaw 품질에 기댄다.
- `iteration_count: 1 -> 2` — 표본을 늘리는 것과 같은 효과에 CPU 2배. `batch_size` 로
  이미 같은 축을 썼다.

**구조적 한계(파라미터로 못 넘는 것)**
1. `wz_std` 하나가 잔떨림과 제자리 회전을 **반대로** 돌린다. 둘을 분리하는 값이 없다.
2. MPPI 는 평균이라 **명령이 거의 매 주기 바뀐다**(같은 값 유지 5 % vs DWB 76 %).
   크기는 DWB 를 이겼어도 **방향 바뀜은 구조적으로 진다**(37.5 vs 35.8).
3. 목적지 0.2 m 안에서 경로가 점 1개가 되면 critic 의 기준이 무너진다.

**MPPI 가 이기는 것**: 손잡이 진동의 *크기*, 벽 여유, 동적 장애물(더 멀리 보고 더 짧게 멈춤),

**DWB 가 이기는 것**: 방향 바뀜, 제자리 회전(특히 U턴), 코너 속도, 결과의 안정성.

**비카 기준으로 보면** 손잡이를 잡은 사람에게 가장 거슬리는 것은 *방향이 바뀌는 순간*이고
(크기는 이미 MPPI 가 이겼다), 안내 로봇에 가장 위험한 것은 *좁은 곳에서 제자리로 도는 것*이다.
**둘 다 DWB 가 낫고, MPPI 에는 그 둘을 동시에 고치는 파라미터가 없다.**
다음 시험(`wz_std 0.42`)에서 제자리 회전과 잔떨림의 접점이 안 나오면 **RPP 로 넘어간다** —
RPP 는 곡률 감속·근접 감속을 기본으로 갖고 충돌 검사를 조건 없이 몸통 전체로 한다
(`nav2-controller-rpp-ready-2026-09-18` 에 값·판정선 준비됨).

## 9. run34 — `wz_std 0.42` 절충 실패. MPPI 종료

커밋 `9ef3541`. 바뀐 값은 `wz_std` 하나(0.35 → 0.42). 완주 8/8, 제어주기 놓침 0.

**코너는 고쳐졌다.** 일반 코너 제자리 회전이 **3 %**다(run30 14 % · run32 33 %).
사용자 관찰 "코너에서 거의 멈칫하지 않았다"와 일치한다.

**직진은 오히려 나빠졌다.** 사용자는 "비슷한 것 같다"고 했으나 수치는 다르다.
같은 설정에서 `wz_std` 만 다른 두 회차를 직접 붙이면:

```

        wz_std 1.20배 → 흔들림 1.51배 (비례보다 빠르다)
        DWB 는 0.084 — run34 는 DWB 보다 나쁘다
```

**U턴 제자리는 54 %로 그대로다**(run30 61 · run32 55 · run33 50).

|---|---|---|---|---|

## 10. RPP 전환 (`8335a23`)

MPPI 는 `FollowPathMPPI` 로, DWB 는 `FollowPathDWB` 로 보존했다. 되돌리기는 이름 교체 한 곳.

### 10.1 무엇이 달라지나 — 세 가지다

**① 곡률 감속.** 경로가 굽을수록 스스로 느려진다. `regulated_linear_scaling_min_radius`
1.2 로 감속이 일찍·세게 걸린다. 회전 상한 0.5 와의 정합:
`R 1.0 → v 0.42·w 0.42 / R 0.5 → 0.21·0.42 / R 0.3 → 0.13·0.43 / R 0.24 → 0.12(하한)·0.50`.
**낮추면 부등식이 깨져 planner 호를 못 따라가고 "직선에서도 흔들린다" 가 난다.**

**② 근접 감속.** 장애물에 가까울수록 느려진다. run28 의 "벽과 나란히 0.5 m/s 전속 직진"
이 구조적으로 안 난다. `cost_scaling_dist 0.35` · `inflation_cost_scaling_factor 3.5`
(**costmap 의 cost_scaling_factor 와 반드시 같아야** 비용→거리 역산이 맞다).

**③ 조건 없는 몸통 충돌 검사.** `inCollision()` 이 `footprintCostAtPose(x,y,θ,footprint)`
를 무조건 부른다. MPPI 는 중심 셀 비용이 0 이면 건너뛴다 — **미해결 `inflation 0.55 <
외접 0.620` 사각지대에서 RPP 가 더 안전하다.** 단 둘 다 254 에서만 거부하고 253 은 통과한다.

### 10.2 08-13 철회의 진짜 원인과 지금 다른 점

당시 회전 반전 6.1 → **24.3 회/분**. 범인은 `rotate_to_heading` 임계 진동이다.
```
shouldRotateToPath = use_rotate_to_heading && |atan2(carrot_y, carrot_x)| > min_angle
참이면 rotateToHeading() → linear_vel = 0.0   (전진을 끊고 제자리 회전)
```
**히스테리시스가 없다.** 그때 planner 가 목적지까지 그린 경로가 1 Hz 로 통째로 바뀌어
조준점 각도가 임계(1.0 rad) 근처를 오갔다 → 매초 "정지-회전 ↔ 주행" 반전.
**lookahead 1.5 → 2.5 로도 24.7 로 그대로였던 이유**: lookahead 는 조준점의 *거리*를
바꾸지만 이 판정은 *각도*만 본다.
**지금 다른 조건**: 레일 8판-3 이라 목표가 3 m 앞 당근이고, 앞 3 m 가 비면 레일 경로를
그대로 쓴다(RailDirect) → 경로가 통째로 안 흔들린다. 코너에는 호가 미리 굽어 있다(R 1.0).

### 10.3 회전 상한을 같이 내렸다

**RPP 에는 회전 상한 파라미터가 없다.** MPPI 는 자체 `wz_max 0.5` 가 있어 스무더의
1.0 이 안 걸렸다. 그대로 두면 손잡이 끝(회전중심 0.62 m)이 **0.62 m/s** 로 휘둘린다.
`velocity_smoother.max_velocity[2]` 1.0 → **0.5**, `max_accel[2]`·`max_decel[2]` ±3.2 → **±2.0**
(RPP 는 곡률 추종 구간에 각가속 제한이 없어 스무더가 유일한 방어다).

### 10.4 [한계] RPP 는 사람을 피하지 못한다

공식 README: "순수 추종 컨트롤러는 동적 장애물에 관심도 걱정도 없이 경로만 따라간다."
**멈출 뿐이다.** 회피는 레일 BT 가 맡는다(앞 3 m 막힘 → 당근 모드 → planner 우회).
**레일 옆 0.2~0.5 m 에 비껴 선 사람은 `IsPathValid` 도 못 거르므로 DWB·MPPI 가 비켜
가던 자리에서 RPP 는 정지하거나 스친다 — 판정 1순위다.**
