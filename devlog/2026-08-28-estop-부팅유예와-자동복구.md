# 2026-08-28 통신 원인 E-stop의 부팅 유예와 자동 복구

## 발단

사용자 문제 제기: "설정값이 여러 조건을 너무 타이트하게 감시하다 보니 조금의
지연에도 주행 중 비상정지가 활성화되는 것 같다."

추측으로 답하지 않고 젯슨 `~/.ros/log`의 8월 전체(1215개 파일)를 집계했다.

## 1. 실측 — 문제의식은 맞고 위치가 다르다

원인별 (최근 8일, 125건):

| 원인 | 횟수 | 비율 |
| --- | --- | --- |
| `motor_can_stale` (단독 57 + 조합 30) | 87 | 70 % |
| `physical_f1` | 29 | 23 % |
| `app` / `voice` | 6 / 3 | 7 % |

통신 지연이 사람이 실제로 누른 것보다 3배 많다. 여기까지는 제기된 대로다.

그런데 전이 직전 상태로 나누면 그림이 달라진다 (8월 전체):

| 전이 | 횟수 | 뜻 |
| --- | --- | --- |
| `IDLE → FAULT` | **229** | 부팅 직후 |
| `CLEARED → *` | 154 | 대기 중 |
| `READY_TO_GO → *` | 142 | reset 후 출발 대기 중 |
| `RUNNING → ESTOP_ACTIVE` | 12 | 주행 중 (사람·CAN 오류) |
| `RUNNING → FAULT` | **2** | 주행 중 통신 지연 |

**주행 중에 통신 지연만으로 멈춘 것은 8월 통틀어 2회**다. 최근 8일은 0회다.

체감이 "주행 중"인 이유는 `READY_TO_GO`에서 걸리는 142회로 보인다. reset을
마치고 출발하려는 순간에 멈추면 주행 중 멈춘 것으로 느껴진다. 2026-08-20
"다시출발 먹통" 사건이 그 형태였다.

## 2. 진단 — 타임아웃 값의 문제가 아니다

`/motor/can_ok`는 33 ms(30 Hz) 주기이고 타임아웃은 0.5 s다. 즉 **15프레임 연속**
미수신이어야 발동한다. 여유는 15배이고, 한두 프레임 지연으로는 걸리지 않는다.

229회의 원인은 지연이 아니라 **미수신**이다. 노드가 뜬 직후에는
`last_physical_ns`·`last_motor_can_ns`가 `None`인데 `is_fresh_ns(None)`이
`False`를 돌려주므로(`freshness.py:26`) 첫 `evaluate()`에서 곧바로 `*_stale`이
붙는다. 0.5 s를 기다리지도 않고 25 ms 만에 걸린다.

그래서 `motor_can_timeout_sec` 상향은 해법이 아니다. 5 s로 늘리면 150프레임,
1분으로 늘리면 1800프레임 연속 미수신이 될 뿐 결과는 같다. 진짜 CAN 고장 감지만
늦어지므로 **이 축은 기각한다.**

`initially_latched=True`(`emergency_stop_node.py`) 한 줄을 지우는 것도 소용없다.
50 ms 뒤 첫 판정에서 똑같이 걸린다.

근본 원인은 하나다: **"아직 안 옴"과 "받다가 끊김"을 구분하지 않는다.**

## 3. 설계 — 성격이 다른 둘을 나눈다

| 원인 | 성격 | 처리 |
| --- | --- | --- |
| `physical_f1`·`app`·`voice` | 사건 — 사람이 판단해서 눌렀다 | 래치 + 관리자 reset (그대로) |
| `motor_can`·`*_stale` | 상태 — 지금 통신이 안 된다 | 래치 + **정지 중 자동 복구** |
| `*_waiting` | 대기 — 아직 첫 수신 전이다 | **래치하지 않음** |

자동 복구 범위는 사용자가 **"정지 중일 때만"** 으로 정했다. 주행 중에 로봇이
말없이 재출발하면 핸들을 잡은 사람이 놀란다.

## 4. 구현

- `EmergencyLatch`에 부팅 유예(`input_grace_ns`). 첫 수신 전의 미수신은
  `*_waiting`으로 두고 래치를 걸지 않는다. 유예를 넘기면 종전대로 `*_stale`,
  한 번 수신한 뒤의 단절은 유예와 무관하게 즉시 `*_stale`이다.
- `emergency_stop_node`가 `/estop_sources`로 원인 종류를 발행한다. `Bool` 두
  개로는 통신 원인과 사람 개입을 구분할 수 없었다. 상태 이름 `WAITING_INPUT`도
  추가했다(진단은 ERROR가 아니라 WARN).
- `AutoRecoveryPolicy`(신규 순수 모델)가 판정한다. 조건 넷을 모두 만족해야 한다:
  원인이 통신 계열뿐 / 주행 중 끊김이 아님 / settle 1.0 s 유지 / 수동 reset과
  경합 없음.
- `app_emergency_node`가 그 판정에 따라 기존 `run_reset_sequence()`를 대신
  호출한다. **절차·순서·fail-closed 성질은 그대로다.** 바뀐 것은 누가
  시작하느냐뿐이며, 통신이 아직 안 돌아왔으면 `estop_reset` 단계에서 거부된다.

새 노드는 만들지 않았다. 필요한 부품이 이미 있었다 — `app_emergency_node`가
reset 오케스트레이터이고 `/safety_state`를 이미 구독하므로 "직전에 주행
중이었나"를 추가 배선 없이 알 수 있다.

### 파라미터

| 이름 | 노드 | 기본값 |
| --- | --- | --- |
| `input_grace_sec` | `emergency_stop_node` | 15.0 |
| `auto_recover_settle_sec` | `app_emergency_node` | 1.0 |
| `auto_recover_enabled` | `app_emergency_node` | True |

앞의 둘을 0 / 매우 큰 값으로 두거나 셋째를 False로 하면 종전 동작이다.

## 5. 검증

단위 시험 123개 통과(신규 24개). 신규 시험은 **뮤테이션 8건**으로 실효성을
확인했다 — 구현을 일부러 깨뜨렸을 때 해당 시험이 정확히 하나씩 잡았다.
시험이 그냥 통과하는 것과 실제로 무언가를 지키는 것은 다르다.

젯슨 3노드 통합 실행(`input_grace_sec=3.0`, `settle=1.0`):

```
144.972  [WAITING INPUT] IDLE -> WAITING_INPUT   source=motor_can_waiting,physical_waiting
147.922  [FAULT] WAITING_INPUT -> FAULT          source=motor_can_stale,physical_stale
151.472  [WAIT RESET] FAULT -> ESTOP_RELEASED_WAIT_RESET   source=none
152.856  [AUTO RECOVER] cause=physical_stale settle=1.0s state_before=ESTOP_ACTIVE
153.058  [ESTOP LATCH CLEARED]
153.075  [SUPERVISOR RESET] state=READY_TO_GO
153.107  [SAFETY READY] -> READY_TO_GO reset_armed=True
153.109  [AUTO RECOVER] 완료
```

관리자 개입 0회로 `READY_TO_GO`에 도달했다. 원인 해소(151.47)부터 복구
시작(152.86)까지 1.38 s로 settle 1.0 s + 확인 주기 0.5 s와 맞는다.
유예 구간도 정확했다(2.95 s).

## 6. 실주행 결과 — 4항목 전부 통과 (2026-08-28 저녁)

젯슨 실기로 네 가지를 모두 확인했다. 바퀴를 든 상태로 진행했다.

| # | 절차 | 기대 | 실측 |
| --- | --- | --- | --- |
| 1 | 정상 기동 | 앱 reset 0회 | **통과.** 기동 3.7 s 만에 원인 해소, 1.36 s 뒤 자동 해제 |
| 2 | **정지 중** motor node 종료 → 재실행 | 자동 복구 | **통과.** 원인 해소 1.43 s 뒤 `[AUTO RECOVER]` |
| 3 | **주행 중** motor node 종료 → 재실행 | 자동 복구 **없음** | **통과.** 57 s 무반응, 앱 reset 으로만 해제 |
| 4 | 물리 버튼 눌렀다 해제 | 자동 복구 **없음** | **통과.** 89 s 무반응, 앱 reset 으로만 해제 |

3번이 이 변경의 핵심 안전 판정이었다. 같은 원인(`motor_can_stale`)인데 상태만으로
갈렸다는 것이 로그에 그대로 남았다.

```
[정지 중] 917484.405  원인 사라짐
          917485.832  [AUTO RECOVER] cause=motor_can_stale     ← 1.43 s, 자동
[주행 중] 917997.833  RUNNING -> ESTOP_ACTIVE                  ← 주행 중임을 인식
          918007.125  원인 사라짐 (motor node 재실행)
          918064.073  ESTOP LATCH CLEARED                      ← 56.9 s, 앱 reset
```

집계: 실기 중 `motor_can_stale` **7회** 발생, 그중 **5회 자동 복구**. 나머지 2회가
3번(주행 중)과 4번(물리 버튼 혼재)으로 설계대로 관리자에게 넘어갔다.

`RUNNING` 상태는 `/cmd_vel_req`에 직접 발행해 만들었다(knob 0 %로 두면 상태는
`RUNNING`이면서 바퀴는 돌지 않아 더 안전하다). `can1 down`은 쓰지 않았다 —
바퀴가 스스로 돌 수 있고, 그것을 막으려고 물리 버튼을 누르면 `physical_f1`이
붙어 시험 조건 자체가 깨진다.

### 실기에서 드러난 것

**물리 버튼을 누르고 기동하면 부팅 시 앱 reset이 여전히 필요하다.** 기존 안전
기동 절차의 ①이 물리 버튼 누름이기 때문이다. 이것은 결함이 아니라 설계대로이며,
"사람이 손댄 사건은 사람이 마무리한다"는 원칙의 결과다. 부팅 자동 해제를 보려면
물리 버튼 대신 **바퀴를 들어** 그 구간을 막아야 한다.

## 7. 남은 관찰 — motor_can_stale 재발 빈도

실기 20분 남짓에 `motor_can_stale`이 7회 났다. 그중 5회는 일부러 만든 것이지만,
17762 처럼 손대지 않았는데 난 것도 있다. 자동 복구가 매번 풀어 주므로 운영에는
지장이 없으나, **그 자체가 근본 원인을 덮는다.** 다음 실주행에서 다음을 센다.

```
grep -hc "AUTO RECOVER] cause" ~/.ros/log/python3_*.log
```

주행 중 자연 발생이 잦으면 CPU 포화(load 14 / 코어 8)를 먼저 본다.

## 8. 부수적으로 확정한 사실

- **`motor_can`은 CAN 소켓·인터페이스 오류만 잡는다.** socketcan은 상대
  드라이버가 없어도 bind·send가 성공하므로, 드라이버 전원 차단은
  `physical_stale`로 나타난다. `physical_stale`을 보고 물리 버튼을 찾으면
  헛수고다.
- **F1 방송을 켜는 주체는 motor node다**(`CMD_PNT_IO_MON_ON`,
  `mdrobot_can_keyboard_knob_node.py:199`). 안전 노드는 CAN을 읽기만 한다.
  기동 순서를 어기면 `physical_stale`이 뜨는 이유가 이것이다.
- `physical_f1` → `button` 이름 변경은 **기각**했다. 실기 1회 비용과 과거 로그
  기록과의 불일치에 비해 얻는 것이 로그 가독성뿐이다. 이 작업과 함께 하면
  비용이 거의 없으므로 다음에 같은 파일을 열 때 재검토한다.
