# 2026-09-01 — 앱에서 금지구역을 그리고, 진단과 비상정지 안내를 현실에 맞춘다

8/31~9/1 이틀에 걸쳐 다섯 가지를 붙였다. 공통점이 하나 있다 — **로봇이 이미 알고
있는 사실을 앱이 정확히 알게 하는 경로**를 손봤다. 새 권한을 앱에 준 것은 없다.

## 1. 금지구역 — 앱에서 그리고 Nav2가 지킨다

관리자가 지도 위에 사각형을 끌면 로봇이 그 안에 들어가지 않는다. 원본 지도는
건드리지 않고 같은 크기의 마스크 파일을 따로 만들어 Nav2에 물린다.

### 마스크 배경은 흰색이 아니라 회색 128이다

이 작업에서 가장 중요한 결정이다. Humble `keepout_filter.cpp`의 갱신 규칙이 두
줄이다.

```cpp
if (data == NO_INFORMATION) { continue; }              // 마스크가 '모름'이면 건드리지 않는다
if (data > old_data || old_data == NO_INFORMATION) {   // 그 외에는 덮어쓴다
```

즉 **흰색(free=0)은 costmap의 '모르는 칸'을 '빈 칸'으로 덮어쓴다.** trinary에서
128은 `occ = 0.498`이라 `free_thresh 0.25`와 `occupied_thresh 0.65` 사이 —
정확히 '모름'이다. 그래서 사각형이 하나도 없는 마스크가 **완전한 무동작**이 되고,
그래야 빈 마스크를 미리 만들어 둬도 안전하다. launch가 항상 같은 모양이 되는
것이 그 덕이다.

지금 지도(`vica_map_0630`)는 205 회색이 82.1 %인데 `free_thresh: 0.25`라 그
칸들이 이미 free로 읽힌다. 그래서 **흰 배경이어도 오늘 당장 사고는 안 난다.**
회색은 임계값을 ROS 표준 0.196으로 바꾸는 날 조용히 터지는 것을 막는 여유다.

### PNG가 아니라 PGM이다

앱 지도 목록이 `maps/*.png`를 훑는다(`map_list_node.publish_maps`). `_keepout.png`를
만들면 지도 드롭다운에 유령 지도가 하나 더 생긴다. 확장자만 바꾸면 그 코드에 손을
안 댄다. P5는 표준 라이브러리로 써서 Pillow·ImageMagick 의존성도 없다.

### 적용은 재시작이 아니라 load_map이다

마스크 서버는 `nav2_map_server::MapServer` 인스턴스다. Humble의 MapServer는
`<노드>/load_map`을 열고 ACTIVE 상태에서 새 yaml을 읽어 같은 토픽에 다시
발행한다. 그 토픽이 `transient_local`이라 KeepoutFilter가 곧바로 받는다.
Nav2 재시작은 AMCL 재수렴과 초기 위치 다시 잡기를 끌고 온다 — 사각형 하나
고치자고 치를 값이 아니다.

**주행 중에는 적용하지 않는다.** 로봇이 새 금지구역 안에 서 있으면 planner가
`Starting point in lethal space`로 실패한다. 저장만 하고 `busy_driving`으로 답한
뒤, 주행이 끝나는 순간 한 번 자동으로 적용하고 `/vica/keepout/state`로 알린다.

### 금지구역에는 inflation이 붙지 않는다

`LayeredCostmap`이 plugins를 먼저 돌리고 filters를 나중에 master grid에 얹는다
(`layered_costmap.cpp` 262~268행). 공식 문서도 "inflation layer와의 간섭을 막으려고
분리했다"고 적었다. 그래서 **로봇은 금지구역 경계선에 몸을 딱 붙일 수 있다**
(내접반경 0.277 m). 앱이 "실제로 막을 범위보다 20~30 cm 크게 그리라"고 안내한다.

마스크를 자동으로 넓히지 않는 것은 사용자 결정이다(A안) — 화면에 보이는 사각형과
로봇이 지키는 사각형이 달라지면 사람이 화면을 믿을 수 없게 된다.

### local costmap은 보류

local의 `global_frame`은 `odom`이라 마스크(map frame)와 달라 KeepoutFilter가
**셀마다 TF 변환**을 돌린다(`keepout_filter.cpp` 285~315행). 6×6 m / 0.05 =
14,400칸을 5 Hz로 갱신하는데 CPU 여유가 이미 빠듯하다(load average 최대 13.8,
제어주기 놓침 0 → 2). global 적용 뒤 `missed its desired rate`를 세어 판단한다.
공식 문서도 둘 다가 항상 필요한 것은 아니라고 적었다.

### 통신은 topic 왕복이 아니라 service다

`SaveKeepout`·`GetKeepout` 두 srv를 새로 만들었다. 최근 앱 기능(PoseCheck·
SaveHome·SaveMap·DeleteMap)이 전부 service이고, topic이면 `request_id` 짝 맞추기와
상태 5종을 앱이 직접 관리해야 한다. 앱은 언제나 **사각형 전체 목록**을 보내므로
삭제 전용 서비스가 없다 — 삭제는 '그 사각형이 빠진 목록'이다.

### 함께 막은 구멍 둘

- `map_list_node`의 지도 삭제 목록에 keepout 세 파일을 넣었다. 빼먹으면 지도를
  지워도 파일이 남아, 같은 이름으로 지도를 다시 만들 때 **옛 금지구역이
  되살아난다.** 화면에 아무 표시도 안 남아 조용히 틀린다.
- `vica_map_save.sh`의 덮어쓰기 검사에도 같은 세 파일을 넣었다.

## 2. 지도 설정 — 세 가지를 한 번에 하나만 펼친다

'장소 저장' 메뉴를 **'지도 설정'**으로 바꾸고 장소·홈·금지구역을 접히는 칸으로
나눴다. 지도 삭제는 종전대로 맨 아래에 따로 둔다.

접는 이유가 보기 편해서만은 아니다. 세 칸은 **지도 터치를 서로 다르게 쓴다** —
장소 찍기·홈 찍기·사각형 끌기. 펼친 칸이 지도 조작권을 가지므로 지금 무엇을 찍는
중인지가 화면에 늘 드러난다.

**TransformationController를 쓰지 않았다.** `GestureDetector`가
`InteractiveViewer`의 자식 안쪽에 있어 `details.localPosition`이 이미 확대·이동이
되돌려진 좌표다. 초기 위치 짚기가 같은 경로로 실기 검증을 통과했다. 한 번 더
되돌리면 두 번 되돌려 어긋난다. 편집 중에는 `panEnabled`·`scaleEnabled`를 꺼서
손가락을 끌 때 지도가 따라오지 않게 한다.

## 3. 웹에서 지도 그림만 안 보이던 것 — 몇 주 묵은 CORS

"ROS 연결도 되고 지도 목록 드롭다운도 뜨는데 이미지만 안 뜬다. 저번부터 그랬다."

원인은 헤더 한 줄이었다.

```
Access-Control-Allow-Origin: *
```

지도 서버가 `python -m http.server`였고 이 헤더를 안 찍는다(요청에 `Origin`을
붙여 실측 확인). 브라우저는 A 주소의 화면이 B 주소의 파일을 읽으려 하면 B가
허락했는지 먼저 본다. **출처에는 포트도 포함**되므로 젯슨 위에서 브라우저를 띄워도
`localhost:5000`과 `localhost:8000`은 서로 남이다 — IP를 아무리 맞춰도 안 된다.

증상이 고약했던 이유는 나머지가 전부 멀쩡해 보였다는 것이다. 목록은
rosbridge(WebSocket)로 오고 그림만 HTTP로 오는데, **WebSocket은 이 검사를 받지
않는다.** 그래서 원인이 네트워크나 앱 코드처럼 보였다.

가른 방법은 5초짜리였다 — 브라우저 주소창에 이미지 URL을 직접 친다. 보이면 서버·
주소·방화벽이 다 정상이라는 뜻이고, 앱 안에서만 막힌 것이다.

APK와 Linux desktop은 브라우저가 아니라 이 검사가 없다. 팀이 예전에 브라우저를
접고 Linux desktop으로 방향을 바꾼 기록이
`VICA_Supervisor/docs/conversation_summary_for_gpt.md`에 있다. **정상 경로는 여전히
그쪽이다.** 그래도 고친 이유는 다음에 누가 크롬으로 열 때 같은 원인을 처음부터
다시 찾기 때문이다.

내보내는 범위를 `/maps/` 아래로 좁혔다. 저 헤더는 "아무 웹페이지나 이 파일을 읽어도
좋다"는 뜻이라 작업공간 전체를 그 상태로 열어 둘 이유가 없다.

## 4. 진단이 쓰지도 않는 것을 감시하고 있었다

앱 시스템 진단에 '3D 인식 저하'가 상시로 떴다. 원인은 nvblox Docker를 안 띄운
것인데, **Nav2는 이미 nvblox를 쓰지 않는다** — `nav2_params.yaml`의 global·local
plugins 어디에도 `nvblox_layer`가 없다. 감시만 현실보다 뒤처져 있었다.

이런 경고가 상시로 떠 있으면 사람이 결함 표시 자체를 무시하게 된다. 그게 진짜
비용이다.

카메라가 실제로 쓰이는 길로 감시를 옮겼다.

```
/camera/camera/depth/color/points  (D455)
    -> depth_band_to_scan (0.30~1.05 m 띠만 눌러 2D로)
/camera/depth_scan
    -> local_costmap 의 observation_sources: scan depth_scan
```

### 점군 구독을 계약 시험이 막았다

처음에 `/camera/camera/depth/color/points`를 직접 감시하게 짰다가
`test_camera_probes_watch_camera_info_not_image`에 걸렸다. 640×480 XYZRGB를 30 Hz로
복사하면 **감시 노드가 초당 수백 MB를 먹는 대역폭 소비자**가 된다. 그 시험이
막으려던 것이 정확히 이것이었다.

대신 이미 있던 `camera_depth`(camera_info, 수백 바이트)와 짝을 지으면 감시 비용
없이 원인이 갈린다.

```
camera_depth 도 함께 끊김  ->  카메라(또는 컨테이너)가 죽었다
depth_scan 만 끊김        ->  변환 노드가 죽었다. 카메라는 멀쩡하다
```

시험 규칙은 '반드시 camera_info'에서 '원본 프레임 금지'로 고쳤다. 막으려던 것은
'카메라 토픽'이 아니라 '무거운 원본'이고, `/camera/depth_scan`은 빔 173개짜리
LaserScan이라 camera_info와 크기가 비슷하며 costmap이 실제로 먹는 값이다.

`min_hz`·`max_hz`는 넓게 두고 `[미검증]`으로 표시했다. 이 파일의 다른 값은 전부
`[정지 실측 2026-08-01]` 주석이 붙어 있는데, 근거 없는 값을 하나 더 만들지 않는다.

컴포넌트 키 `perception`은 그대로다 — `RobotHealth.msg`의 필드 이름이라 바꾸면 세
저장소 계약이 흔들린다. 앱 표시 문구만 '3D 인식' → **'카메라 인식'**.

## 5. 현장에서 걸린 비상정지에 관리자 호출을 알린다

LLM 쪽에 "비상정지 시 관리자를 호출한다"는 안내가 있다. 앱에도 같은 사실을 띄운다.

```
주행 중 비상정지로 비카가 관리자를 호출했습니다. 확인이 필요합니다.
```

**관리자가 앱에서 직접 누른 경우에는 붙이지 않는다.** 부르는 사람과 받는 사람이
같다. 그런데 앱은 그것을 가릴 수 없었다 — `/app_estop_state`에 `active`·`message`·
`reset_allowed`·`auto_recovered`뿐이고 **누가 걸었는지가 없다.**

원인은 ROS에는 있었다. `/estop_sources`에 `physical_f1`·`app`·`voice`·`motor_can`·
`*_stale`이 나가고 `app_emergency_node`도 `last_estop_sources`로 들고 있다. 그래서
같은 상태 메시지에 `sources`를 실어 보낸다. 앱이 `/estop_sources`를 따로 구독하면
두 토픽의 도착 순서가 어긋나 **원인을 모르는 채 팝업이 먼저 뜨는 순간**이 생긴다.

### 함정 — last_estop_sources는 해제된 뒤에도 남는다

`estop_sources_callback`이 빈 목록으로는 덮어쓰지 않는다. 자동 복구 로그가 "무엇
때문에 걸렸던 것인지"를 적어야 해서 그렇게 되어 있다. 그 값을 그대로 내보내면 앱은
**이미 풀린 비상정지의 옛 원인**을 보게 된다. 그래서 걸려 있을 때만 싣는다.

키를 더하기만 했으므로 이 필드를 모르는 기존 앱은 그대로 동작한다. 그때는 원인을
모르는 것으로 보고 문구를 붙이지 않는다 — 모르면서 "불렀다"고 말하는 쪽이 더 나쁘다.

### 팝업 겹침을 정리했다

주행 중 물리 버튼을 누르면 두 가지가 함께 일어난다 — 비상정지가 걸리고, 가던
목적지가 취소된다. 그래서 전체화면 비상정지 알림 위에 "주행이 취소되었습니다"가 한
번 더 겹쳤다. 같은 사건을 두 번 알리는 것이고, 그렇게 쌓인 팝업은 관리자가 읽지 않고
닫는 습관을 만든다(성공을 팝업으로 알리지 않는 것과 같은 이유다).

비상정지가 걸려 있는 동안의 **취소**는 팝업을 띄우지 않고 알림 목록에만 남긴다.
**실패**는 막지 않는다 — 아무도 누르지 않았는데 로봇이 스스로 포기한 별개 사건이라
비상정지와 겹칠 일이 없다. 주행 실패 팝업에는 `비카가 관리자를 호출했습니다.
확인이 필요합니다.`를 넣었다.

조사 중에 하나 나왔다: 앱의 `GoalEventKind.emergencyStopped('emergency_stopped')`는
**ROS에서 아무도 발행하지 않는 죽은 값**이다. E-stop이 걸리면 Nav2 goal이 취소되어
`goal_canceled`가 온다.

## 실기 확인 목록

같은 날 다른 작업(초기 위치 3단계 탐색, 통신 타임아웃 3초, 라이다 점 표시)도 함께
올라와 있어 아래에 넣었다. **순서대로 하면 앞 단계가 뒷 단계의 전제를 만든다.**

### 0. 빌드와 기동

```bash
colcon build --packages-select vica_interfaces vica_nav2 vica_system_monitor vica_safety
```

- [ ] `vica_interfaces` 빌드 성공 (srv 2개가 새로 생겼다)
- [ ] `ros2 param get /emergency_stop_node motor_can_timeout_sec` → **3.0**
      (다른 작업의 변경. 0.5로 나오면 빌드/설치가 안 붙은 것)

### 1. 지도 그림 (CORS)

- [ ] ⑪ Supervisor 브리지 launch **재기동** 후 앱에서 지도가 보인다
- [ ] 크롬으로 열어도 지도가 보인다 (F12 콘솔에 CORS 오류 없음)
- [ ] `curl -I http://<젯슨IP>:8000/maps/<지도>.png` → `Access-Control-Allow-Origin: *`
- [ ] `http://<젯슨IP>:8000/src/` → **404** (범위 축소 확인)

### 2. 시스템 진단

- [ ] nvblox Docker를 **안 띄운 상태**에서 앱 진단에 경고가 **없다** ← 이번 목적
- [ ] `ros2 topic hz /camera/depth_scan` — 값을 적어 둔다(`min_hz`/`max_hz` 조일 근거)
- [ ] 카메라 USB를 뽑으면 '카메라 인식' 저하가 뜬다
- [ ] 카메라는 두고 `depth_band_to_scan`만 죽이면 `DEPTH_SCAN_STALE`만 뜨고
      `CAMERA_DEPTH_STALE`은 안 뜬다 (원인 구분이 실제로 되는지)

### 3. 금지구역 — 파일과 토픽

