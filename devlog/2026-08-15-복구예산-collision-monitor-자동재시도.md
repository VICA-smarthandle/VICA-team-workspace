## 2. 복구 예산 — 여섯 조합을 재고 30 x 1 s 로 갔다

```
 6회 x 5 s = 15 s, 재계획  6번   Goal failed 발생 · 정체 34.0 s
20회 x 2 s = 20 s, 재계획 20번   failed 0. 그러나 비켜난 뒤에도 대기를 다 채움
10회 x 2 s = 10 s, 재계획 10번   No valid 160 · 놓침 18 · load 18.5
30회 x 1 s = 15 s, 재계획 30번   No valid   7 · 놓침  5 · load 10.0   <- 확정
20회 x 1 s = 10 s, 재계획 20번   Goal failed 재발
40회 x 1 s = 20 s, 재계획 40번   총량이 길다는 사용자 우려로 30회로 내림
```

**갈린 축은 총 시간이 아니라 다시 보는 빈도다.** `wait` 는 도는 동안 상황을
보지 않으므로 그 값이 곧 재출발 지연이고, 1 s 가 이 구조의 최소값이다
(Humble `WaitAction` 은 `InputPort<int>`).

같은 15 s 라도 `6회 x 5 s` 와 `30회 x 1 s` 는 재계획 횟수가 5배 다르다.
이것이 결과를 갈랐다.

### run11 -> run12 실측

| | run11 (6 x 5 s) | run12 (30 x 1 s) | |
| --- | --- | --- | --- |
| **최장 정지** | 62.1 s | **28.2 s** | 절반 이하 |
| **정지 시간 합** | 190 s | **127 s** | 33 % 감소 |
| 목적지 도착 | 4곳 | **5곳** | 더 갔는데 |
| 주행 시간 | 329 s | **309 s** | 더 짧다 |
| 이동거리 ÷ 직선거리 | 37.0 | **21.4** | 경로가 곧아짐 |
| **Goal failed** | — | **0회** | |

`No valid trajectories` 가 168 -> 226 으로 늘었지만 **분모가 다르다.** 1초마다
30번 시도하니 시도 횟수 자체가 많아진 것이고, 정작 실패는 0이 됐다. CPU 도
같은 이유로 올랐다(controller 16.6 -> 27.6 %). `load average` 는 오히려
20.2 -> 16.9 로 내렸다.

두 계약을 동시에 만족하는 첫 조합이기도 하다 — 하한 15 s
(`test_recovery_patience_is_long_enough`)와 재출발 상한 2 s
(`test_restart_delay_is_bounded`). 그동안은 한쪽을 맞추면 다른 쪽에 skip 을
걸어야 했다.

## 3. 자동 재시도 — 정체의 절반은 사람이 앱을 누르는 시간이었다

run9 #6 구간 46초의 내역이 근거다.

```
198.3~222.4 s (24 s)  Nav2 가 복구를 시도하다 Goal failed
222.4~242.6 s (20 s)  아무도 아무것도 안 함. 로봇은 실패 상태로 대기
242.6 s               사람이 앱에서 목적지를 다시 보냄
```

**뒤의 20초는 Nav2 도 nvblox 도 아니다.** Nav2 는 이미 포기하고 "다시 시도해
주세요" 안내까지 마친 상태였고, 재시도 코드가 아예 없었다.

기본값은 3초 간격 2회다. 무한 재시도는 하지 않는다 — 통로 1.0 m 에 사람이 서면
남는 0.55 m 로는 어떤 설정으로도 못 지나가므로, 영원히 시도하면 이용자가 상황을
알 수 없다. 사용자 취소(`NavStatus.CANCELED`)와 E-stop 중에는 재시도하지 않는다.

**효과**: 도입 직후 회차에서 `Goal failed` 2회가 모두 자동 회복됐다.

```
방2     883.9 s 출발 -> 919.8 s "길이 막혀 잠시 기다렸다가 다시 가겠습니다" -> 976.8 s 도착
안내소 2064.6 s 출발 -> 2110.6 s 같은 안내 -> 2136.6 s 도착
```

run12 에서는 `Goal failed` 자체가 0이라 재시도가 쓰일 일도 없었다.

### [함정] dwell 이 재시도보다 먼저 끝난다

`dwell_sec`(2.0)이 `nav_retry_delay_sec`(3.0)보다 짧다. 재시도 판정을 `elif` 로
두면 재시도 시각이 오기 전에 dwell 이 끝나 `IDLE` 로 내려가고, `_to_idle` 이
예약을 지워 **재시도가 영영 실행되지 않는다.** 처음 구현이 그랬고 기존 시험
140건이 전부 통과해서 가려졌다. "예약이 있으면 기다린다"를 먼저 판정하도록
고쳤고 시험 셋을 추가했다.

## 4. 남은 문제 — 사람이 가까이 붙었을 때

사용자 판정: *"장애물이 가까이 붙으면 궤적이 전멸하면서 재시도와 nvblox 갱신
시간을 다 채우고 주행을 시작한다."*

**오늘 한 것은 '버티기를 잘하게' 만든 것이지 '지도가 빨리 풀리게' 만든 것이
아니다.** 복구 예산도 자동 재시도도 지도가 풀릴 때까지 버티는 수단이다.

### 왜 가까이 붙으면 갇히나 (run9 실측)

로봇은 앞뒤가 비대칭이다.

```
앞 35.5 cm  ─┤ 로봇 ├─── 손잡이 ─── 뒤 54.6 cm
```

사람이 정면 0.36 m 까지 왔다. footprint 정면 경계가 0.355 m 이므로 **5 mm
차이로 닿기 직전**이었다. 그 뒤 46초를 서 있었는데, 막고 있던 것은 앞이 아니라
뒤였다.

```
시각      전방   후방   측면
199 s      63    100    100    사람이 지나가는 중
202 s       0    100     99    앞은 뚫렸는데 뒤가 막힘
241 s       0     99     99    46초 지속
244 s       0     41     45    뒤가 풀리자 곧바로 출발
```

**방향을 틀려면 손잡이가 반경 0.546 m 를 쓸고 지나간다.** 뒤가 막히면 회전
궤적을 하나도 못 만든다. 앞이 비어 있어도 소용없다.

거리와 정지 시간이 비례한다(run9).

| 최근접 | 정지 |
| --- | --- |
| 1.94 m | 7 s |
| 1.65 m | 11 s |
| 1.54 m | 19 s |
| **0.36 m** | **48 s** |

### 미해결 — planner 의 "lethal space" 판정

정체 구간에서 `planner_server` 가 `Starting point in lethal space` 를 15회
냈는데, **그 시각 두 costmap 의 값 분포 최대가 100 이었다**(충돌 판정 기준은
253). 측정과 판정이 어긋난다.

배제된 가설: costmap 축소(`downsample_costmap` 미설정) · unknown
(`allow_unknown: True`) · footprint 반경 밖(반경 11셀 안에 253 이상 없음).

남은 후보는 Lattice primitive 궤적이 지나는 영역이지만 **bag 만으로는 더 못
판다.** 다만 이 규명과 무관하게 대책은 같다 — 갇히지 않으면 판정할 일도 없다.

## 5. collision_monitor — 갇히기 전에 멈춘다

`velocity_smoother` 와 `/cmd_vel_req` 사이에 끼웠다.

```
controller --cmd_vel_nav--> velocity_smoother --/cmd_vel-->
collision_monitor --/cmd_vel_req--> Safety --> motor
```

폴리곤은 전방만 본다. 후방은 핸들 잡은 이용자가 상시 발동시키므로 두지 않는다
(백로그 §9).

```
PolygonStop  x 0.36~0.60, y ±0.28   정지
PolygonSlow  x 0.36~1.10, y ±0.32   40 % 감속
```

### 정지 위치 계산

```
정상 흐름 (Slow 를 거침)
  1.10 m 에서 40 % 감속 -> 0.2 m/s 진입 -> 0.60 m 에서 정지 명령
  실제 정지 0.524 m -> footprint 앞끝(0.355 m)에서 여유 16.9 cm

갑자기 나타남 (Slow 를 못 거침)
  0.5 m/s 진입 -> 0.60 m 에서 정지 명령
  지연 300 ms 이동 15.0 cm + 감속 10.0 cm = 25.0 cm
  실제 정지 0.350 m -> 여유 -0.5 cm
```

**지배항은 CAN·드라이버 지연 300 ms 다.** 파라미터로 접근할 수 없다(백로그 §8 D2).

run12 에서 정지 2회 · 감속 6회 발동했다. 폴리곤 폭(±0.28)은 내접반경
(0.275 m)보다 5 mm 클 뿐이라 더 줄일 여지가 없고, 통로 폭(0810 병목 1.77 m)에
비해 충분히 좁아 벽만으로 상시 발동하지 않는다.

### 5.1 [함정] cmd_vel_in_topic — 배선이 조용히 끊긴다

처음에 `cmd_vel_smoothed` 로 적었다가 **배선이 통째로 끊겼다.**

```
/cmd_vel_nav       23.8 Hz    controller 는 명령을 내고 있었다
/cmd_vel_smoothed  발행 없음   monitor 가 여기를 보고 있었다
/cmd_vel_req       발행 없음
/cmd_vel_safe      발행 없음   모터까지 아무것도 못 갔다
```

**앱에는 "주행 중" 으로 보이는데 로봇은 한 발도 못 움직였다.** monitor 는
`active` 였고 발동 로그도 없어서 노드만 보면 정상이다.

원인은 `velocity_smoother` 의 실제 발행 이름이다. 노드 기본 출력은
`cmd_vel_smoothed` 지만 nav2_bringup 이 remap 을 건다:

```python
# navigation_launch.py:183
[('cmd_vel', 'cmd_vel_nav'), ('cmd_vel_smoothed', 'cmd_vel')]
```

즉 입력이 `cmd_vel_nav`, 출력이 `/cmd_vel` 이다. 종전 launch 의
`SetRemap(cmd_vel_smoothed -> /cmd_vel_req)` 은 그 remap 위에 한 번 더 얹혀
동작하던 것이었다.

**계약도 같이 틀려 있었다.** `'cmd_vel_smoothed'` 를 상수로 기대해서, 틀린 값을
넣었는데 시험이 통과했다. 이제 nav2_bringup 의 launch 파일에서 remap 을 직접
읽어 비교한다.

**확인법**: `ros2 node info /velocity_smoother` 의 Publishers 를 직접 본다.

## 6. 경로 선택이 회차마다 다르다

사용자 관찰: 같은 구간에서 한 번은 넓은 길, 다음엔 좁은 길을 택했다.

**planner 설정은 오늘 하나도 안 바뀌었다**(`cost_penalty` 4.0 · `inflation`
0.55 · lattice 0.5 m 회전반경 · `tolerance` 0.2). AMCL 과 footprint 도 그 두
회차 사이에는 그대로였다.

남는 설명은 **그 순간의 costmap 상태**다. nvblox 가 30.6초 기억하므로 직전에
사람이나 물체가 지나간 자리가 남아 있으면 그 길을 피한다. **회차마다 지도가
미묘하게 다르고, 재현되지 않는 것이 정상이다.**

`이동거리 ÷ 직선거리` 가 37.0 -> 21.4 로 줄어 경로 자체는 곧아졌는데, 이쪽은
재계획 빈도가 5배로 늘어 경로를 자주 갱신한 결과로 보인다.

이미 무시하고 있을 수 있다. 찍히고 있다면 inflation 까지 붙어 후방 반경 전체가
상시 비싼 지대가 되므로 회전 궤적 생성에 불리하다.
