# 2026-07-29

Nav2 주행 튜닝을 이어갔다. 결론부터 적으면, **그동안 파라미터를 바꿔가며 얻은 "갇혔다"
판정들이 대부분 무효**였다. 복구 동작이 배선 결함으로 한 번도 작동하지 않았기 때문에,
어떤 설정이든 한 번 멈추면 빠져나올 수 없었다. 배선을 고친 뒤 다시 재보니 갇힘의 진짜
원인은 파라미터가 아니라 planner와 controller가 로봇 형태를 다르게 보는 구조적 불일치였다.

## 1. 복구 동작이 한 번도 작동하지 않았다

`bt_navigator`가 planner 실패 뒤 곧바로 `Goal failed`를 내는 것이 이상해 추적했다.

```
/cmd_vel        발행자 5 (전부 behavior_server)   구독자 0    ← 죽은 토픽
/cmd_vel_req    발행자 1 (velocity_smoother)      구독자 1
```

원인은 Nav2 humble `navigation_launch.py`의 remap 누락이다. `controller_server`에는
`('cmd_vel', 'cmd_vel_nav')`를 주는데 `behavior_server`에는 아무 remap도 주지 않는다.
VICA는 `cmd_vel_smoothed → /cmd_vel_req`만 remap했으므로, 복구 동작(`Spin`·`BackUp`·
`DriveOnHeading`)의 속도 명령이 아무도 듣지 않는 `/cmd_vel`로 나갔다.

`CLAUDE.md`의 "Nav2 최종 요청은 `/cmd_vel_req`" 계약 위반이기도 하다.

### 수정

`vica_nav2/launch/nav2_map_test.launch.py`에 노드 지정 remap을 추가했다.

```python
SetRemap(src="behavior_server:cmd_vel", dst="/cmd_vel_req")
```

접두사 없는 전역 `cmd_vel` remap은 쓸 수 없다. `launch_ros/actions/node.py`(468~477행)가
global remap을 node-level보다 **먼저** 붙이고 rcl은 첫 일치 규칙을 쓰므로,
`controller_server`의 `cmd_vel:=cmd_vel_nav`를 덮어써 velocity_smoother를 건너뛰고
velocity_smoother는 자기 출력을 구독하는 자기루프가 된다. 노드 지정 문법은
별도 프로세스로 실증했다(이름이 다르면 규칙이 무시되므로 실패해도 안전하다).

`test_nav2_launch_contract.py`에 계약 테스트 3개를 추가했다. 전역 remap 금지도 포함한다.

### 결과

재기동 후 `/cmd_vel`은 토픽 자체가 사라지고 `/cmd_vel_req` 발행자가 6이 됐다
(velocity_smoother 1 + behavior_server 5). 주행 중 `/cmd_vel_safe`에 wz 1.00이 실려
복구 명령이 Safety를 통과해 모터까지 가는 것을 확인했다.

## 2. 철회한 진단 — LiDAR 자기반사

`Starting point in lethal space` 원인으로 "LiDAR가 자기 핸들 기둥을 보고 그 자리를
lethal로 만든다"고 진단했다가 **철회했다.**

측정 자체는 맞았다. `/scan` 1570 프레임 전부에서 정후방 ±2.75°(720빔 중 12빔)에
0.338~0.394 m 거리로 자기 차체가 찍힌다. 폭 3.6 cm는 핸들 기둥 40×40 mm와 일치하고,
줄자 실측(LiDAR→기둥 0.39 m)과도 맞는다. 앞서 "후방 45°"라고 말한 것은 히스토그램
bin 폭이었고 실제는 5.5°다.

그러나 costmap에는 들어가지 않는다. 실행 중인 시스템에서 확인한 값은 다음과 같다.

```
local  voxel_layer.footprint_clearing_enabled    = True
global obstacle_layer.footprint_clearing_enabled = True
global static_layer.footprint_clearing_enabled   = False
```

footprint 안쪽은 매 갱신마다 FREE로 지워지고, 기둥은 footprint 안이다. bag에서 직접
읽은 비용도 로봇 중심·기둥 자리 모두 0이었다. `laser_filters` 추가나 스캔 각도 제한은
**얻는 것이 없다.**

부수적으로 URDF/STL의 기둥 위치가 실제와 7~10 cm 어긋난다는 것을 확인했다.
CAD는 x −0.265~−0.305, 실측은 −0.205다. 지금 문제는 아니지만 기록해 둔다.

한편 `nvblox_costmap_layer.cpp`에는 footprint clearing이 없다(`updateWithMax`만 한다).
실제로 `r1_dyn25`의 복구 실패 시점에는 footprint 안쪽에 lethal 1셀이 있었다.
`static_tsdf`에서는 관측되지 않아 dynamic 모드에서 더 잘 생기는 현상으로 보인다.

## 3. 갇힘의 진짜 원인

`r2_static`이 방2→화장실에서 목적지 3.63 m 앞에 굳었다. 그 지점(map +4.81, +1.99)의
실측이다.

```
로봇 헤딩              +75.7°
가장 가까운 lethal      0.456 m (로봇 기준 +33.6°)
반경 0.277 m(내접) 안의 lethal    0개   ← planner는 "비었다"
반경 0.707 m(외접) 안의 lethal   38개   ← DWB는 "회전하면 부딪힌다"
로봇 중심 셀 비용        0            ← Starting point in lethal space가 아니다
/plan                  계속 발행됨    ← planner는 경로를 만들고 있었다
마지막 20 s 순변위       0.008 m,  wz 부호전환 124회
```

`SmacPlanner2D`는 중심 셀 비용만 검사하는 점 로봇 planner다(디스어셈블로 확인:
`cmp w0, #0xfc` = 252 초과 거부, 즉 253 INSCRIBED 이상). inflation 덕에 장애물에서
0.277 m는 떨어지지만 그것이 보장하는 것은 **내접원**뿐이다.

VICA는 길이 0.905 m, 외접반경 0.707 m로 내접 0.277 m의 **2.6배**다. 그래서 planner가
통과 가능으로 그린 자리에서 방향을 틀려 하면 0.65 m짜리 후방(핸들)이 0.456 m 거리의
장애물을 쓸게 되고, `ObstacleFootprint` critic이 그 궤적을 전부 거부한다.
남는 것은 속도 0뿐이다.

이것으로 그동안의 관측이 전부 설명된다.

| 관측 | 설명 |
| --- | --- |
| dynamic·static 둘 다 같은 지점에서 갇힘 | `mapping_type`과 무관 |
| `inflation_radius` 0.45→0.38→0.35 무효 | inflation은 내접원까지만 보장 |
| `decay` 0.0/0.5/2.5 전부 무효 | 장애물 개수가 아니라 기하 문제 |
| `ObstacleFootprint.scale` 0.3에서 악화 | footprint 페널티↑ = 거부 궤적↑ |

## 4. 복구 4종이 모두 무력하다

`behavior_server` 로그 실측이다.

```
Running wait      → completed                    5.003 s
Running backup    → Collision Ahead              0.0005 s
Running spin      → Turning 1.57 → Collision Ahead 0.1007 s
```

`Spin`과 `BackUp`은 padded footprint를 미리 스윕해 검사하는데, 0.905 m 차체로는
통로에서 거의 항상 막힌다. `simulate_ahead_time: 2.0`에 `max_rotational_vel: 1.0`
(DWB `max_vel_theta` 0.4의 2.5배)이라 2초 앞 = 114° 회전 전체를 검사한다.
실제 회전량은 목표 1.57 rad에 대해 0.3~23.3°에 그쳤다.

시간 배분은 `Wait` 79 %, 재시도 20 %, `Spin` 1.1 %, `BackUp` 0.007 %다.
**`BackUp` 제거는 시간 단축 효과가 없다.**

다만 안전상으로는 제거가 필요하다. 오늘 실패한 것은 로봇이 갇혀 있었기 때문이고,
트인 곳에서는 검사를 통과해 실제로 0.30 m 후진한다. 실서비스에서 그 방향에는
핸들을 잡은 사람이 있다. `min_vel_x: 0.0`은 DWB만 막고 `behavior_server`에는
적용되지 않으므로, 후진을 확실히 막으려면 BT에서 `BackUp` 노드를 빼야 한다.
`Spin`은 0.6 m 핸들 팔을 사람이 잡은 채로 90° 휘두르는 동작이라 더 위험하다.

## 6. 무효가 된 과거 실험

판정 근거가 "갇혔다"였던 것은 모두 재시험 대상이다. 복구가 죽어 있었으므로 파라미터가
만든 것이 "잠깐의 주춤"인지 "진짜 통과 불가"인지 구분할 수 없었다.

| 파라미터 | 시험값 | 당시 판정 |
| --- | --- | --- |
| `ObstacleFootprint.scale` | 0.3 / 0.4 / 0.5 | 좁은 곳에서 갇힘 → 0.15로 하향 |
| nvblox `mapping_type` | `dynamic` | 쓸 수 없다 |
| `decay_tsdf_rate_hz` | 0.0 / 0.5 / 2.5 | 3개 값 전부 실패 |
| `inflation_radius` | 0.38 / 0.35 | 둘 다 실패 |

반대로 **완주 주행의 측정값으로 판정한 것은 그대로 유효하다** — footprint 실측,
`padding` 0.05, `inflation_radius` 0.45, `forward_point_distance` 0.325,
SmacPlanner2D 교체, `ObstacleFootprint` critic 도입, `observation_persistence` 0.5,
`max_decel` 정합.

완주한 7회를 같은 지표로 재측정했다. 여유는 정적 지도의 벽까지 거리이고,

현재 파일 상태는 `scale015_full` 조합과 사실상 같고, 달라진 것은 nvblox decay 5.0 → 2.5와
복구 배선 연결 두 가지뿐이며 둘 다 개선이다.

## 8. 사선 책상다리 — 센서 한계

낮은 사선 브레이스는 LiDAR 평면(0.382 m)보다 아래에 있어 LiDAR가 아예 못 본다.
nvblox가 유일한 센서인데 여기에 해상도 한계가 있다.

```
voxel_size                                     0.05 m   ← 브레이스 두께 2~4 cm보다 크다
projective_integrator_truncation_distance_vox  4.0      → 절단대 0.20 m
```

슬라이싱을 더 잘게 하는 것은 해법이 아니다. 현재 `esdf_slice` 0.05~0.9 m는 그 높이대
전체를 하나의 2D 평면으로 **최대투영**하는 가장 보수적인 설정이고, Nav2 costmap은 2D라
슬라이스를 하나만 받는다. 남는 레버는 `voxel_size` 하향(메모리·연산 약 4.6배),
`truncation_distance_vox` 하향, decay를 낮춰 기억을 늘리는 것, 그리고 Collision Monitor다.

D455 수평 FOV 87°·전방 고정이라 코너에서 측면으로 넘어가는 순간의 관측 단절은
파라미터로 넘을 수 없다.

## 9. Collision Monitor 검토

지금 도입하지 않기로 했다. 지원 동작은 `stop`·`slowdown`·`approach` 세 가지뿐이고
모두 **속도 크기만** 바꾼다. 방향을 바꾸는 동작이 없으므로 "장애물에서 떨어져 간다"는
목표와 무관하다. 오히려 정지·감속을 추가로 만들어 지금 추적 중인 지표(최장 정지,
서행 횟수, 완주 시간)를 오염시킨다.

도입할 때 주의할 것이 하나 있다. `behavior_server`가 `/cmd_vel_req`로 직접 발행하므로,
Collision Monitor를 velocity_smoother 뒤에만 끼우면 **복구 동작이 그것을 건너뛴다.**
오늘 고친 것과 같은 종류의 결함이다. `official_reference_urls.md` 183행대로 Safety
Supervisor를 대체하지 않고 그 앞에 놓아야 한다.

## 11. Smart Handle — 정지 상태 yaw 드리프트 측정 (별건)

Nav2 튜닝과 무관한 별건이지만 같은 날 같은 실기에서 잰 결과다. 상세는
`devlog/2026-07-28-smart-handle-guidance-plan.md` 10.1c절에 있다.

300초 측정, 9005 샘플(30.0 Hz). **오탐 0회, 회전 진입 임계값 25°까지 여유 417배.**

| 관점 | 값 |
| --- | --- |
| 총 드리프트 | −0.466° (−1.55 m°/s, −5.59°/시간) |
| 최대 편차 | −1.130° |
| 회전 판정 실효값 (1.5초 창 누적 최대) | 0.060° = 임계값의 0.240% |

180초에서 드리프트 방향이 반전됐다. 시간 비례 누적이 아니라 저주파 진동이므로
장시간 운용에서 임계값에 접근하지 않는다. 창 안에서는 느린 드리프트(1.5초당
0.0023°)보다 IMU 순간 노이즈가 26배 지배적인데, 노이즈는 부호가 랜덤이라 창 안에서
상쇄된다.

`ekf.yaml`을 손볼 이유가 없다는 결론이다. 다만 **주행 중 융합 품질은 여전히
`[미검증]`**이며 임계값 확정은 Phase 5b(바닥 주행)에서 한다.

> 측정 구성은 `wheel_ekf.launch.py start_encoder:=false` — IMU 단독 융합이다. 정지
> 상태에서 휠 오도메트리의 vyaw=0이 드리프트를 억제하므로, 이 값은 운영 조건의
> **상한**이다. `/cmd_vel*` 발행자를 띄우지 않았고 CAN에 쓰지 않았다.

> 참고: 오늘 Nav2 시험에서 `ekf_node`가 30 Hz를 못 맞췄던 것(아래 미해결 항목)과 달리,
> 이번 최소 구성에서는 `/odom`이 정확히 30.0 Hz로 나왔다. 부하 문제였음을 시사한다.

## 12. Smart Handle Phase 5a·5b 완료 — 갇힘 재현 사례 하나 추가
